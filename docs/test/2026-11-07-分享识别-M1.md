> 范围：M1 = 纯逻辑识别核心，**不联网、不转存、不接消息层**，只验证「文件事实 → 计划」

## 1. 交付物

| 文件 | 作用 |
| --- | --- |
| `plugins.v2/cloudsubscribex/utils/share_recognize.py` | 三步管线的纯逻辑实现：分类 → 分组 → 选主版本 + 缺集补齐 |

样本 dump 由 parse-lab 的匿名列举脚本产出（`parse-lab/scripts/dump_share_tree.py`，只读列举，不转存、不含凭证）。

## 2. 实现要点（与方案的对应）

- R1 递归：输入即完整文件清单，模块不做深度截断。
- R2/R3：`MEDIA_EXTS` 白名单；`iso` 走 `treat_iso`（默认关）；字幕/外挂音轨 `sidecar` 不进集覆盖，但选中媒体同目录的一起带。
- R4：`build_plan()` **没有 message 参数**，消息层物理上进不来（单测用 `TypeError` 卡死这条路）。
- R5：集覆盖 = 组内媒体文件集号并集；`season_total` 只用来算 `missing`。
- R6：状态仅 `ready / review / skip`，四异常码 `NO_MEDIA / NO_EPISODES / NO_IDENTITY / SCAN_FAILED`。
- 版本：`median(文件体积)` 判质量；主版本 = 中位体积最大组，并列按 `DV > HDR > SDR > 无标签`；缺集按组中位数从大到小补，标 `mixed_quality`，补满即停。

## 3. 真实样本结果

| 样本 | 结果 |
| --- | --- |
| 美人余 `ba3982f86612`（TMDB 294446，S1 28 集） | `skip: NO_MEDIA`，0 选中，21 个 zip 全记噪音 |
| 嫁金钗 `c9e40c8d0c24`（TMDB 300146，S1 30 集） | `ready`，主版本 `4K DV杜比视界 高码率`（中位 6.48GB/集，27 集），28–30 从根目录散文件组（`28/29/30 HDR.mkv`，1.25GB/集）补齐 → 30 集完整、`missing=[]`、`mixed_quality=True` |

与方案预期的差异：方案猜「28–30 从 `4K/` 补」，实测 `4K/` 已有 30 集但中位仅 1.23GB/集，而根目录散落着 3 个 HDR 文件，按体积中位数排序由散文件组先补上。**结论不变**（30 集完整、mixed），只是补集来源更准。

## 4. 测试结果

```
python -m pytest tests/test_share_recognize.py -q
13 passed
```

覆盖：

1. 嫁金钗 ready + 30 集 + `mixed_quality` + 补集 28–30；
2. 主版本必须是中位体积最大组（`4K DV…`），完整的 `4K/` 不顶替；
3. 美人余 `NO_MEDIA`；
4. 消息文本无法进入计划（`TypeError`）；
5. 字幕不计集但跟随转存；
6. 纯字幕分享 `NO_MEDIA`；
7. `work_id=None` → `review: NO_IDENTITY`（不得 ready）；
8. 无集号 → `review: NO_EPISODES`；
9. `iso` 默认关 / 开关打开后可识别；
10. 补集只来自更小的组；主版本已完整则不洗版。

## 5. 已知边界（M1 不做）

- 不接 TMDB：`work_id` / `season_total` 由调用方给，M1 只验证文件侧。
- 不接网盘枚举：输入是 `[{path, size}]`，真实枚举适配在 M2。
- 不接转存：`selected` 只是路径清单，M2 才接 115/夸克转存链路。
- 整目录跑全量 pytest 在 HEAD 上就有 16 个 collection error（测试文件间 mock 污染），与本次改动无关，仍按单文件跑。
