# 扫描落盘覆盖终态（permanently-queued）—— 根因与修复验证（1.7.91）

- 日期：2026-10-27
- 提交：c310cec
- 现象：频道监控资源池 29 条长期停在 `queued`，转存队列 `queue_pending=0`，
  即 worker 已把它们取走不再处理，条目却永远不回结果。

## 1. 根因

1.7.89 引入转存队列后，扫描线程与转存 worker 都会写同一个 `tg_items` 池子：

| 写入方 | 时机 | 写法 |
| --- | --- | --- |
| 扫描 `run_scan` | 每 10 分钟一轮，一轮含抓消息 + 匹配，耗时数分钟 | 用**扫描开始时的快照**整体覆盖 |
| 转存 worker | 后台，每条转存完/失败时 | 锁内读最新→只改目标条目→保存 |

扫描快照是旧的，落盘时把 worker 刚写的 `transferred`/`failed` 覆盖回 `queued`，
而 worker 已从 `_queued_ids` 移除该 id → 再无任何路径处理它。

线上证据（23:45 前后）：

- 23:45:38 日志 `跨盘转存失败：夸克→115 … 未命中秒传，已按设置中止`
- 同一时刻资源池统计仍为 `queued 29`，`failed 0`
- 23:45:03 扫描 `新增 1 条资源` 后落盘 → 覆盖发生

## 2. 修复

`_persist_scan_items()`：

- 在 `_items_lock` 内重新读取最新池子，按 id 合并；
- 最新状态属于 `transferred / skipped / failed` → **保留 worker 结论**，扫描版本丢弃；
- 其余（`new`/`queued`/`ignored`）用扫描版本更新；
- 扫描期间别处新写的条目一并保留；最后在锁内 `_trim_items` + 保存。

## 5. 存量 29 条的处理

重启容器后 `_recover_queued_items()` 会把仍在 `queued` 的条目重新入队（1.7.89 就有的
兜底），因此它们会被重试：成功则 `transferred`，跨盘秒传未命中则 `failed`（状态可见、
不再卡死）。旧代码从未清理这些条目，堆积只会越滚越大。
