# 2026-11-12 1.9.80 循环导入死锁修复 — 验收

## 触发

用户报「插件没法更新」。核查：

| 项 | 结果 |
| --- | --- |
| MP 已装版本 | **1.9.76**（`has_update=True`） |
| 市场索引 / Release | 1.9.79，资产匿名 200 / 5,227,921 B —— **包没问题** |
| MP 日志 13:51:08、16:38:21 | `loader.py - 加载插件 cloudsubscribex 失败：deadlock detected by _ModuleLock('app.plugins.cloudsubscribex.core.api.sync')` |
| 紧随其后 | `lifecycle.py - 插件 CloudSubscribeX 加载失败：加载器未返回匹配的插件类` → 回退旧版本 |

**同一个死锁出现了两次**（13:51 与 16:38），不是偶发。

## 根因（循环导入，两条环路）

`core/__init__.py:3` 会 `from ..utils.notify_template import ...`（触发 `utils` 包），而 `utils` 侧反向 import `core`：

1. `utils/__init__.py:22` → `from ..core.media import media_identity`
2. `utils/__init__.py:21` → `utils/strm_export.py:18` → `from ..core.cloud import CloudDriveCapability`

于是：`core.api.sync` → `from .. import ...` → `core/__init__.py`（拿锁）→ `utils/__init__` → `core.media`/`core.cloud` → **回到仍在初始化的 core 包** → CPython 报 deadlock。

## 修复

| 文件 | 改动 |
| --- | --- |
| `utils/__init__.py` | 删掉 `from ..core.media import media_identity` 与 `__all__` 里的该项（全仓无人从 `utils` 引用它，使用方都直接 `from ...core.media import`）；加注释说明为何不能再加回 |
| `utils/strm_export.py` | `from ..core.cloud import CloudDriveCapability` 从模块级移到**两个函数内的延迟 import**（`_directory_ops` / `rebuild_strm_by_export_tree`），此时 core 包已初始化完 |

`core` → `utils` 这条方向保留（只 import `utils/notify_template.py`，独立文件，不经 `utils/__init__`），`utils` → `core` 彻底断开，环路消除。

## 走过的弯路（如实记录）

我先尝试把 `core/api/*.py` 里 14 处 `from .. import` 全部改成直接子模块导入。**方向没错但代价过大**：这些测试用 `register_module("cloudsubscribex.core", SearchCapability=MagicMock(), ...)` 把符号放在**包级**，改直连后测试桩失效，`test_tmdb_candidate_type_fallback` 等 2 个文件收集失败。**已全部回退**，只保留真正打破环路的 `utils` 侧改动 —— 最小改动、零回归。
