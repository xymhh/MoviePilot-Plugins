# 通知体积校正（1.7.99）

## 现象

2026-10-28 16:08:14 的「网盘订阅助手 · 转存完成」写 **13 个文件 / 合计 2.87GB**，
而 115 目标目录里这 13 集实际写入 **46.75GiB**。
2.87GB 恰好等于 `3,085,704,678` 字节 —— 只等于其中一集（S01E28）的体积。

## 根因

1. 这条通知来自 `_send_finalized_batch`：终态回查后才聚合发送。
2. `_build_finalized_detail` 里 `size = self._detail_size(history_record, item)`，
   而 pending 记录没有 `file_size`、`item` 也没带 `size` → 每条 detail 的 size = 0，
   聚合后仍是 0。
3. `_enrich_transfer_details` 兜底：「size 为 0 时按 file_name 回查历史」，
   而聚合后的 detail 只保留了**最后一集的 file_name**（E28），
   于是拿单集体积填进了 13 集的合计位 → 2.87GB。
4. 原逻辑还有一条短路：`size > 0 and source` 直接 `continue`，
   所以这条 detail 一旦被填成非 0，就再也不会被纠正。

## 修法（1.7.99）

新增纯函数模块 `plugins.v2/cloudsubscribex/handlers/sync/notify_size.py`：

- `history_episode_size(detail, records)`：按 `title` + `season` + `episodes` 匹配历史台账，
  **只认 `status == 成功`**，每集取 `time` 最新一条，累加 `file_size`；
- `apply_history_size(detail, records)`：台账值 > 详情值时才覆盖（体积只增不减），
  返回值即校正后大小。

`notify.py::_enrich_transfer_details` 把这条校正挪到短路判断**之前**，
所有剧集 detail（无论走哪条转存链路）都会用台账核对一次。

## 测试

`tests/test_notify_size_reconcile.py`（6 条，全过）：

- 多集体积累加（真实数值复现 13 集场景）；
- 失败记录不计入（E26 的候选体积 2,851,472,089 不能被算进去）；
- 台账值小于详情值时保持原值（体积只增不减）；
- 每集取最新一条；
- 跨季记录不串；
- 无集数的电影 detail 不受影响。

全量：**952 passed / 3 存量失败 / 2 条环境性收集错误**（p115client 在本机 Python 3.11 下
f-string 语法错误，与本次改动无关），`lint.py --all` 0 error、静默失败面 0/0。
