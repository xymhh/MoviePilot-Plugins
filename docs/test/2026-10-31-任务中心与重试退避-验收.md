## 2. 主 agent 修正的缺陷（委派方原实现）

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 死信在 `begin()` 里被自动复活 | 委派实现在 `SyncJobLedger.begin()` 里对死信调 `reopen_dead_letter` → **每一轮正常同步都会把永久失败（分享失效等）重新入队并清零尝试次数**，等于无限重试、退避白做 | 删除该分支并加注释说明；改为新端点 `POST /tasks/retry` 显式重开，只在用户点「重试」时复活；对应测试由「begin 自动重开」改为「begin 绝不自动重开」+「显式重开后 begin 能认领」 |
| 纯作业死信无重试动作 | 前端只在有历史标识时给「重试」按钮，作业账本类死信无从处理 | `_finalize()` 增加 `dead_letter && job_id → retry`；前端 `retryTask()` 按有无历史分别调 `/history/retry` 与 `/tasks/retry` |

## 3. 关键行为（发版后的语义）

1. 失败 → `retry_wait` + `next_retry_at = now + min(60×2^(attempt-1), 1800)`；`claim()` 只有到点才抢。
2. 尝试次数用尽 → 直接 `failed`，`last_error` 前缀 `dead_letter: `（不再停在永远抢不到的 `retry_wait`）。
3. 死信只能由用户显式重试复活（`POST /tasks/retry`），`attempt` 与 `next_retry_at` 清零，重新获得 3 次机会。
4. 任务中心 = `sync_jobs` 非终态 ∪ `history_records` 非终态，按 `history_id` 合并成一行，最多 200 条，按 `updated_at` 倒序。
5. 前端两处渲染（PC `v-data-table` / 手机卡片）同步支持筛选、重试、停止。
