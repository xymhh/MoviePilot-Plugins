## 0. 背景

用户在 PC 端打开「追更列表」看不到订阅卡片；随后在手机端详情抽屉又发现 3 处问题。本文按用户原话逐条落账，含已复现证据与拟定改法，等用户点名后按条施工。

**用户口径（2026-11-06）**：「成功绿色失败红色是在徽标上体现，不是让你加文本信息」——状态语义只能靠**颜色**表达，不许再用文字图例说明。

## 1. P0｜PC 端卡片全部塌成 2px（已复现 + 已验证修法）

**现象**：1600×900 下 81 张卡片全部只剩一条 2px 横线，内容被裁掉；手机 390px 正常（138px/张）。

| 视口 | 卡片数 | 单卡高度 | `.card-inner` 高度 |
| --- | --- | --- | --- |
| 1600×900 | 81 | **2px** | 32px（= 上下 padding，内容 0） |
| 390×844 | 81 | 138px | 136px |

**根因**：`frontend/cloudsubscribex/src/components/dashboard/MediaHub.vue` 样式块 `.card-inner { height: 100% }`，而 `.media-card` 是**自动行高的 grid 单元**。PC 端 `.hub-pane` 给 `.media-grid` 施加了确定高度，百分比高度在 auto 行里形成「行高 0 → 卡片 0 → 子元素 100% = 0」的自洽塌陷；手机端 grid 高度不受限，百分比退化成 auto 故不复现。1.9.48 改卡片布局后引入。

**已验证修法**（浏览器注入后 2px → 196px，截图 `tmp_task/hub_1600_fixed.png`）：

```css
.media-grid { grid-auto-rows: max-content; align-content: start; }
.media-card { display: flex; }
.media-card .card-inner { height: auto; flex: 1 1 auto; }
```

**验收**：PC 1600/1280/1024 三档卡片 ≥180px、无重叠；手机 390 仍 138px 不回退；同行卡片等高。

## 2. P1｜详情抽屉顶部信息太长、换行成 3 行（用户「图中文本信息太长导致换行」）

**证据**（截图 `media/0663fe383fd3.jpg`）：抽屉头部 7 个标签竖排成 3 行——`电视剧 / 第1季 / 监控中 / 已播 6 集 / 已入库 4 集 / 待补齐 4 集 / 全剧共 8 集`；下面小标题「选集追更全景矩阵」自身也折成两行。

**位置**：`frontend/cloudsubscribex/src/components/dashboard/MediaDrawer.vue:40-56`（7 个 v-chip）+ `:121`（小标题）。

**拟定改法**：
- 7 个标签合并成 **2 个**：`6/8 集 · 已播 6`（缺口/总量）+ 类型/季；
- 小标题缩短为「选集进度」，与图例同一行；
- 目标：抽屉头部 **≤2 行**，390px 宽不换行。

## 3. P1｜状态色没落在徽标上，反而用文案图例说明（用户明确反对）

**现状三处**：

1. 海报角标 `.poster-status-badge`（`MediaHub.vue:487`）**全是黑底** `rgba(0,0,0,.65)` + 白字，只有文字色和 1px 边框随状态变 → 远看完全一样。
2. 记录徽标 `record-status-chip`（`MediaDrawer.vue:188-193`）用 `variant="tonal"`，深色主题下底色几乎无差 → 截图里「成功」看着都是灰的。
3. `MediaDrawer.vue:176` 直接放了一句 **「成功绿色 · 失败红色」** 文字图例 —— 正是用户说的「不是让你加文本信息」。

**拟定改法**：
- 徽标改**实心底色**：成功 = 绿底白字，失败 = 红底白字，跳过/转存中 = 琥珀/青；只留极短标签（成功 / 失败 / 转存中 42%）；
- **删掉** `:176` 的文字图例；
- 角标与记录徽标共用同一套语义色（复用 `recordStatusColor()` / `cardStatusTone()`），不再新增任何说明文字。

**验收**：390px 宽截图里，成功/失败徽标在**不看文字**时也能一眼区分；页面内不存在「成功绿色」这类说明句。

## 4. P0｜1-2 集实际存在，却显示「待补齐」（已坐实，附实测数据）

**用户原话**：「最重要的是这部剧 1-2 集是存在的，却显示不存（在）」。截图对象 = 律界战争 (2026) 第 1 季。

**三轮实测（本轮亲自跑的线上数据）**：

| 数据源 | 结果 |
| --- | --- |
| 插件 `page_data.subscribes_progress`（subscribe_id **35**） | `library_episodes = [3,4,5,6]`，`missing = [1,2,7,8]`，`total = 8` |
| 插件历史成功记录 | 仅 `E3 / E4 / E5 / E6` 四条成功（截图「追更记录 (4)」一致） |
| **Emby 媒体库**（`/media/content?server=emby&keyword=律界战争`） | **ep 1 / 2 / 3 / 4 / 5 / 6 全部存在**（S1 共 6 集） |
| MoviePilot 订阅（id 35） | `note = [3,4,5,6]`，`start_episode = 3`，`lack_episode = 2` |

**根因**：`core/api/page.py:459 _build_subscribes_progress()` 的「已入库」只取 **MP 订阅 `note` ∪ 插件转存历史成功集号**（`page.py:637` 那一段 union）。这部剧的 E1/E2 是**在订阅之外进的库**（订阅 `start_episode=3`，即订阅从第 3 集才开始追），两处都不含 1、2，于是永远显示「待补」——**界面从不读媒体库里真实存在的文件**。

**拟定改法（二选一，待定）**：
- **A（推荐）实测优先**：构建进度时一次性拉取媒体库（Emby）本季剧集列表，按 `tmdb_id + season` 归并，与 `note ∪ 历史` 求并集；60 秒内存缓存，失败时回落现状（不报错、不变空）。可挂在既有 `media_library` 服务上，不新增外部依赖。
- **B 轻量**：扫本地媒体目录 `/strm/115网盘/.../Season N` 的文件名解析 `SxxExx`，不依赖 Emby 在线。

**验收**：律界战争该季卡片显示 `已播 6 · 已入库 6 · 缺 E7-E8`；补单测覆盖「MP note 缺 E1/E2 但媒体库有」的场景；媒体库不可用时不得影响列表加载。

## 5. 追加需求（2026-11-06，用户：「做，但再加上追更列表的筛选功能，目前无法快速找到正在转存的任务」）

**问题**：追更列表只有「全部 / 有缺集待补 / 已全部入库」三个筛选项，正在跑任务的那几张卡混在 81 张里，得靠翻。

**改法**：新增第 4 个 chip「正在转存 (N)」，判定口径 = 该订阅有活跃任务（`tasks` 里同 subscribe_id / 同片名同季）**或** `transferring_episodes` 非空；计数实时取交集数，点一下只剩正在跑的卡。

**实施位置**：`MediaHub.vue`（chip + `isTransferring` / `transferringCountTotal` / `displayedGroups` 分支）
