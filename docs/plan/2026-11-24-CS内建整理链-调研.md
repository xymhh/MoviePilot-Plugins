# 「在 CS 里实现整理」调研（2026-11-24）

> 需求（用户原话两次）：
> ①「我希望使用 p115strmhelper 插件的整理功能，本地下载后上传到待整理目录，然后再整理到媒体库，并且需要做下载前挡」
> ②「我说的是在 cs 插件中实现 p115strmhelper 插件的整理功能」
> 结论先行：**不装 P115StrmHelper，把「待整理目录 → 媒体库」这条整理链在 CS 内部实现**；
> CS 已有一套等价的整理台（`core/services/organize.py`），本需求是把它接回主链路，不是从零移植。

## 一、P115StrmHelper（线上可读源码 3.0.2）到底做了什么

从 `GET /api/v1/plugin/file/P115StrmHelper/...` 读到的关键事实：

| 能力 | 配置键 / 入口 | 说明 |
| --- | --- | --- |
| 网盘整理 | `pan_transfer_enabled` + `pan_transfer_paths` | 把「网盘整理目录」里的文件整理到媒体库；`pan_transfer_unknown_path` 放识别失败的 |
| 整理接管 | `transfer_module_enhancement` + 「接管网盘整理」 | **要求 MP 存储模块为「115网盘Plus」**，接管 115→115 的 MP 整理任务批量处理 |
| 整理后 STRM | `transfer_monitor_enabled` + `transfer_monitor_paths` | 监听 `EventType.TransferComplete`，对监控目录下的文件生成 STRM |
| 媒体库已存在拦截 | `媒体库已存在时拦截整理` | `ChainEventType.TransferIntercept` 里拦截，避免重复入库 |
| 重命名/覆盖 | `TransferRenameBuild` / `TransferOverwriteCheck` 事件 | MP v3.2.6+ 的整理链钩子，插件在其中改文件名 / 判覆盖 |
| 转存分享到待整理目录 | `/p115_add_share` | 分享 → 待整理目录，之后靠网盘整理搬到媒体库 |

要点：**它自己不做下载，也不做上传**——上传是 MP 整理链（存储模块 115网盘Plus）干的；
它负责的是「整理这一步的 115 特化」：批量 move、重命名、覆盖判定、STRM 生成、拦截重复。

## 二、CS 现有的等价能力（`core/services/organize.py`，整理台）

| 能力 | CS 现状 | 与 P115 的差距 |
| --- | --- | --- |
| 扫描待整理目录并按作品/季分包 | `start_scan` + `utils/organize_plan.py`（`scan_entries` / `build_packages`） | 无 |
| TMDB 识别 | `_recognize_package`（复用插件既有识别链） | 无 |
| 重命名（模板） | `_target_final_name` + `render_template`/`resolve_template` | 无 |
| 批量移动 | `_move_targets_batch` / `_move_target`（115 批量 move，含空目录清理） | 无 |
| STRM | 由 `handlers/sync/strm_ops.py` 统一生成（增量/全量） | 整理后需触发一次增量 |
| 失败重试 / 历史 | 有扫描状态与执行结果，但没接进漏斗账本 | 需要接 |
| 定时执行 | 1.30.0 随 `organize_source_path` 退役（04:00 改成漏斗扫描对账） | **要恢复** |
| 媒体库已存在拦截 | 有（`_build_group_plan` 判目标存在） | 无 |

结论：**能力齐了，缺的是「接线」**——整理台现在只有手动入口（且入口从导航撤了），
主链路仍是「CS 直接上传到媒体库 + 交 MP 整理」。

## 三、三条候选路线

| 路线 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| A 装 P115StrmHelper 接线 | 装 3.0.2、切存储模块 115网盘Plus、CS 只负责下载 | 要改 MP 全局存储模块 | 与 CS 自注册的「115网盘CS版」冲突；P115 patch 了 u115_open/p115disk_upload，互相打架 |
| **B 复用 CS 整理台（推荐）** | CS 上传到待整理目录 → 触发整理台扫该目录 → 移动 + STRM | 恢复定时扫描 + 接线（约 1 天） | 中：改动主链路，需灰度开关 |
| C 新写一条整理链 | 另起一套扫描/移动/STRM | 重复造轮子（已有 1000+ 行整理台） | 高 |

选 **B**：符合「先搜轮子」原则，且不动 MP 全局存储模块。

## 四、待用户确认的两个默认值

1. **待整理目录**：默认取 CS 现有配置 `p115_transfer_path`（线上值 `/Alist/影视/moviepilot/转存`），
   整理目标 `p115_media_path`（`/Alist/影视/moviepilot/媒体库`）。
2. **切换方式**：新增开关 `organize_after_upload`（默认**关**，灰度）——
   开 = 上传到待整理目录 + 由 CS 整理台整理；关 = 维持现状（直接上传媒体库 + 交 MP 整理）。

## 五、参考：为什么不能直接把文件留在 /downloads 让 MP 整理

MP 的整理链需要「下载器任务 + 整理历史」上下文，CS 的跨盘文件没有下载器任务；
这也是 1.12.0 起 CS 自己上传、只借 MP 整理做「移动」的原因。改成「上传到待整理目录
+ 自己整理」后，这条链完全落在 CS 内部，不再依赖 MP 整理的历史与存储模块。
