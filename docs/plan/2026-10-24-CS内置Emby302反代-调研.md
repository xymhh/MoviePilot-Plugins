# CS 内置 Emby 302 反代（替代 MediaWarp）— 调研

> 时间：2026-10-24｜提出者：用户（"我还需要一个功能来代替 MediaWarp，这样以后只需要一个网盘订阅助手插件就行了"）

## 1. 要解决的问题

现状：CS 生成 STRM（内容 = `http://moviepilot-v3:3000/api/v1/plugin/CloudSubscribeX/redirect?pickcode=xxx`），
Emby 播放时由 **Emby 服务端**请求该 URL 拿到 302 → 跟随后把流**中转**给客户端。
客户端因此吃的是 Emby 的出口带宽，4K 高码率容易卡；且必须额外装 MediaWarp 才能让客户端直连 CDN。

目标：CS 自己充当 Emby 前面的那一层，把播放请求 302 到 115 CDN，客户端直连。
之后可删掉 MediaWarp（少一个插件、少一个 Go 二进制、少一份配置）。

**关键结论：GitHub 上没有"直连 115 API"的成熟 Emby 反代**（搜 `115 emby proxy`、`115 pickcode` 均 0 结果）。
所有可用反代（go-emby2openlist / MediaRelay / embyExternalUrl 系）都靠 **OpenList/Alist** 取直链——
因为"多网盘直链提取"是脏活，社区选择外包给 OpenList。CS 例外：`core/api/redirect.py` 已自备 115 直链能力。

**可合法借鉴的代码（MIT）**：
1. `MediaRelay` —— **LRU 直链缓存 + 请求合并**（直接对应"不封控 + 效率最大化"两条硬约束）、路由判定、Emby 内嵌 WebUI 注入方式；
2. `embyExternalUrl`（emby2Alist/nginx/conf.d/emby.js 33K、util.js 25K）—— Emby 请求分类、PlaybackInfo/stream/Range/HEAD 处理、转码分支判定。

**只能看思路、不能抄代码（许可不允许）**：MediaWarp（AGPL）、go-emby2openlist（GPL）、CayFlow / 115-station / SmartStrm / emby-direct-web（无 LICENSE = 版权保留）。

**踩坑清单（来自 CayFlow CHANGELOG，仅作情报）**：
- "修复某些情况下 302 播放会走服务器流量" → 转码/客户端分支没切干净，会退回中转；
- "cookie 每次变化都会重启服务，避免提取直链失败" → 115 cookie 轮换要重建直链提取器。

## 3. 结论：**自研（方案 A），只做「反代 + 302」这一段**

> 二轮搜索后结论不变，但实现方式由"净室自研"改为"**按 MIT 参考实现移植 + 补 CS 独有的一段（pickcode 反查）**"。
> 不再重新发明路由判定/缓存/请求合并：直接对照 `MediaRelay`（MIT）与 `embyExternalUrl`（MIT）的逻辑翻译成 Python。

选③自研的理由（别人没有的那一段）：
1. **只有 CS 同时掌握「订阅 → 转存 → 结构化目录 → STRM → pickcode → 直链」全链路**，反代时不需要再靠路径映射猜，
   直接用 Emby Item 的 Path 反查 strm 里的 pickcode，命中率高、无路径配置负担；
2. 用户明确要求「一个插件」，引入 Go 二进制或第二个服务都违背目标；
3. 需要的能力范围很窄：**只做播放请求的 302**，不做前端美化、不做客户端过滤、不做弹幕/共同观影——
   MediaWarp 那 11MB 二进制里 2/3 的功能 CS 不需要。

不做的事（明确排除）：
- 前端 JS 注入/美化（MediaWarp 的 Crx/Fanart/ActorPlus 等）
- 客户端黑白名单（后续可选）
- 转码代理（转码请求一律透传给 Emby，CS 只在「可以直接播」时 302）
