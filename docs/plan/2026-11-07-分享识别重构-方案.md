# 分享识别重构方案（精简版）

> 日期：2026-11-07（v2 精简，替代同目录 v1）
> 状态：**已定稿**（用户 2026-11-07 确认）→ M1 只读核心已实现，证据见 `../test/2026-11-07-分享识别-M1.md`
> 原则：能少一条规则就少一条。宁可漏认，不可错认；宁可停下来问，不可猜着转。

---

## 1. 三步管线

```
① 枚举：递归拿到分享里每个文件的完整路径
② 分组定身份：一级目录 = 版本组；消息给片名；TMDB 定作品
③ 算覆盖出计划：每组算集号并集 → 选一组 → 转 / 不转
```

没有第四步。没有置信度评分、没有多轮仲裁。

---

## 2. 六条硬规则

| # | 规则 | 为什么 |
|---|---|---|
| R1 | **递归到底**，拿到全部分支的文件清单 | 不看到全部就没法过滤 |
| R2 | **只有媒体后缀算集**：`mkv mp4 ts m2ts mts avi mov wmv flv rmvb rm m4v mpg mpeg webm`；`iso` 由开关 `treat_iso_as_media`（默认关） | 其它都是噪音，猜了就错 |
| R3 | **字幕/外挂音轨不参与识别，但同目录的一起转**：`srt ass ssa sub idx sup vtt mka ac3 dts flac` | 只转视频会把片变哑巴 |
| R4 | **消息只给片名**（可带年份）；`更N集/全N集/完结` 只写日志，不参与任何计算 | 消息是广告，文件是事实 |
| R5 | **集覆盖 = 组内媒体文件集号的并集**；TMDB 集数只用来算「缺几集」 | 唯一权威是文件 |
| R6 | **状态只有三种**：`ready`（转）/ `review`（等人看）/ `skip`（不转）。后两种绝不产生转存动作 | 不确定就停 |

---

## 3. 分组与选版本（质量优先，缺集补齐）

- **分组**：一级子目录 = 一个版本组；根目录散落的媒体文件合并成「散文件组」。
- **质量指标**：组内单个文件的**体积中位数**（比目录名标签可靠——标签会写错，体积不会）。
- **主版本**：体积中位数最大的组；并列时按标签优先级 `DV > HDR > SDR > 无标签` 决出。
- **补集**：主版本缺的集，按组体积中位数从大到小依次从其他组补，标 `mixed_quality`。
- **补满即停**：覆盖完整就不继续找，不为了"更高质量"洗版。

> 用样本「嫁金钗」验证：DV 组 6.48GB/集（27 集）胜出为主版本，缺 28–30 由根目录散文件组（`28/29/30 HDR.mkv`，1.25GB/集）补齐 → 结果 30 集完整，标记 `mixed_quality`。
> 反例检查：`4K/` 虽然 30 集齐全，但画质只有 1.23GB/集，**不做主版本**。（M1 实测修正：补集来源是散文件组，不是 `4K/`；结论不变）

## 4. 数据结构（三个就够）

```python
Share = { share_id, files: list[File] }

File = {
  path, name, ext, size,
  group,            # 版本组 id（一级目录）
  season,           # 从目录或文件名取，取不到 None
  ep,               # 集号，取不到 None
  kind,             # media | sidecar | other
}

Plan = {
  work_id,          # TMDB id，None 则 review
  season,
  group,            # 选中的版本组
  selected: [path],
  skipped:  [(path, reason)],
  missing:  [ep],            # 补不齐的集
  mixed_quality,             # 是否用了低质量版本补集
  status,           # ready | review | skip
  reason,           # 状态原因，必填
}
```

---

## 5. 异常只有 4 个

| 状态 | reason | 含义 |
|---|---|---|
| `skip` | `NO_MEDIA` | 一个媒体文件都没有（含只有压缩包） |
| `review` | `NO_EPISODES` | 有媒体但一个集号都提不出 |
| `review` | `NO_IDENTITY` | 定不了是哪部作品 |
| `review` | `SCAN_FAILED` | 枚举失败/超时/被限流 |

其它情况一律照常转，只记日志，不阻断。

---

## 6. 验收（3 条不变量）

1. 把消息里的 `更15集` 改成 `更99集`，`Plan` 完全不变。
2. 任何 `kind != media` 的文件不得出现在集覆盖里；纯字幕分享判 `NO_MEDIA`。
3. `work_id is None` 时 `status` 不得为 `ready`。
4. 主版本必须是体积中位数最大的组；补集只能来自更小的组。

**回归样本**：美人余（全 zip → `skip: NO_MEDIA`）、嫁金钗（主版本 DV 27 集 + 从 `4K/` 补 28–30 → 30 集完整、`mixed_quality`）、38 条频道消息（片名清洗 + 进度只记日志）。

## 7. 这一版砍掉了什么（相对 v1）

| 砍掉 | 原因 |
|---|---|
| 七层判定 → 三步 | 层多不等于准，每层都是一次出错机会 |
| 缺集三分类（tail / internal / unknown） | 只报「缺哪几集」就够，分类是人脑补的复杂度 |
| 版本三档策略（strict/balanced/loose） | 一种策略（质量优先、缺集补齐）已够，开关留给以后 |
| 异常码 11 个 → 4 个 | 其余情况记日志即可，阻断反而制造麻烦 |
| 置信度体系、sources/conflicts 字段 | 没有校准数据支撑，纯装饰 |
| 扫描预算 / 缓存 / 断点续扫 | 先跑通，遇到限流再补；`SCAN_FAILED` 兜住 |
| 附属文件精确定位（主干同名、跨组判定） | 同目录字幕全部带上即可，宁多不漏 |
| TMDB 别名、罗马数字归一等待办 | 等真实误判出现再补，不预先造规则 |
