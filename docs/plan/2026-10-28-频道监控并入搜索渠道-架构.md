## 1. 目标 / 非目标

**目标**

1. 频道监控在**产品层**与其它搜索渠道并列：同一份渠道列表、同一套开关、同一份失败告警与账本。
2. 发现结果走**同一条判定链**：先比「有没有」再比「好不好」，产出唯一的 `task_types`（追更 / 洗版）。
3. 历史记录作为判定基线的**事实来源**；来源字段拆成「怎么发现」与「怎么落地」两件事。

**非目标**

1. 不把常驻长轮询塞进无状态的 `search(keyword)` 接口。
2. 不改 `status` 语义（`处理中/成功/失败/待确认` 继续只表达生命周期）。
3. 不动 `messages` 模式的纯通知能力（保留为渠道能力位）。

## 3. 架构决定

### 3.1 形式并列，运行分离

```
search/<渠道>/definition.py     ← query 渠道：实现 search(keyword)
search/tgchannels/definition.py ← push 渠道：只声明能力与表单，不实现 search()
core/tg_monitor.py              ← push 侧车（常驻）：拉取/游标/flood wait/队列
                      │
                      └─ submit_candidate(Candidate) ──► DiscoveryService
                                                          │ 匹配订阅 → 追更/洗版判定 → 传输/落库
```

- `SearchSourceDefinition` 增加能力位：`capabilities: FrozenSet[str]`，取值 `query`/`push`/`notify`。UI 用能力位决定渲染成「搜索卡片」还是「监控卡片」，两者在同一个渠道列表里。
- push 渠道**不实现** `search()`；`SearchSourceRegistry` 组装搜索时按 `query` 能力过滤，避免监控渠道被塞进搜索预算（`search/budget.py`）。
- 频道监控的常驻能力留在 `tg_monitor.py`：flood wait、游标、验证码、队列优先级都是秒级状态机，放进无状态接口会破坏搜索超时语义。

### 3.2 唯一候选入口

```python
submit_candidate(source_id: str, candidate: Candidate, *, via: str) -> SubmitResult
```

- `Candidate`：`url/links/title/message_id/channel/size_hint/quality_hint/discovered_at`
- `via`：`tg:@频道|消息ID`、`pansou`、`mikan` 等，直接落进历史的 `discovered_via`
- 入口内部只做三件事：媒体匹配 → 判定（3.3）→ 交给传输。**不做**转存本身，避免和 `sync_lock` 打架（今天 1.7.103 补写抢锁已踩过）
- Phase 1 里 `submit_candidate` 内部仍调现在的 `api_vue_start_manual_sync`，行为等价，只多写 `discovered_via`。

### 3.3 追更 / 洗版 判定模型

事实层（唯一基线，顺序即优先级）：

1. 季目录实测文件（`_scan_episode_versions_in_dir`）
2. 插件历史成功记录（含 `landed_size`、`sha1`）
3. 媒体服务器已有条目（Emby/Jellyfin）

判定：

| 条件 | 结果 |
| --- | --- |
| 该集在事实层**不存在** | `task_types=["follow"]`，直接转存（缺集优先） |
| 存在，`compare_quality` 判 `upgrade`（评分更高，或同分但体积增益 ≥ min_gain） | `task_types=["upgrade"]`，替换 |
| 存在，`compare_quality` 判 `no_gain` | 不转存，写 `no_gain` 一行到资源账本（**禁止静默**） |
| 存在，但基线只有「媒体服务器条目」（无 size） | `task_types=["upgrade"]` 但标记 `baseline_weak=true`，日志提示基线缺体积 |

`task_types` 是**类型字段**；`status` 保持生命周期语义。二者都不承载「来源」。

### 3.4 来源字段正交化

| 字段 | 含义 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| `discovered_via` | 发现渠道：`tg:@chan/msgid`、`pansou`、`mikan` | 发现侧（`submit_candidate` 的 `via`） | 统计、规则回查、通知里的「来源渠道」 |
| `landed_via` | 落地方式：`provider` + `transfer_mode`（同盘拷贝/秒传命中/跨盘/中继）+ `landed_size`（写入后核验）+ `sha1` + `verified_at` | 传输侧终态 | 判重、洗版比较、通知体积（1.7.99 修过）、深链删除 |

老字段 `source_drive_key/name` 保留兼容，语义收敛为 `landed_via.provider`；历史页「来源」列改读 `landed_via`，另加一列「发现渠道」读 `discovered_via`。

## 4. 迁移（3 阶段，每阶段可独立回滚）

**Phase 1 · 等价搬运（不改行为）**

- 新增 `search/tgchannels/definition.py`（`capabilities={"push","notify"}`）+ 配置迁移：`tg_channels/tg_channel_rules` → 渠道卡片字段
- `_auto_transfer_tg_item` 改调 `submit_candidate(via=f"tg:{channel}/{msg_id}")`，内部仍走手动转存
- 历史补写 `discovered_via`；账本记录「发现→落地」对照
- 回滚：开关 `discovery_unified=false` 直接走旧函数

**Phase 2 · 判定统一（灰度）**

- push 候选改走订阅匹配 + `_episode_dedup_decision`（与搜索路同源）
- 灰度：先开一个频道，观察 24h 的 `follow/upgrade/no_gain` 计数与误判
- `messages` 能力频道保持纯通知，不进判定链

**Phase 3 · UI 并列**

- 渠道列表统一渲染；监控渠道显示「推送」徽标 + 消息游标/最近命中时间
- 搜索页的「渠道开关」同时控制监控开关（同一个 `enabled`）

## 5. 失败与回滚

| 场景 | 处理 |
| --- | --- |
| TG flood wait | 尊重现有退避（`:198`），队列保留，不重试风暴 |
| 判定链异常 | 候选降级为 Phase 1 手动转存，打 WARNING（不允许 `except: pass`） |
| 历史缺失 | 走 1.7.102 的 `_backfill_history_from_pending` 语义；不把「无历史」当「无文件」 |
| 并发 | 候选提交只写账本/队列，历史写回统一在 `_offline_pending_lock` 内；不抢 `sync_lock` |

## 6. 风险

1. **抽象错配**：push 源塞进 `search()` 会让搜索超时/预算失真——用能力位隔离，接受这点设计成本。
2. **TG 标题不可信**：实测过「标 4K 实际 1.46GB」。判定禁止吃 `quality_hint`，只吃 `landed_size`/`sha1`。
3. **老记录 `discovered_via` 缺失**：只能按 `source_drive_name`+`kind` 粗略回填，历史统计会有断层，需在 UI 标注「老记录」。
4. **配置迁移丢规则**：`tg_channel_rules` 有旧版回退逻辑（`:405` 的 warning），迁移必须一次性写全 per-channel 规则，否则会静默回退全局关键词。
5. **延迟**：统一后 TG 命中不再「立刻转存」，要等匹配与评分。高优先级队列 + 可配置「追更直通」。

## 11. P2b 落地后发现：判定链本来就共享（2026-10-28）

**重要更正**：原架构假设「频道推送与搜索各自判定、需要合并」。读码实测：

`_auto_transfer_tg_item` → `api_vue_start_manual_sync(resource_links=…)`
→ `_do_api_vue_start_manual_sync`（`core/api/sync.py:391`）把链接解析成 `resources`
→ `sync_kwargs = {manual_resources, manual_target, manual_upgrade}`（`core/api/sync.py:832`）
→ `sync_subscribes` → `_do_sync` → `process_tv_subscribe(manual_resources=…)`
（`core/services/runtime.py:652`），而 `_episode_dedup_decision` 的调用点就在
`process_tv_subscribe` 内部（`handlers/sync/television.py:728`）。

即：**推送候选早已走同一套季集判重 / 缺集优先 / 洗版阈值判定**，两条链路的差异只在
「发现」环节（谁找到这个分享链接），不在「判定」环节。因此 P2 不需要重写判定，
只需把「来源」这一维补齐并观测。

落地内容（随 1.7.105 发布）：
- `submit_candidate` 把 `discovered_via` 写进手动同步 payload。
- `_do_api_vue_start_manual_sync` → `sync_kwargs["discovered_via"]`（`core/api/sync.py`）。
- `_do_sync` 把 `discovered_via` 落到订阅对象私有属性（`core/services/sync.py`，仿 `_manual_upgrade`）。
- `_build_transfer_history_item` 兜底读 `subscribe._discovered_via`，非空才写键（老记录不受影响）。
- 测试：`tests/test_history_discovered_via.py`（4 例）+ `tests/test_discovery_submit.py`（7 例）。
- 未做：`landed_via`（落地网盘/路径）与 UI 展示；灰度统计（`follow/upgrade/no_gain` 计数）仍是 P2c。
