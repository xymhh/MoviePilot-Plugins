# 洗版链路浪费：负缓存 + 体积兜底哈希键 + 入队去重

> 状态：已完成 2026-10-28 → ../summary/2026-10-28-洗版浪费优化-落地.md

## 背景（线上实测）

10-28 清洗版链路账本：92 次下载 245.7GiB，实际落库 56.3GiB（22.9%）；
33 次「秒传未命中 → abort」，其中同一文件被重复整份下载，白下约 20.6GiB
（尚公主 E09–E12 各 4.8–5.3GB、玉簟秋 S01E26 2.85GB 被下两次）。

三个漏洞：

1. **1.7.99 的 SHA1 缓存键含文件名**（`provider|size|name`）。洗版/重试从分享列表拿到的
   文件名与首次记录的不同（`...mkv` vs 目标名），键不匹配 → 缓存形同不存在 → 再下一次 5GB。
2. **没有负缓存**：115 已确认「没有这个哈希」这件事没记住，19 小时内同一文件重试两次。
3. **入队不去重**：同订阅同集的不同分享同时入队，19 条积压里 4 条是同一集。

## 方案

### 1. 哈希缓存加「体积兜底键」

`core/transfer.py::_hash_cache_keys()` 返回两个键：精确键 `provider|size|name`
+ 兜底键 `provider|size`。读取先精确后兜底，写入两个都写。
体积是 4.8GB 级视频的强指纹，同名不同文件几乎不可能同体积；
换来的是文件名变体、改名、目标名/源名混用都能命中。

### 2. 秒传未命中负缓存（新表 `source_miss_cache`）

- 模型：`core/database/models.py::SourceMissCache`，主键 `target_key|SHA1`，存 `missed_at`。
- 仓储：`SourceMissCacheRepository`（get/put/purge_expired/prune），随 `create_all` 自动建表，
  老库升级不需要手工迁移。
- 插件侧：`get_cached_rapid_miss` / `put_cached_rapid_miss`，TTL 24h、上限 4000 条。
- 生效点：
  - `transfer.py` 任务开始前，若已知 SHA1 且 24h 内确认过未命中 → 直接
    `RapidMissAborted`，**不下载、不探测**，日志写「跳过：X 的秒传 N 分钟前已确认未命中」；
  - `RapidMissAborted` 落终态时写负缓存，SHA1 来源是探测用的校验和或下载后实算值。
- 状态码不变（failed/aborted/`abort_reason=rapid_miss`），下游历史分类零改动。

### 3. 入队去重

`core/tg_monitor.py::_match_and_enqueue`：

- 复用 `_quality_candidate_key()`（订阅+季+集），新条目写 `matched_dedupe_key` 落台账；
- 本批内同键只留画质分最高的（`_candidate_quality_score`），被替换的条目退回 ignored；
- 跨批次：台账里 `queued/transferring/processing` 的同键条目算占位，新候选直接 ignored；
- 整季包/无集号的条目 `_quality_candidate_key` 返回 None → 不参与去重（避免误杀）。

## 验收

- 新增 11 个用例：负缓存 3（跳过第二次 / 过期可重试 / 体积兜底键命中）、
  负缓存表 5、入队去重 2、台账存取 1。
- 全量：804 tests，与改动前基线（793 tests，1 失败 + 14 环境性收集错误）**同源失败，无新增**。
- `scripts/lint.py --all`：0 error，静默面预算 0/0。

## 不做

- 不改 `upgrade_mode=largest` 的 `quality_min_gain_percent` 门槛（另立需求）。
- 不动中继（`relay_enabled=False`，配置侧未启用）。
