# 1.6.42 点选兜底不再要求类型相容（洛基/征途线上案例）

> 状态：已完成 2026-10-15 → ../summary/2026-10-15-点选兜底类型相容性.md

## 背景（用户报告）

用户 2026-10-15 提问：「查看 MP 日志，为什么搜索没结果时没有添加订阅」。
查 `plugins/cloudsubscribe.log` 后确认：**不是「搜索没结果所以没建订阅」，而是
「点选 → 建订阅」这一步就没走到**，平台搜索的 0 结果是**透传之后**的副作用。

### 线上证据（cloudsubscribe.log，2026-10-15）

案例 1「洛基」（11:58）：

案例 2「征途」（10:42）：`10:41:58 征途 TMDB识别结果：电影 征途 (2020) 611395` +
`10:42:04 点选 电视剧 征途 (2026) 336207` → 同样的「未接上片名登记」。
核对订阅表（`GET /api/v1/subscribe/`，59 条）确认**没有**洛基、也没有征途。

### 根因

`core/pending_titles.py` 的 `consume()` 把类型相容性检查放在**四级匹配之前**：

- 登记记录被后台识别补成 `mtype=movie` / `tmdbid=636901`（`core/hook/message.py` 的 enrich）；
- 用户点选的是 `mtype=tv` / `tmdbid=84958`；
- `_compatible()` 两侧类型都已知且不同 → False → `continue`；
- 于是 tmdbid 命中、同名命中、模糊命中、点选兜底（1.6.33 加的 `allow_sole`）**全部被挡**，
  `consume()` 返回 None，订阅不建、平台搜索不被拦。

## 目标

点选路径（用户明确点了一次候选）必须能接上：类型不相容不能成为**否决条件**。
非点选调用方（订阅搜索、扫描）行为**完全不变**。

## 改动（最小面）

`core/pending_titles.py` 的 `consume()`：

1. 循环内先算 `compatible`，`allow_sole=True` 时分别登记：
   - 类型相容 → `sole_hit` / `sole_candidates`（优先）；
   - 类型不相容 → `sole_fallback_hit` / `sole_fallback_candidates`（最后一级兜底）。
2. 决策顺序不变：`tmdbid` → `title` → `fuzzy` → `sole`（相容优先，其次不相容兜底）。
3. 非点选调用方（`allow_sole=False`）走原来的 `if not compatible: continue`，行为逐字节不变。
4. `match_candidates` 按实际选中的那一级记录条数上报，便于日志核对。

订阅本身仍按**点选项的身份**创建（`_handle_selected_title` → `_resolve_selected_media`），
登记记录只决定回执发给哪个渠道 —— 这是 1.6.33 就定下的口径，本次只把「类型相容」从
否决条件降级为优先级。

## 验收标准

- 单测：复刻洛基案例（登记 enrich 成 movie/tmdbid=636901，点选 tv/tmdbid=84958）
  → `match="sole"` 且订阅按 84958 建；该用例在旧代码上**必失败**（git stash 反证）。
- 单测：类型不相容的记录在**非点选**路径上仍不消费（记录保留）。
- 单测：多条记录时点选兜底**优先**取类型相容的那条。
- 全量 `pytest tests/` 无新增失败；`scripts/lint.py --all` 0 error。
- 真机：升级后发「洛基」→ 点选电视剧 → 收到「已按你在平台候选中选定的《洛基》创建订阅」。

## 禁止事项

- 不放宽 `fuzzy`（近名）与 `title`（同名）在非点选路径上的类型要求；
- 不改平台搜索拦截、订阅创建、网盘搜索排队等既有链路；
- 不动版本号以外的其它配置项与前端文案。
