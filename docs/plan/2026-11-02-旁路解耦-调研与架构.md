# 2026-11-02 旁路解耦（第三期）调研与架构

> 状态：进行中 2026-11-02
> 上位路线（会话内确认的五阶段）：② Doctor → ① 配置向导 → ③ 旁路解耦 → ④ 巨石拆分 → ⑤ 历史归档
> 进度：②① 已发布（v1.9.18 / v1.9.19），本篇为 ③。

## 1. 问题：旁路为什么能拖垮主干

主链路只有三段：**搜索 → 转存 → 落库**。其余都是旁路：

| 旁路 | 代码位置 | 触发方式 |
| --- | --- | --- |
| 签到 | `core/services/checkin.py:1052` `run_scheduled_checkins` | 独立 cron service |
| STRM 生成 | `handlers/sync/service.py:1543` `rebuild_strm_files` → `rebuild_strm_tree` | 定时 / 手动 |
| 媒体库刷新（Emby/Plex/Jellyfin） | `handlers/sync/service.py:1369` `refresh_media_servers` → `_emby_library_refresh` | 同步收尾 / 手动 |
| 消息通知 | `handlers/sync/service.py:791` `finish_notification_batch` | 同步收尾 |
| aria2 加速下载 | `core/transfer.py:613` `download_file` | 跨盘转存内部 |

现状的三处结构性缺陷：

1. **单点异常逃逸**：旁路调用点各自零散 `try/except`，覆盖不一致；漏一处就让整轮同步中断，用户看到「任务跑一半失败」。
2. **无失败记忆**：同一个坏点（Emby 地址挂了、webhook 401、STRM 目录不可写）每轮都重试，每轮都耗时，`sync_lock` 被长时间占住 → 手动「立即搜索」返回「已有订阅任务正在运行」。
3. **不可见**：旁路失败只落一条 warning 日志，页面上看不出「是谁在拖」，只能翻容器日志。

历史上 `_ModuleLock` 死锁、卡更新，都是旁路（更新/导入）与主干抢同一把锁造成的同类问题。

## 3. 方案对比（解耦策略）

| 方案 | 做法 | 代价 | 结论 |
| --- | --- | --- | --- |
| A. 拆进程 | 旁路跑独立进程/队列 | 需要新 IPC、状态同步，插件环境无进程管理权 | 否 |
| B. 全异步线程池 | 旁路全部丢后台线程 | 与 MP 调度线程池抢线程，状态一致性难保证，排障更难 | 否 |
| C. 能力级熔断 + 统一包裹 | 每个旁路能力有独立失败计数与冷却，超阈值跳过 | 改动集中、可单测、可回滚 | **选 C** |
| D. 什么都不改，只加日志 | — | 不能阻止「每轮重复踩坑」 | 否 |

选 C 的理由：插件运行在 MP 单进程内，能真正控制的只有「调用边界」。在边界上做三件事就够了：**隔离异常、记住失败、暴露状态**。时间预算/延迟队列（真正的异步化）留到后续，因为会动 `sync_lock` 语义，风险远高于收益。

## 4. 架构

### 4.1 新增 `core/bypass_guard.py`

进程级单例 `bypass_guard`，按能力 key 维护：

```
failures       连续失败次数
trips          进入冷却的次数（用于指数退避）
cooldown_until 冷却截止时间戳
last_error     最近一次错误文本
last_error_at  最近一次错误时间
last_ok_at     最近一次成功时间
```

接口：

| 方法 | 语义 |
| --- | --- |
| `allow(key)` | 是否放行；冷却中返回 False 并只记一次 debug |
| `call(key, fn, *args, fallback=None, **kwargs)` | 统一包裹：冷却中直接返回 fallback；异常记失败并返回 fallback；成功复位 |
| `note(key, error)` | 只记一次失败（调用方自己做了降级，如 aria2 回落内置下载器） |
| `snapshot()` | 供 Doctor / 调试读取 |
| `reset(key=None)` | 清空状态（测试与手动恢复） |

常量：`THRESHOLD=3`（连续失败 3 次熔断）、`BASE_COOLDOWN=600s`、`MAX_COOLDOWN=3600s`（每次重新熔断翻倍）。
`InterruptedError / KeyboardInterrupt / SystemExit` **不吞**，直接透传——用户点停止必须立刻停。

### 4.2 接入点（旁路边界，5 处）

| key | 接入位置 | 降级返回 |
| --- | --- | --- |
| `notify` | `SyncHandler.finish_notification_batch` | `False` |
| `media_server` | `SyncHandler.refresh_media_servers` | `{}` |
| `strm` | `SyncHandler.rebuild_strm_files` | 全 0 统计字典 |
| `checkin` | `CheckinService.run_scheduled_checkins` | `_skipped_result("签到能力冷却中")` |
| `aria2` | `core/transfer.py` 回落分支 `note("aria2", error)` | 已内置回落内置下载器 |

主链路（搜索 / 转存 / 落库 / 历史写入）**一行不改**。

### 4.3 可见性

Doctor 增加第 9 项「旁路能力」：
- 全部正常 → 绿灯，显示「5 项旁路正常」；
- 有冷却中 → 黄灯，列出 `能力名(剩余 X 分钟)` + 最近错误；
- 全部冷却 → 红灯。

前端 `DoctorDialog.vue` 按 `items` 泛型渲染，无需改前端。

### 4.4 失败与回滚

- 熔断只影响旁路，主链路行为不变 → 回滚 = 去掉 `guard.call` 包裹，保留文件无害。
- 状态在内存，进程重启清零（冷却不跨重启）。理由：重启后环境可能已修好，宁可再试一次，也不要被旧状态卡住。

## 5. 验收标准

1. 单测：3 次连续失败后 `allow()` 为 False；冷却到期自动恢复；成功一次即复位；异常不外抛；`InterruptedError` 透传。
2. 接入点单测：旁路抛异常时 `refresh_media_servers` 返回 `{}`、`rebuild_strm_files` 返回全 0、`finish_notification_batch` 返回 False，且主流程调用方无异常。
3. Doctor 返回 9 项，`bypass` 项在注入故障后变黄。
4. 真机：线上插件更新后打开体检，`bypass` 项绿灯；日志无新增异常。
