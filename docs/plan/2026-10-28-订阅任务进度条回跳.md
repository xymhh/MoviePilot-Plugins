# 订阅任务进度条回跳（蹦迪）：成因与修法

> 状态：已实现并提交，待发 1.7.99（2026-10-28）

## 现象

用户报：更新到 1.7.98 后，订阅任务里的跨盘转存进度条反复蹦——多次冲到接近 100% 又掉下来。

## 成因（三处叠加，全部属实）

一个文件一个 task（`create()` 里 `id=f"cross:{task_id}"`），夸克→115 走的是
「下载到本地缓存 → 校验 → 秒传探测 → 上传」这条 cache 路线（115 没有
`upload_progressive`，只有 123 有）。进度条的数字来源在前后端都不统一：

1. **前端拿两种尺子量同一根进度条**
   `RuntimeCard.vue: taskProgress()` 只要 `stage_total > 0` 就用
   `stage_transferred / stage_total`，这是**当前阶段字节比**；
   而 `progress` 字段是**分阶段百分比**（下载 0–49 / 校验 50 / 秒传 52 / 上传 52–99）。
   阶段字节比每换一个阶段就从 0 重新爬，于是同一个文件出现两次 0→100 扫动：
   下载扫一次，上传再扫一次。4 集（E09–E12）= 8 次扫动 ⇒ 「蹦迪」。
2. **上传阶段基准比秒传阶段低 2 个点**
   `core/transfer.py` 里 `rapid_upload` 写 `progress=52`，紧接着上传回调算
   `percent = 50 + min(49, raw//2)`，第一条回调从 50 开始 ⇒ 52 → 50 回跳。
3. **父任务聚合把「已成功但仍停在 49%」的子任务按 49 计入**
   `core/services/runtime.py: _serialize_runtime_tasks()` 对父任务按 `total` 加权平均，
   子任务完成后 progress 停在 49/99，下一个文件从 0 起 ⇒ 加权平均断崖。

## 修法

| 位置 | 改动 |
| --- | --- |
| `frontend/.../RuntimeCard.vue` | 跨盘转存行优先用后端 `progress` 百分比；只有拿不到百分比时才退回阶段字节比 |
| `core/transfer.py: _update()` | `progress` 单调钳制（只增不减），并加注释说明「要归零请新建 task_id」 |
| `core/transfer.py` 上传回调 | 有本地下载时基准 50 → 52，与秒传阶段对齐 |
| `core/services/runtime.py` | 子任务 `status == "success"` 在加权平均里按 100 计 |

- `tests/test_sync_transfer_progress_aggregate.py`：成功子任务按 100 计（55% 而非 29%）、单子任务保留自身百分比
