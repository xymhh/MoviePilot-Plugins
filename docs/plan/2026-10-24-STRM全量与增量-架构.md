# STRM 全量/增量 + Emby 302（CS 内置）— 架构 v2：复用 P115StrmHelper，不重写

> 状态：设计冻结 2026-10-24 v2（推翻 v1 的自研 302/索引方案）
> 原则：**成熟轮子已在同进程里跑着，CS 只做编排与兜底，不重写 STRM 引擎、不重写 302。**
> 调研见 [2026-10-24-STRM全量与增量-调研.md](./2026-10-24-STRM全量与增量-调研.md)

## 0. 为什么改方案（v1 被推翻的原因）

v1 打算自研 `strm_index` 表 + 增量 diff + 302 端点，实测后发现全是重复劳动：

| 能力 | 现成实现（已在本机 MP 进程内） | 实测结论 |
| --- | --- | --- |
| 302 直链 | `GET /api/v1/plugin/P115StrmHelper/redirect_url?pickcode=`，`allow_anonymous: true` | ✅ 实测 `pickcode=akoocdeuj01e3hhcu` → `302` → `https://cdnfhnfile.115cdn.net/...小城良方 - S01E07 - 第7集.mp4`，无需认证 |
| 单文件 STRM | `POST /api_strm_sync_creata`，payload 含 `pick_code`/`local_path`/`media_server_refresh` | ✅ 代码已确认，字段见 `schemas/strm_api.py::StrmApiData` |
| 按目录 STRM | `POST /api_strm_sync_create_by_path`，`{"data":[{"local_path","pan_media_path"}],"media_server_refresh":true}` | ✅ 代码已确认 |
| 全量 | `POST /full_sync` + `servicer.full_sync_strm_files`（线程池 + Rust 扩展 `full_strm_sync`） | ✅ 存在 |
| 增量 | `servicer.increment_sync_strm_files` + `monitor_life`（115 事件） | ✅ 存在（当前未生效，见 §6） |
| 取链鉴权 | `get_status` 等写接口返回 `401 Not authenticated` | ⚠️ HTTP 调用需 token ⇒ 走**进程内直调**绕开 |

结论：CS 侧代码量从 4.5 天降到 **~1 天**，且 302 与本机已在用的播放链路完全一致（不会出现「新 strm 老播放器不认」）。

## 1. 职责边界（v2）

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| P115StrmHelper | STRM 内容生成、全量/增量扫描、302 跳转、Emby 刷新、mediainfo | 不知道 CS 的订阅与转存结果 |
| **CS `integrations/p115strmhelper.py`（新增，唯一新代码）** | 探测插件可用性、把 CS 的转存结果翻译成 P115StrmHelper 的调用、失败重试与降级 | 不写 `.strm` 文件、不解析 pickcode、不做 302 |
| CS `utils/strm_scan.py`（已有，**降级兜底，默认不跑**） | P115StrmHelper 不可用时按 CID 全量补缺 | 不再是主路径 |
| CS `utils/strm.py`（已有） | 保留：模板渲染能力，供兜底路径与自定义 base_url 使用 | 模板默认值改为指向 redirect_url |

## 2. 唯一新增代码：适配器

```python
# plugins.v2/cloudsubscribex/integrations/p115strmhelper.py
class P115StrmBridge:
    """进程内桥接 P115StrmHelper；不可用时返回 unavailable，不抛异常。"""

    def available(self) -> bool: ...
    def create_strm(self, *, pick_code: str, name: str, local_path: str,
                    media_server_refresh: bool = True) -> dict: ...
    def create_strm_by_path(self, *, local_path: str, pan_media_path: str,
                            media_server_refresh: bool = True) -> dict: ...
    def full_sync(self) -> dict: ...
```

实现路径（按优先级，代码里 `try` 串联）：
1. **进程内直调**：从 MP 的插件注册表取已加载实例 → `plugin.api.api_strm_sync_creata(payload)`，无认证、无 HTTP 开销（首选）
2. HTTP 兜底：`POST http://127.0.0.1:3000/api/v1/plugin/P115StrmHelper/api_strm_sync_creata?token=<mp_api_token>`（新增配置项 `mp_api_token`，仅在此路径需要）
3. 都不可用 → 记 `unavailable`，走 §4 兜底

## 3. 调用时机（CS 侧只加 3 个钩子）

| 时机 | 动作 | 代码位置 |
| --- | --- | --- |
| 转存成功（`sync_jobs` → `ok`） | `create_strm(pick_code=<转存结果 pickcode>, local_path=<本地映射路径>, media_server_refresh=True)` | `handlers/sync/service.py` 现有 `_generate_strm` 调用处**替换实现**，函数签名不变 |
| 洗版/替换成功 | 同上（覆盖写） | 同上 |
| 手动「立即校准」 | `full_sync()`；按钮沿用现有 `/strm/full_scan`，内部改为调 bridge | `core/api/runtime.py:189` |

批量场景（一次转存 8 集）用 `/api_strm_sync_creata` 的 `data` 数组一次提交，不逐集调用。

## 4. 降级策略（P115StrmHelper 缺失 / 报错）

| 情况 | 行为 |
| --- | --- |
| 插件未安装 | bridge 返回 unavailable，日志一次 WARN，随后走 `strm_scan` 全量 + 现有 `strm.py` 模板（`{base_url}/d/{pickcode}` 走外部 9527） |
| 接口报错 / 超时（>10s） | 单次重试 1 次，仍失败则入 CS 的 `strm_pending` 轻量队列（复用 `sync_jobs` 的 retry 机制，不新建表），30 分钟后重试 |
| 302 端点 502 | 不归 CS 管，播放器报错；CS 仅在 `/strm/status` 里展示 bridge 健康度 |

**注意**：不像 v1 那样新建 `strm_index` 表——P115StrmHelper 自带 `p115strmhelper_file.db` 索引，CS 再建一份就是双重真相源。
