# TG 频道转存队列：缺集优先、洗版靠后

> 状态：已完成（代码+单测），待发版验证 → `../test/2026-10-28-TG队列缺集优先.md`

## 需求

用户反馈：频道监控排队的任务很多，希望**缺集转存优先**，洗版排后面。

## 现状（1.7.99）

- `core/tg_monitor.py` 的转存队列是 `queue.Queue`，纯 FIFO。
- 扫描时命中订阅即入队，顺序 = 扫描顺序（频道消息顺序）。
- 「缺集还是洗版」由下游同步链路在转存时才判定，队列本身不区分。
- 结果：洗版任务（体积大、要下 4K 源、耗时）经常挡在补集任务前面。

## 方案（最小改动，不动下游链路）

1. **优先级来源**：订阅是否还缺集。`_tg_subscribe_rows` 增补 `lack` 字段
   （MoviePilot 订阅对象自带 `lack`，缺几集）。
2. **入队时定级**：`_match_and_enqueue` 组一张 `subscribe_id → lack` 表，
   命中后写 `item["queue_priority"]`：`lack > 0` → `0`（补集优先），
   否则 `1`（订阅已齐，只可能是洗版）；同时写 `queue_priority_reason` 便于排障。
3. **队列改优先级队列**：`queue.PriorityQueue` 存 `(priority, seq, item_id)`，
   同优先级按入队序号先进先出。
4. **兼容**：`_queue_entry_id()` 同时接受元组与旧的纯字符串条目（老测试、热更新残留）；
   优先级写进条目，插件重启 `_recover_queued_items()` 时沿用落盘值，
   没有该字段的老条目按 `1`（洗版）排后面。

## 不做

- 不改进「缺集 vs 洗版」的判定逻辑（仍由同步链路决定），只改排队顺序。
- 不做抢占：正在跑的那一批不打断（避免半途中断转存）。

## 验收

- 缺集条目后入队但先出队；同优先级保持入队顺序；
- `lack>0` 的订阅命中 → `queue_priority=0`，`lack=0` → `1`；
- 重启恢复沿用落盘优先级；
- 全量单测与 lint 不退化。
