# TG 频道监控判定链简化 —— 调研

- 日期：2026-10-27
- 状态：进行中（1.7.89）
- 触发：用户反馈「频道监控逻辑太混乱，不应该监控订阅，有合适的就转存，不合适的忽略」；并明确判定：**先命中订阅，优先缺集，其次洗版**。

## 2. 现在的三套机制（混乱来源）

1. **频道级监控模式** `monitor_mode`：`messages`（只收录不转存）/ `subscriptions`（匹配转存）。
2. **频道级订阅白名单** `auto_subscribe_ids`：只影响「没匹配到算不算噪音」，并不真正限定转存目标。
3. **订阅匹配 + 画质择优 + pending/ignored/skipped 池**：
   - 匹配用全部订阅（`allowed_ids=None`），只有唯一高置信才转；
   - 同集多候选按画质分保留最优，其余 `pending` 兜底；
   - 未匹配进 `pending` 或 `ignored`（保 50 条供「新增订阅后回补」）；
   - 旧 `new` 条目每轮限 5 条补转（`MAX_REMATCH_TRANSFERS`）。

结果：一条消息可能落在 5 种状态之一，用户看不出「到底转没转、为什么没转」；
白名单看起来像开关，实际只决定噪音标签；池子里 106/147 条是历史与噪音。

## 3. 结构性缺陷：转存在扫描线程里同步执行

`ChannelMonitor.scan()` → `_run_auto_transfers()` 逐条调用
`_auto_transfer_tg_item()` → `SyncApi.api_vue_start_manual_sync(wait=True)`，
每条都要跑完整手动转存（115 转存 + 整理 + 通知），单条数分钟。

一次扫描 37 条新资源 → 扫描线程被占满几小时：
- 20:35 起的扫描至今未结束（`last_scan_at` 停在 20:24）；
- 期间频道不再扫描，新消息堆积；
- 该轮 37 条全部停在 `new`，`status` 也不更新。

## 4. 附带故障

1. `升级失败：HistoryService._append_tv_transfer_detail() got multiple values for argument 'notification_kind'`
   —— 运行时新旧模块签名不一致（插件热更新未整体重启），且该调用失败会直接中断整条洗版流程。
2. 跨盘转存「未命中秒传即中止」→ 大量 `service.py 跨盘转存失败`，属配置策略，另行确认。

## 5. 可选方案

| 方案 | 内容 | 代价 | 结论 |
| --- | --- | --- | --- |
| A. 单门槛 + 异步队列（采用） | 命中订阅才转；未命中即忽略；转存由后台队列串行执行，按订阅合并批量提交 | 改 `tg_monitor.py` 判定与调度，前端删两个控件 | 与用户要求一致，同时根治卡死 |
| B. 内容驱动（不看订阅） | 按画质/类型/关键词直接转存，自动建订阅或落临时目录 | 需自动建订阅 + 目标目录策略，改动面大 | 否决：没有订阅就没有「缺集/洗版」语义 |
| C. 保持现状 + 只调参数 | 关白名单、放大回溯 | 卡死问题仍在 | 否决 |

## 6. 结论

采用 A。判定链收敛为一条：
`抓链接 → 匹配全部订阅（唯一高置信）→ 命中：缺集优先、其次洗版 → 入队转存；未命中：ignored（只留 20 条排障样本）`。
