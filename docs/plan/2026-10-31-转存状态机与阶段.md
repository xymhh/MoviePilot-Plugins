## 0. 背景（执行方必须先读）

CloudSubscribeX（下称 CS）是 MoviePilot 的网盘订阅插件：搜索资源 → 转存到网盘 → 落盘校验 → 生成 STRM → 进媒体库。
用户每天跑几十个订阅任务，历史表里会长期堆积状态不正确的记录（「假成功」「永远处理中」）。

此前已经做过两轮修复（**不要重做，只许复用**）：

| 已有能力 | 位置 | 说明 |
| --- | --- | --- |
| 落盘自检 | `plugins.v2/cloudsubscribex/handlers/sync/landed.py` | 成功终态前核对目标目录真有文件；查无实据把状态降级成 `待确认` |
| 孤儿记录修复 | `handlers/sync/history.py:1735` `reconcile_orphan_finalize_records()` | 「后处理已提交但终态没写回」的记录补写 |
| 失败原因正交分类 | `core/failure.py` | `failure_kind` / `failure_retryable`，永久性/暂时性失败分开 |
| 同步作业账本 + 租约 | `core/database/sync_jobs.py` | 已有 `JOB_*` 状态与 `lease_until`，`reclaim_expired()` 在 `:247` |
| 数据库层 + alembic | `core/database/`（`manager.py:112` 启动自动 `upgrade head`） | 迁移目录 `core/database/alembic/` |

本轮要解决的**不是**「再造一套业务」，而是三件具体、可验证的事。

## 1. 现状缺口（已由主 agent 逐处核对，执行方无需重新论证，但要按这些位置改）

1. **状态写入散落，没有任何合法性校验。** 状态是六个人见人爱的中文字符串，任何模块都能随便写：
   - `handlers/sync/retry.py:86`、`:88`、`:105`、`:587`
   - `handlers/sync/movie.py:714-715`
   - `handlers/sync/television.py:959-960`
   - `handlers/sync/upgrade.py:704-705`
   - `handlers/sync/pt_upgrade.py:325`
   - `handlers/sync/resources.py:425`、`:885`
   - `handlers/sync/history.py` 内部多处（`:1450-1467`、`:1754-1764` 等）
   数据库列是自由文本 `String(32)`（`core/database/models.py:73`），写错也照样入库。
   实际后果：终态能被「跳过」覆盖成非终态、能被重复写成别的终态，事后只能靠人肉看日志。

2. **没有「阶段」概念。** 只有进度数值（`core/transfer.py:1206` 的 `stage_transferred/stage_total`）。
   用户看到「处理中」无从得知是卡在转存、校验还是后处理。

3. **`reclaim_expired()` 全仓无调用者**（`core/database/sync_jobs.py:247`）。进程重启后
   遗留的 `transferring/verifying/finalizing` 作业租约永远不回收，作业被永久跳过。

4. **前端状态筛选缺「待确认」。** `frontend/cloudsubscribex/src/components/dashboard/HistoryTable.vue:800`
   的 `statusOptions` 只有 `["处理中","下载中","成功","失败","秒传失败","跳过"]`，而
   `statusColor()`（`:1056`）和列表 chip 都支持「待确认」——用户在界面上筛不到这批记录。

## 2. 必须交付的三件事

### S1 状态机模块 `core/state.py`（唯一写入口）

- 用常量集合固化 **六个既有中文字符串**，一个都不许改名、不许新增：
  `处理中` / `下载中` / `成功` / `失败` / `跳过` / `待确认`
  - 注意：前端下拉里的「秒传失败」是**筛选层伪状态**（`status=失败 AND failure_kind=checksum_miss`），
    **不是状态**，禁止写进库里当 status。
- 定义**合法迁移表** `ALLOWED_TRANSITIONS`，最少覆盖：
  - `处理中 → 下载中 / 成功 / 失败 / 跳过 / 待确认`
  - `下载中 → 处理中 / 成功 / 失败 / 跳过 / 待确认`
  - `成功 → 待确认`（落盘自检降级，唯一允许的终态退出）
  - `待确认 → 成功 / 失败 / 跳过`（人工核查/重新检查落盘后收敛）
  - `失败 → 处理中`（重试）、`跳过 → 成功 / 处理中`（手动标记成功 / 重试）
  - **终态之间互不覆盖**：`成功→失败`、`失败→成功`（除非来自人工标记成功走显式入口）、`跳过→失败` 一律非法
- 提供唯一入口：

```python
def transition(record: dict, to: str, *, stage: str | None = None,
               reason: str = "", task_id: str = "") -> bool
```

  - 合法：原地改 `record["status"]`（`stage` 非空则同时写 `record["stage"]`），返回 `True`
  - 非法：**不改不改库、不抛异常**，打一条 `WARN` 日志，字段顺序固定
    `task_id=… from=… to=… stage=… reason=…`，返回 `False`
  - 记录本身的 `failure_kind` 等字段不受影响（保持 `core/failure.py` 现有语义）
- **`ALLOWED_TRANSITIONS` 要能被单测直接 import 断言**，不要藏在闭包里。
- 上面列出的 9 个写入点全部改为调用 `transition()`；`history.py` 内部的状态赋值同样改走它。
  `handlers/sync/history.py` 里 `_MANUAL_SUCCESS_STATUSES`（`:63`）代表的人工标记成功属于
  **显式入口**，允许 `失败/跳过 → 成功`，实现方式是在 `state.py` 里加一个参数或专用函数
  `transition_manual(record, "成功", ...)`，**不要**把这条放宽写进通用迁移表。

### S2 `stage` 字段（库 + 下发 + 前端）

- 阶段取值（英文常量，前端负责中文展示）：
  `queued` 排队 / `searching` 搜索 / `transferring` 转存 / `verifying` 校验落盘 /
  `postprocessing` 后处理（重命名/STRM/整理）/ `done` 结束
- alembic 迁移给 history 表加 `stage VARCHAR(32) NOT NULL DEFAULT ''`：
  - 迁移文件放 `core/database/alembic/versions/`，按现有命名风格
  - **必须向后兼容**：老库升级不报错、老记录 `stage` 为空串；空 stage 在页面上不显示（不要显示「未知」）
  - 老记录回填**不做**（无法还原，别编造）
- `handlers/sync/history.py` 的页面字段构建处补 `stage` + `stage_label`（中文：排队/搜索/转存/校验/后处理/结束），
  空串时 `stage_label` 也为空
- `HistoryTable.vue`：
  - 状态 chip 下方（或同格小字）显示 `stage_label`，仅非空时显示
  - `statusOptions`（`:800`）补 `"待确认"`
  - PC 表格和手机卡片两处都要改（`:470` 和 `:647` 附近是两个渲染分支）

### S3 清扫兜底（让非终态必然收敛）

- **接上 `reclaim_expired()`**：在现有周期性调度里调用（找插件已有的定时任务挂载点，
  例如 `__init__.py` 中 `reconcile_orphan_finalize_records()` 所在的那条周期链路附近，
  `__init__.py:813` / `:1920` 可参考），默认每 5 分钟一次；回收数量进 INFO 日志。
- **新增超时清扫**（可放 `handlers/sync/history.py` 或新模块 `handlers/sync/sweeper.py`）：
  - 条件：状态 ∈ {`处理中`,`下载中`} 且 `updated_at`（或等价时间字段）早于 now-60min
    且同步作业账本里**没有**对应的活动作业
  - 动作：跑一次已有的落盘自检
    - 目录列举**成功且确有文件** → `成功`
    - 目录列举**成功但无文件** → `待确认`
    - 目录列举**失败/超时（无法核实）** → **保持原状态不动**，打 WARN（区分「无法核实」与「确实没有」，
      这是既定原则，不许合并处理）
  - 每条改动打 INFO：`task_id=… from=… to=… stage=… reason=sweeper`
- 60 分钟阈值做成模块常量（便于单测覆盖），**不要**加用户配置项（本轮不加开关）。
