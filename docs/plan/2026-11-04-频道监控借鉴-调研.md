# 调研：频道监控该向哪些成熟项目借鉴（CloudSubscribeX 1.9.40）

> 日期：2026-11-04｜触发：用户反馈「频道监控不如其它项目好用，看看 GitHub 成熟项目」
> 范围：只评估「频道发现 → 过滤 → 转存」这一段，不涉及整理/STRM/播放
> 结论：**② 改造**——保留现有「订阅匹配 + 按集收敛 + 队列」引擎，补 3 个能力，不整体照搬

## 二、我们现在的真实短板（代码证据）

| 短板 | 证据 | 用户可感知的后果 |
| --- | --- | --- |
| **只有「命中订阅」一条路** | `core/tg_monitor.py:505` 强制 `monitor_mode="subscriptions"`；`auto_subscribe_ids` 仅保留字段不生效 | 想「把这个频道的新资源全部存到某目录」做不到，必须先建订阅 |
| **没有每频道目标目录** | `normalize_channel_rules()` 只有 channel/keywords/exclude/scan_limit | 多频道无法分流，全靠订阅名匹配 |
| **没有通知** | `tg_monitor.py` 全文无 notify/push；只有页面内条目状态 | 转存成功/失败、连续失败、频道异常都要自己刷页面 |
| **没有代理** | `configure()` 无 proxy 参数；Telethon 客户端直连 | 服务器在受限网络时整个功能不可用（当前机器在法兰克福，暂不影响） |
| **10 分钟轮询** | `_loop()` 固定 `self._interval`，默认 10 分钟（最小 1 分钟） | 热门剧集抢不到首传；消息被删就永久丢失 |
| **失败条目会卡住** | 2026-10-30 调研已记录：合并后成员消息失去独立状态 | 一次批量失败要人工逐条点（1.7.114 只修了「假失败」一类） |

已有的强项不要丢：按集收敛、质量偏好、去重、断点续跑、队列积压保护、私有频道（用户会话）。

## 三、建议吸收的 3 项（按性价比排序）

### A. 关键词直存 + 每频道目标目录（最高优先）

- 参考：TgtoDrive「目录分流」、tgto123「每频道关键词 + 固定目标目录」
- 规则新增 `mode: subscription | directory`：
  - `directory` 模式：关键词命中即把该消息的所有分享链接转存到 `target_dir`，不要求订阅；
  - `subscription` 模式：保持现状。
- 复用现有手动转存链路（`SyncApi.api_vue_start_manual_sync`），只换「目标解析」。
- 工作量：**1.5–2 天**（后端 + 配置 UI + 回归测试）。

### B. 通知与日报

- 参考：TgtoDrive 企业微信通知 / Telegram 定时发送；tgto123 每日热更推送
- 事件：新条目命中、转存成功、转存失败、连续 N 次扫描异常；
- 渠道：复用插件现有**飞书**通知，加「TG 监控」独立开关 + 每日 09:00 汇总。
- 工作量：**0.5 天**。

### C. 实时监听（可选开关）

- 参考：成熟项目多为轮询，但 Telethon 用户会话可直接 `events.NewMessage`；
- 设计：`tg_realtime=true` 时注册事件处理器，实时入队；轮询保留作兜底（每 30 分钟对账一次游标）；
- 风险：断线重连、FLOOD_WAIT、进程重启丢事件 → 必须保留轮询对账。
- 工作量：**1 天**（含异常与重连测试）。

### 暂不吸收

- 整包搬运 / 不判集数（TgtoDrive）：与「按集收敛省流量」相反，用户明确要省流量；
- 多账号会话池：当前单账号够用，收益低、风控风险高；
- 代理：等服务器迁回受限网络再加（0.5 天，随时可补）。

---

## 四、结论

选 **② 改造**：

1. 不换引擎，避免重蹈「一条消息搬一整套」的流量问题；
2. 先做 A（直存 + 目录分流），这是「不如其它项目好用」的最大感知差；
3. B 紧随其后，成本最低；
4. C 作为可选增强，必须带轮询兜底。

- C 是否需要「仅对指定频道实时」，避免全量事件放大风控？
