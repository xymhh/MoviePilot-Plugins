# aria2 作为插件内置下载引擎 — 调研（2026-10-31）

> 状态：待审（未动代码）
> 目标：把 aria2 作为 CloudSubscribeX 的**内置**下载引擎（随插件分发二进制、插件自己拉起与管理），不再依赖外部 aria2-pro 容器 / RPC 端点。

## 0. 为什么要做（动机，不含虚假收益）

实测（2026-10-31，见 `ARIA2_QUARK_TODO.md`）：**aria2 与裸 curl 多连接在同一连接数下基本同速**（96 连接 11.91 vs 12.28 MB/s；64 连接 3.01/3.28 vs 2.57）。所以选型理由不是"更快"，而是：

| 收益 | 现状痛点 |
| --- | --- |
| 断点续传成熟（`.aria2` 控制文件、跨进程恢复） | 现有 Python 下载腿重试要从头来，靠 `_LinkRefresher` 兜 |
| 连接调度/分段/重试/限速都是久经考验的逻辑 | 自研 `_download_parallel` 只有 range 拼接，缺退避与失败分片重试 |
| 单进程吃连接，不占用 MP 的线程与 FD | 现实现每任务 N 线程，`ulimit -n 1024` 是硬墙 |
| 任务级 `split/max-connection-per-server` 可调、可观测 | 只能改全局线程数 |
| 二进制可随包分发，用户零安装 | 现在要单独跑一个 aria2-pro 容器并映射端口 |

## 2. 结论：**拼装 + 自研薄壳**

- **二进制**：直接取 `dmesg00/aria2-static-builds` v1.37.0 的 linux-gnu-64bit 静态包（已实测可运行），不再自编。
- **控制面**：自研极简 JSON-RPC 客户端（约 150 行，零新依赖），不复用 aria2p。
- **接缝**：在 `core/transfer.py` 的下载入口加"选引擎"薄层，`Aria2Downloader` 与原下载器同签名，任何异常一律回落原下载器。
- 不引入第三方下载器进程管理框架，不接 BT/磁力。

## 3. 必须让用户知道的约束

1. **GPL-2.0**：随插件 zip 分发 `aria2c` 二进制 → 仓库需保留上游 COPYING/源码地址与构建来源说明，用户能取到对应源码。插件自身代码不受影响（只 fork 进程，不链接）。
2. **架构**：仅打包 `linux-x86_64`（你的 MP 是 Debian 13 / x86_64 / glibc 2.41 / 4 核 / 12 GB）。其他架构（arm64、armv7）自动回落内置下载器，日志提示一次。
3. **体积**：包内 +约 4 MB（strip 后）。
4. **不承诺更快**：实测同连接数同速；接入后速度上限仍由`aria2_connections`（建议 64，96 为有效上限，128 反而更差）决定。
