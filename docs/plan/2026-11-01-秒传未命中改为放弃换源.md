# 秒传未命中策略：从「回落上传」改为「放弃并换源」（1.8.9）

> 状态：已实现，测试与 lint 通过，前端已重建，待推送发版

## 背景

用户 2026-11-01 要求：「秒传失败直接清理，并标记这个资源，然后继续从其它分享中下载，尝试秒传」。

改造前（1.8.8 及以前）默认 `cross_transfer_rapid_miss_action=fallback`：

- 秒传未命中 → 保留完整中继缓存 → 继续真实上传（30 GB 级别的包要传完）；
- 上传失败时缓存还会被刻意保留供重试，再叠加 6 小时保留期，磁盘被长期占用。

用户的实际场景：一部片有多个分享候选，只要其中一个文件的 115 库里已有，秒传就能零传输完成。既然如此，未命中就该快速放弃这个候选，换下一个。

## 改动

| 位置 | 改动 |
| --- | --- |
| `core/config.py` | `cross_transfer_rapid_miss_action` 默认 `fallback` → `abort` |
| `__init__.py` | 类属性默认值、`apply` 读取默认值同步改为 `abort` |
| `core/drive_manager.py` | 构造 `CrossTransferTaskManager` 时的 `getattr` 兜底改为 `abort` |
| `core/transfer.py` | 构造参数默认 `abort`；`RapidMissAborted` 分支补日志：已清理中继缓存 + 记录 SHA1 + 继续尝试其它分享；任务 message 追加「中继缓存已清理」 |
| `handlers/sync/service.py` | `abort_reason=rapid_miss` 的失败改为 `warning` 级、明确「已跳过该资源，本次同步继续尝试后面的候选」 |
| `frontend/.../fields/transfer.js` | 选项文案与提示重写，标明默认项与代价；dist 已重建 |

## 行为链路（abort 模式）

1. 源盘给了 SHA1 → 先做零流量探测（源盘能随机读区段时）；
2. 夸克这类探不了的源 → 正常下载本体；
3. 下载完成 → 用本地文件做 115 秒传校验（`sign_check` 区段 SHA1）；
4. 未命中 → `RapidMissAborted`：**无条件删除中继缓存**（即使 `cache_complete=True`），写 `abort_reason=rapid_miss`，把 SHA1 写入负缓存（24h）；
5. 上层候选循环 `continue` → 试下一个分享；
6. 同一 SHA1 在 24 小时内再次出现 → 直接跳过，不再下载验证。

## 明确不做

- **不做「全部候选都未命中后再兜底真上传」**：那等于把默认行为又改回 fallback。需要时说一句即可加开关。
- **不做「边下边探」**：115 的 `sign_check` 区段要等 `upload_file_init` 返回才知道，改成「先下区段再判定」需要下载腿支持暂停/续下，属于独立改造。
- **不动负缓存 TTL（24 小时）**：够用且能自愈（别人把这文件传上 115 后自然命中）。

## 代价（写在这里，避免以后困惑）

默认 abort 后，**115 库里没有的片源不会再有真实上传**，转存会直接失败。想恢复老行为：配置页「秒传未命中处理」选「回落普通上传」，或 `cross_transfer_rapid_miss_action=fallback`。

另外 `cross_transfer_direct_stream`（跨盘直传）在 abort 模式下不生效（UI 已置灰），因为直传与「先判定再上传」互斥。
