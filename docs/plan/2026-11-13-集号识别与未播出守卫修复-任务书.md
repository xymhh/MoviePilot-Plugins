## 根因（两个独立缺陷）

### A. 识别计划与转存阶段集号解析口径不一致

- 识别计划：`utils/share_recognize.py:classify_path` → `_episode_from_name`，正则 `^0*(\d{1,4})(?=[ ._\-]|$)` 认「开头数字」，故 `14 DV.mkv → 14`。
- 转存阶段：`handlers/sync/naming.py:_summarize_share_episodes` → `FileMatcher.episode_from_file`；认不出的走 `utils/share_recognize.py:rescue_tail_episodes_from_names` → `_tail_episode_from_name`（正则 `(?<![0-9A-Za-z])(\d{1,3})$`，只认「末尾紧贴数字」）。
- 结果 `share_episodes={1..13}` → `missing_episode_set({14}) ∩ share_episodes = ∅` → `episodes_to_match` 空 → 0 转存。

### B. 媒体库已存在的集被 TMDB 错位日期判为未播出

- `handlers/sync/television.py`：`target_episode_air_dates` 为空日期也一律算未播出（2026-11-08 谷雨事故防护），且 `cloud_matched -= unaired_episodes`。
- 但库里明明有 E05，TMDB 分集数据错位（无 air_date / 未来日期），导致 E05 被判未播出、`note` 里被剔除（`_reconcile_subscribe_physical_episodes`）。
- 用户诉求：**库里实际存在的集不应被判未播出**，谷雨防护仍要保留（TMDB 整季无分集数据时退回旧口径）。

## 修复范围（冻结）

### A：统一集号识别口径

- 在 `utils/share_recognize.py` 新增**供转存阶段复用**的集号解析函数（与 `classify_path` 同源），支持「开头数字 + 空格 + 画质词」（`14 DV.mkv` → 14）。
- `handlers/sync/naming.py:_summarize_share_episodes`：对 `FileMatcher.episode_from_file` 认不出的文件名，用新函数补判；`rescue_tail_episodes_from_names` 的门槛（命中 >= 3、去重 >= 3、命中率 >= 80%）保持不动，避免谷雨式误转。
- 必须排除年份/分辨率（`_NOT_EPISODE` = 480/576/720/1080/2160/4320）、`2024.mkv` 这类年份文件。
- 不改 `FileMatcher.episode_from_file`、不改识别计划 `build_plan`。

### B：未播出守卫对「库里已存在的集」放行

- `handlers/sync/television.py`：`unaired_episodes` 计算后，减去 `media_server_episodes & expected_episodes`（媒体服务器实际存在的集）。
- 保留：TMDB 整季无分集数据时 `unaired_episodes=set()` 的旧口径；已有 `skipped` 日志与 `_reconcile_subscribe_physical_episodes` 行为不变。
- 不改订阅 `total_episode`、不改 `_season_episode_air_dates` 的取数逻辑。

## 明确不做

- 不改 `television.py` 的 `cloud_matched -= unaired_episodes` 语义之外的任何传输逻辑、不动每日额度、代理注入、负缓存、状态机、历史表结构。
- 不做「剧名不符」守卫放宽（那是第三个独立问题，用户未要求）。
- 不引入新依赖、不改 `requirements.txt`、不新增前端 UI。
- 不改订阅 `total_episode=25` 数据。
