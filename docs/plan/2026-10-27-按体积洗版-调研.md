# 按体积择优入库（洗版）— 调研

> 状态：已完成 2026-10-27，方案选定「② 改造本插件既有判重链路」
> 用户拍板：① 允许删旧文件 ② 采用推荐方案（分辨率 > 体积 + 阈值）③ 只对新入库生效，不做存量一次性洗版

## 1. 问题

2026-10-27 全库体检：41 部国漫 1737 集里 8 部画质参差（画江湖 720P 145 集 + 1080P 38 集、一人之下三档、狐妖 4K 144 集 + 1080P 13 集、灵笼、刺客伍六七）。根因不是「挑错了文件」，而是**同一部剧不同批次命中的分享不同**，每批各入库一批，入库时不和库里已有版本比「谁更好」。

用户要的：分享链接本身带文件大小，能不能按大小判断并洗版入库。

## 2. 事实核对（先查本地，再查 GitHub）

- **分享列表确实带文件大小**：`handlers/search/platform_rules.py:250` 在没有规则组时就是按 `size` 倒序挑最大文件；`handlers/sync/upgrade.py:469` 也是直接读 `matched_file.get("size")`，不下载即可得体积。
- **本插件已有「替换 + 删旧」能力**：`handlers/sync/episode_dedup.py:310 _episode_dedup_decision()` 返回 `proceed / replace / skip`，`_apply_episode_dedup()` 按 `file_id` 删旧文件，且**在新文件转存成功之后**才删（`handlers/sync/television.py:958`），失败只 warning 不阻塞。
- **但三道闸门让它在实际环境里不生效**：
  1. `core/config.py:225` `enable_cloud_upgrade=False`、`upgrade_subscribe_ids=[]` → 洗版链路根本不跑；
  2. `prefer_template_named_version=True`（默认）→ `episode_dedup.py:341` 只要现有文件名已符合重命名模板就直接 `skip`，而本插件转存的文件必然被模板改过名 → **体积再大也不换**；
  3. 决策先比 MP 规则组评分、同分才比体积（`rule_scoring.py` + `upgrade_mode=largest`），而实际没配规则组，评分全是 0。

结论：**不是缺能力，是判据埋在一个不会被走到的分支里。**

## 4. 结论

选 **② 改造**：不新造模块、不引外部件，在既有 `episode_dedup` 决策链里插入一个**纯函数比较器**，把「分辨率 > 体积」做成默认判据，删旧复用现有 `_apply_episode_dedup`。

- ① 拼装（MP 规则组 + 官方插件）：做不到「和库内已有文件比体积」，且用户已明确不要配一堆规则组。
- ③ 自研一套新链路：`episode_dedup` 已经把「列目录 → 比 → 删旧 → 写历史」跑通了，新造一份就是重复劳动（本项目已有一次 `cs-relay` 重复造轮子的教训）。

别人没有的那一段具体是：**「同集已有文件 vs 新候选文件」的体积/分辨率增减判定 + 阈值 + 删旧**，且判据来自分享列表自带 size，不需要下载探测（115 Range 探测作为可选增强，本次不做）。
