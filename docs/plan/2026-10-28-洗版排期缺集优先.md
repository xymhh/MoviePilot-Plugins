# 洗版排期：缺集优先 + 每轮洗版上限（1.7.101）

> 状态：已完成 2026-10-28 → ../summary/2026-10-28-洗版排期缺集优先.md

## 现象

用户更新到 1.7.100 后反馈：凡人修仙传（洗版订阅，已入库 30+ 集、连载追更中）
的订阅任务仍然先去处理洗版，最新的缺集要等整轮洗完才轮到。

## 根因

`handlers/sync/upgrade.py::_process_tv_subscribe_upgrade` 把「已入库集（洗版对象）」
和「缺失集（补集对象）」合并成一个集合，再 `sorted()` 按集号升序处理：

- 凡人：库内 E01–E34，缺 E35+ → 排序结果 `[1,2,...,34,35,36]`；
- 每集 4.8GB 的 4K 洗版排在前面，补集永远最后。

1.7.99 的「缺集优先」只作用于 **TG 频道队列**（`core/tg_monitor.py`），
订阅任务路径完全没有优先级概念 —— 这是两套入队入口。

## 改法

新增纯函数 `handlers/sync/upgrade.py::plan_upgrade_episode_order()`：

```python
plan_upgrade_episode_order(local_episodes, all_expected_episodes, target_episodes, limit)
# -> (本轮待搜索集数, 缺集集合, 因上限推迟的集)
```

规则：

1. **缺集优先**：`sorted(missing) + sorted(upgrade_only)`，补集永远排在最前；
2. **每轮洗版上限**（新配置 `upgrade_episode_limit`，默认 0=不限）：
   只截断洗版部分，缺集全额处理；
3. **手动指定集数**（`target_episodes` 非空，多为补集请求）：整批按优先处理，
   不受上限约束。

日志：有缺集时输出「缺集优先：先补 E35–E36（2 集）」；被上限推迟时输出
「每轮洗版上限 N 集，本轮暂不洗版 M 集：[...]」。

前端：插件设置 → 洗版 → 洗版参数 → 「每轮洗版集数上限」（`number`，最小 0）。

## 验收

- 新增 `tests/test_upgrade_episode_priority.py`（4 例）：缺集优先、上限只截断洗版、
  手动集数不受限、总集数未知时仍排序。
- 全量 808 tests，1 失败 + 14 收集错误与基线一致（本机缺依赖）；lint 0 error。

## 说明

- 未做「按体积增益排序」：候选源体积在搜索后才有，需要在批次内预扫一遍候选，
  收益（把大文件排后）不如缺集优先直接，本轮不做。
- 未改 TG 队列优先级（1.7.99 已实现）。
