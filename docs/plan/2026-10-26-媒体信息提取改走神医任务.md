# 媒体信息提取改走神医任务 + 直链缓存 TTL 收敛（1.7.74）

> 状态：已完成 2026-10-26 → [总结](../summary/2026-10-26-媒体信息提取根因与修复.md)

## 背景（实测证据）

《宋代足球小将》40 集在 Emby 里全部**没有媒体信息**（`MediaSources[].MediaStreams` 为空，播放仍正常）。

| 实测项 | 结果 |
| --- | --- |
| 115 直链寿命 | 19:46:17 签发的链接，20:56 再取返回 `{"message":"request expired","status":403}` → **≤70 分钟** |
| CS 直链缓存 | `core/api/redirect.py` `_CACHE_TTL_SECONDS = 6 * 3600`（6 小时）→ 远超真实寿命 |
| ffprobe 默认 UA 打 CS 302 | 403（过期链接） |
| 带新链 + 显式 UA 取流 | 200，`duration=880.678s` |
| CS 触发提取的方式 | `POST /emby/Items/{id}/PlaybackInfo` 返回 200，但 MediaStreams 仍为 0 —— **PlaybackInfo 不会触发 ffprobe** |
| 失败日志 | 近 3000 行日志 9 次「Emby 入库后仍未找到媒体项」（路径翻译问题已由 1.7.67 修掉），另有 `TypeError: 'NoneType' object does not support the context manager protocol` 掩盖真实连接错误 |

## 方案

1. **直链缓存 TTL 6h → 45 分钟**：低于实测寿命，ffprobe / 神医在拿链时拿到的必然是新鲜链接。
   代价：同一文件重复播放会多换几次链（115 换链本身很快，实测 <300ms）。
2. **提取改为触发 Emby 计划任务 `Extract MediaInfo`**（神医助手注册）：
   - 仍先按 `Items?Path=` 确认媒体项存在（保留「仍未找到媒体项」诊断）；
   - 命中后调用 `POST /emby/ScheduledTasks/Running/{taskId}` 启动任务，由神医按自己的节奏 ffprobe；
   - 同一媒体服务器 **5 分钟冷却**（`_MEDIAINFO_TASK_COOLDOWN = 300`），成批剧集只触发一次；
   - 任务已在运行则视为成功、不重复 POST。
3. **修 `with RequestUtils(...).get_res(...)` 的空响应坑**：`get_res` 异常时返回 `None`，
   `with None` 抛 `TypeError` 把真因吞掉；改为统一走 `_emby_request()`（`raise_exception=True`
   + 原样带出 `异常类型: 消息`），并按退避重排。

## 约束

- 不改配置项（复用已有 `emby_mediainfo_enabled` 开关），不动前端。
- 只对 Emby 生效（Jellyfin/Plex 分支保持原样）。
- 任务名可改（类常量 `_MEDIAINFO_TASK_NAME`），避免神医改任务名后静默失效。
