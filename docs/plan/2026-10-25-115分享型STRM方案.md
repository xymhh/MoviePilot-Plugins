# 115 分享型 STRM（不转存）方案调研

> 状态：调研完成 2026-10-25，待实施

## 需求

CloudSubscribeX 目前只会为「已转存到网盘」的文件生成 STRM（`{base_url}?pickcode=…`）。
用户还希望能对**115 分享链接**直接生成 STRM（不转存、不占空间、随时可播），
行为对齐 P115StrmHelper 的「分享 STRM」功能。

## 现成方案对比

| # | 方案 | 维护 / 许可 | 能力 | 差距 |
| --- | --- | --- | --- | --- |
| 1 | `DDSRem-Dev/MoviePilot-Plugins` → `p115strmhelper`（线上用的就是它） | 活跃，GPL-3.0 | 分享 STRM 全流程：解析分享、遍历文件树、`?share_code=&receive_code=&id=` 模板、302 换链、清理 | 与 CS 的订阅/转存/整理链路是两套体系；直接依赖等于放弃 CS 统一管理 |
| 2 | `p115client.share_download_url()` | p115client 官方库，MP 已内置 | 一行拿到分享文件的 CDN 直链（`app="android"`） | 只解决「换链」，生成/目录/命名/清理要自己做 |
| 3 | CS 现有 `drive/p115/share.py` | 本项目 | 已能解析分享链接（share_code/receive_code 缓存）、遍历分享文件树、校验状态 | 只服务于「转存」，没有 STRM 生成与播放换链 |
| 4 | MediaWarp | 活跃（Go） | Emby 302 反代成熟 | 不支持 115 分享链接换链；它假设 strm 内容已是可直连 URL |
| 5 | Alist / OpenList 115 分享挂载 | 活跃 | 把分享当目录挂载 | 需要额外服务与存储驱动，播放仍走 AList 代理，链路更长 |

## 结论：方案 ②+③ 拼装，改造 CS 自身

- **换链**：直接用 `p115client.share_download_url({"share_code","receive_code","file_id"}, app="android")`，
  不新建 HTTP 客户端、不自己拼签名。
- **解析/遍历**：复用现有 `drive/p115/share.py`（已能拿 share_code、receive_code、文件树）。
- **STRM 内容模板**：沿用现成模板机制，新增分享变量
  `{share_code} {receive_code} {file_id}`，默认模板
  `{base_url}/api/v1/plugin/CloudSubscribeX/redirect?share_code={share_code}&receive_code={receive_code}&id={file_id}&file_name={file_name}`。
- **播放**：`redirect` 端点识别 `share_code` 参数 → 走 `share_download_url` → 302，
  缓存键 `(share_code|receive_code|file_id, user_agent)`。

不选①的原因：用户要的是**一套**插件管订阅 + 转存 + STRM，再把 P115StrmHelper 的分享能力也并进来；
两套插件并行会产生目录/文件内容互相覆盖（本次 `/strm/115网盘` 就是活例子）。

## 已知风险

1. `share_download_url(app="android")` 产出的直链是否同样绑定取链 UA（`f=1`）需实测；
   若绑定，UA 必须像 pickcode 一样一路传下去（1.7.54 已铺好的管道可直接复用）。
2. 分享失效（`errno=4100008`）需要自动刷新 receive_code 后重试一次（P115StrmHelper 就是这么做的）。
3. 目录切换：`/strm/追更` → `/strm/115网盘` 时，若先全量覆盖、后补分享功能，
   P115StrmHelper 已生成的分享 STRM 会被改写成 CS 不认识的格式 → 那些集直接播不了。
   **所以顺序必须是：先补分享功能 → 再切换目录 + 全量覆盖。**
