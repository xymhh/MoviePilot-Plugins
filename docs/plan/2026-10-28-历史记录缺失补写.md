# 转存成功却丢历史记录：补写方案（1.7.102）

> 状态：已完成 2026-10-28 → ../summary/2026-10-28-历史记录缺失补写-落地.md

## 现场证据（2026-10-28 线上日志）

- `20:28:40–20:28:43 postprocess.py — 历史记录长时间缺失，放弃写入终态（成功）`：凡人修仙传 S01E08–E35 连续 30 条。
- 文件确实落盘：`16:49:25 target_writer — 目标写入written E04 1.26GB 写入后核验通过`、`20:06:36 E35 1.63GB`；`20:28:46` 通知「本次转存 31 个文件 E04-E35」。
- 历史页实测：该剧 160 条记录仍是 2026-10-11 的老数据，E04–E32、E34、E35 一条都没有。
- Emby 侧 191 集齐全，所以不会重复转存；丢失的是「插件历史」这条链路：历史页缺口、深度联动删除匹配不到来源、洗版体积基线只能拿 STRM（无 size）。

## 根因

`handlers/sync/history.py::_mark_offline_history_status_batch` 只做「更新已存在的记录」：按 `finalize_key` / `share_url` / `(file_name, cloud_dir)` / `(cloud_dir, season, episode)` 定位。当转存链路本身没写进历史（记录从未创建），四条兜底全部落空 → `matched_records=0` → 后处理重排队 10 次 / 30 分钟后「放弃写入终态」，pending 项被丢弃，事实永久丢失。

## 方案

1. `_append_backfill_history_record(...)`：用已知落盘事实（mediainfo + 订阅 + 季集 + 文件名 + 目录 + 体积）直接生成一条状态为「成功」的历史记录，带 `landed=True`、`backfilled=True`；按 `(cloud_dir, file_name, season, episode)` 去重，绝不覆盖已有记录。
2. `_backfill_history_from_pending(item)`：从后处理项自带的 `mediainfo` / `subscribe_id` / `success_episodes` 取值，逐集补写。
3. `postprocess.py::_resolve_history_record`：放弃终态之前先补写，补写成功即视为终态已写并结算 pending 项（不再打「放弃写入终态」）。
4. `backfill_history_from_cloud(keyword)` + `POST /history/backfill`：扫订阅季目录实测文件，把「网盘有、历史无」的集批量补写成成功记录——用于修复 1.7.102 之前已经丢掉的历史（例如凡人那 30 条）。

## 边界

- 只补「历史里没有」的季集；已有记录（含失败、待确认）一律不动。
- 补写记录 `landed=True` 有据：数据来自 `target_writer` 写入核验通过的 pending 项，或季目录实测列表。
- 不写 MP 整理历史（避免污染 MP 侧判重），只在插件历史内可见。
- 手动 `mark_success` 定过案的记录不受影响。
