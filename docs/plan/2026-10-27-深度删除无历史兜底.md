# 深度删除：无转存历史时的路径反查兜底

> 状态：已完成 2026-10-27 → 见文末验收

## 背景

2026-10-27 12:01，用户在 Emby 删除 4 部国漫（百日成王 / 深渊之上 / 武神主宰 / 万界独尊）：

- Emby 国漫库 41 → 37，删除动作本身成功
- 115 网盘 41 个目录一个没少
- 插件日志：4 条 `收到深度删除请求`，4 条 `深度删除未匹配到对应的插件历史记录`
- 查插件历史：这 4 部 `total=0` —— 不是本插件转存的，没有 `cloud_dir/file_name` 映射

结论：`delete_by_media_server_paths()` 只能靠转存历史反查网盘文件，
覆盖不了「手动转存 / 其他插件转存 / 早期版本」的媒体。

## 需求

媒体服务器整剧删除时，即使没有转存历史，也要能删掉对应网盘目录。

## 方案

`delete_by_media_server_paths()` 在 `matched == 0` 时调用新增的
`_delete_cloud_media_by_server_paths(targets)`：

1. `_configured_media_path()` 把媒体服务器路径翻译成本地真实路径
   （显式映射优先，尾部对齐兜底；必须落在 `local_resource_path` 之下）
2. 去掉媒体根前缀得到相对路径，拼到 `_CLOUD_MEDIA_ROOT` 得到网盘目录
3. 逐条安全校验 → `resolve_directory()` 确认存在 → `delete_file(dir_id)`（走回收站）
4. `_purge_local_media_directory()` 清掉本地遗留 STRM 目录
5. 通知文案新增「网盘目录 N 个」

## 安全边界（硬约束）

| 约束 | 行为 |
| --- | --- |
| 相对路径 < 2 级（媒体根、分类目录） | 拒绝，`skipped += 1` |
| 命中 `_is_protected_cloud_directory()`（媒体根/转存目录/其父级） | 拒绝 |
| 网盘目录不存在 | 跳过 |
| 目标是单文件而非目录 | 跳过（本版只处理整剧/整部电影） |
| 本地路径不在 `local_resource_path` 之下 | 跳过 |
| 删除方式 | 网盘回收站，可恢复 |

## 非目标

- 不处理单集/单文件删除的兜底（留待后续，需要先做文件名→网盘文件解析）
- 不改动原有「有转存历史」的匹配路径

## 1.7.83 追加：1.7.82 线上实测仍失败（16:12/16:13）

**用户 16:12、16:13 在 Emby 里删《武神主宰》《万界独尊》，深度删除依旧没删网盘。**

日志（plugins/cloudsubscribex.log）：

```
cleanup.py - 深度删除兜底：无法定位媒体路径，跳过 /media/strm/115网盘/剧集/国漫/武神主宰 (2020) {tmdb-110181}
  - 媒体服务器条目路径不在插件配置的媒体根路径中：…，当前媒体根路径=/strm/115网盘
media_library.py - WARNING 深度删除未匹配到对应的插件历史记录
```

**根因：时序，不是映射也不是权限。**

| 证据 | 结论 |
| --- | --- |
| 16:12/16:13 报「路径不在媒体根下」 | 反推时 `_configured_media_path()` 的三步（原样命中 → 显式映射 → 尾部对齐）都要 `exists()` |
| 本地 STRM 目录 `…/国漫/武神主宰 (2020) {tmdb-110181}` 的 mtime = **16:20:00** | 测试当时该目录**不存在**；16:20 由 STRM 同步重新生成 |
| 115 网盘 `/Alist/影视/moviepilot/媒体库/剧集/国漫` 仍 41 个目录，`/cloud/directories` 可解析出 id | 网盘侧正常，纯粹是反推阶段被本地不存在卡住 |

即：**神医深度删除会先删本地 STRM 文件，webhook 到达 MP 时本地目录已经没了** → 靠 `exists()` 校验的反推必然失败 → 永远跳过。1.7.82 在「本地文件还在」的前提下才成立，真实链路里这个前提不成立。

## 1.7.83 修复

- 新增 `_virtual_media_path()`（`handlers/sync/cleanup.py`）：本地路径校验失败时，用 `media_server_path_mappings` 做**纯前缀翻译**得到虚拟本地路径（不要求 `exists()`）
- 仅当显式映射存在且翻译结果落在 `local_resource_path` 之下才采用；没配映射仍然跳过（不猜）
- 采用虚拟路径后照旧走四道校验：相对路径 ≥ 2 级、保护目录、网盘目录必须真实存在、删除走回收站
- 本地目录已不存在 → `_purge_local_media_directory()` 返回 0，不会误删

**真实环境配置已就绪**：`media_server_path_mappings=/media/strm=/strm`，`local_resource_path=/strm/115网盘`（1.7.82 之所以没走通映射，是因为映射那一步也要 `exists()`）。

## 1.7.84：一次删除弹 3 条通知（16:40 实测）

用户 16:40 删《武神主宰》，企微/飞书收到 3 条一模一样的「深度联动删除完成（网盘目录 1 个）」。

日志证据（plugins/cloudsubscribex.log）：

| 时间 | tid | 结果 |
| --- | --- | --- |
| 16:40:48 | 4afd… | 兜底推断成功 → 删网盘目录 1 → **通知 1** |
| 16:40:48 | b382… | 同上 → 删网盘目录 1 → **通知 2** |
| 16:40:49/50 | 511b… / f134… | 511b 又删一次并通知，f134 才报「网盘目录不存在，跳过」 |

**根因**：神医/Emby 一次整剧删除连发 **4 条 webhook**（library.deleted ×2 + deep.delete ×2），每条都带同一 `Item Path`；1.7.83 逐条独立处理，于是同一网盘目录被删 3 次、通知 3 条。

**修复（1.7.84）**：新增 `utils/deep_delete_dedupe.py`

- 按目标路径做 **120 秒窗口占位**，窗口内同一目标只放行第一条事件；其余直接忽略（不删、不通知）
- 处理失败（无历史命中 / 网盘目录不存在）会 `release()` 释放占位，后续事件仍可重试
- 路径归一（去尾斜杠）+ 过期裁剪，避免内存增长
