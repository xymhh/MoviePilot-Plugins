# 秒传未命中 → 保留 SHA1 → 后续零流量重试（设计）

> 状态：已实现，待发布 1.7.98（2026-10-28）
> 背景：`docs/test/2026-10-28-洗版生效与秒传abort.md`

## 1. 问题

用户是海外 VPS，上传 115 极慢，配置 `cross_transfer_rapid_miss_action=abort`。实测暴露两个事实：

1. 夸克源没有 sha1，所以「先探测后下载」走不通 → 插件**完整下载 5GB**、算 sha1、试 115 秒传、未命中 → abort 并删本地。每次重试都白下一遍（今天 E09–E12 共 4 集约 20.7GB）。
2. 秒传命中的前提是「115 上已有同 sha1 文件」。这份 4K 今天没有，但**过几天可能就有**（别人上传）。

所以正确形态不是「中止就彻底放弃」，而是：**下载一次学到 sha1 → 存起来 → 以后每次只拿 sha1 去探测**。

## 2. 设计

| 环节 | 做法 |
| --- | --- |
| 记录时机 | 文件完整下载落盘后（`_run_locked` 里 `cache_complete = True` 处）算一次 SHA1 存入缓存，随后照旧走秒传/abort 逻辑 |
| 缓存位置 | 插件数据目录 `source_sha1_cache.json`（`get_data_path()`），不写库、不动 DB schema |
| 键 | `来源网盘|体积|文件名`（分享链接会变，不进键） |
| 值 | `{sha1, size, name, updated_at}` |
| 过期/上限 | 30 天 TTL、最多 2000 条（超出按 updated_at 淘汰最旧） |
| 使用时机 | 任务开始时若 `algorithm/checksum` 都为空 → 查缓存；命中则把 `algorithm=sha1, checksum=<缓存>`，日志写「命中源文件 SHA1 缓存，改为零流量秒传探测」 |
| 探测方式 | 复用已有链路：`probe_by_hash` + `_RemoteSha1RangeReader`（115 要求的二次校验区间，从夸克直链 Range 取几十 KB，不落盘） |
| 命中 | 任务成功、`method=rapid`、不下载不上传 |
| 未命中 | abort 模式下立即中止（**不下载**）；fallback 模式照旧下载+上传 |
| 清理 | 本地缓存文件照旧删；哈希条目保留，这就是重试的本钱 |

## 3. 边界

- 键不含分享链接：同一部片的多条 4K 分享若文件名体积相同，会被视为同一文件——115 秒传本身会用 sha1 校验，误判只会导致「探测未命中」，不会误入库。
- 缓存文件损坏/写入失败：按无缓存处理，只影响重试效率，不影响转存正确性。
- 首次仍要下载 5GB：夸克不提供 sha1 时无法避免；这是「学习成本」，只付一次。

## 2026-10-28 追加：持久化方案定为 SQLite 表（B 方案）

原方案把缓存写成 `source_sha1_cache.json`。已确认该实现是读-改-写 + 原子替换、无锁，并发写会丢更新，且与插件其它数据（`cloudsubscribe.db`）分裂成两套持久化。

用户决定：迁入同库表 `source_sha1_cache(cache_key PK, sha1, size, name, updated_at)`。

- 读取：`get(key, ttl_seconds=30d)`，过期即视为未命中
- 写入：原子 upsert（主键 `cache_key`），`limit=2000` 时按 `updated_at desc, cache_key desc` 淘汰尾部；写入前 `db.flush()`（会话 `autoflush=False`）
- 升级：结构靠 `init_db()` 的 `create_all` 补建缺失表；旧 JSON 在 `CloudSubscribeDataStore.initialize()` 里一次性导入并改名 `.json.migrated`
