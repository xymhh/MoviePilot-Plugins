# 调研：TgtoDrive 的频道监控转存是怎么做的（对照 CloudSubscribeX 1.7.110）

> 日期：2026-10-30｜触发：用户建议「学一下 tgtodrive 的逻辑」
> 对象：[walkingddd/TgtoDrive](https://github.com/walkingddd/TgtoDrive) ★2224，MIT，最近提交 2026-10-20，Python
> 读的是仓库内脚本版：`v6.6.4（最新版请在docker安装）/tgto123.py`(4190 行)、`tgto115.py`(613)、`tgto189.py`(1129)，以及 `README.md`

## 1. 它到底怎么转（证据）

| 环节 | 做法 | 代码位置 |
| --- | --- | --- |
| 发现 | 只轮询频道**最新消息窗口**，不建订阅、不回溯 | `tgto123.py:629 get_latest_messages`（按 `ENV_TG_CHANNEL` 多频道，`|` 分隔） |
| 幂等键 | **消息 URL**（`t.me/<channel>/<msg_id>`）唯一，处理过就跳过——**成功失败都算处理过** | `tgto123.py:602 is_message_processed`、`:611 save_message`（`IntegrityError`→UPDATE） |
| 链接提取 | 一条消息里**所有**网盘链接都提，自动补 `pwd=` | `tgto123.py:691-700`（正则抓提取码拼进 URL）、`:716 extract_target_url` |
| 转存 | **整个分享递归搬走**，落到**固定目标目录** `UPLOAD_TARGET_PID`；**完全不解析剧名/季/集** | `tgto123.py:728/853 transfer_shared_link`（`recursive_fetch`） |
| 剧集识别 | 不在转存阶段。`seasons/episodes` 只来自 TMDB，用来拼分享文案 | `tgto123.py:227-247 build_share_message` |
| 归位/去重 | 交给独立模块「影视整理」：TMDB 识别季集、分类命名归档、**覆盖比较**、多版本共存 | `README.md:32` |
| 再往后 | 「Emby 库存管理」：快照、筛缺集、预览去重清理清单 | `README.md:37` |
| 失败可见性 | 每条消息一行 `transfer_status`，重启后查表续跑，不静默丢 | `tgto123.py:611-626` |

全仓 **没有一个 `SxxExx / 第N集` 解析**（`grep -c "season\|episode"` 只命中 TMDB 文案拼接），
这是理解它的关键：**转存阶段不做内容判断**。

## 2. 和我们（1.7.110）的根本差异

| 维度 | TgtoDrive | 我们 |
| --- | --- | --- |
| 最小单元 | **一条 TG 消息** | 一个**订阅+季**队列单元（消息被合并进去） |
| 幂等键 | 消息 URL（天然不重复搬同一条） | 订阅+季（同一季只跑一次，但**丢了消息粒度**） |
| 集数判断 | 不判断，整包搬 | 判断（1.7.110 新增 `target_episodes`），只建目标集的基线 |
| 覆盖/洗版决策点 | **整理阶段**（文件级覆盖比较） | **转存阶段**（订阅级 baseline，先于搬运） |
| 漏集风险 | 极低（整包都进来） | 有（判断错/合并错就漏，见 1.7.110 的 `merged_from` 隐患） |
| 流量成本 | 高（14 条分享就搬 14 份） | 低（同季只跑一次，按集收敛） |
| 失败处理 | 每条消息有状态行，可续跑 | 合并后成员消息失去独立状态，39 条 failed 卡住 |

一句话：**它用「多花流量」换「绝不漏集」；我们用「按集收敛」换「省流量」，代价是决策点提前、错一次就漏。**

## 3. 结论：① 部分吸收，不整体照搬（选①而非③）

整体照搬会让我们退回「一条消息转一整套」——用户现在最痛的就是流量与排队，
照搬等于放弃 1.7.110 的收益。但它的两个结构性优点我们确实缺，**该吸收**：

### 吸收点 A：消息级幂等台账（必须做，成本小）

- 现状：消息合并进队列单元后，只有 `merged_from` 一串 id，单元失败/被丢弃 → 成员消息一起失联，
  用户在「频道监控」页只能看到 1 条失败，不知道背后 14 条消息都没转。
- 改法：条目增加 `message_states: {msg_id: pending|done|failed|merged}`，
  单元终态时**按消息子集**回写结果；失败时把成员消息退回 `pending` 且**保留去重键不占位**，
  下一轮可重新合并、重试——等价于 TgtoDrive「每条消息一行状态，失败可续跑」。
- 收益：39 条 failed 那类「卡住不动」不会再无解，也不会因为一次失败把 19 条消息一起作废。

### 吸收点 B：把「洗版/覆盖」决策点后移（中期，需单独任务书）

- 现状：`manual_upgrade=True` 在**转存前**就要建整季 baseline、算每集归属，所以一条消息=一次全季扫描。
- TgtoDrive 的做法：转存只搬，覆盖比较在**整理阶段按文件**做（`README.md:32`）。
- 落地路径（不推翻现有）：新转存先落到 `待整理/` 落点，洗版判定读取「落点目录 + 库内已有」的实际文件再决定
  归位/覆盖。这样 `target_episodes` 只影响「搬哪些」，不影响「怎么归位」，两个职责彻底分开。
- 代价：需要给整理链路加「落点目录」概念，工作量约 1.5-2 天，且要真机验证 STRM/Emby 不受影响。

### 不吸收：整包搬运 + 不做集数判断

省流量的收益是用户明确要的（单集消息重下 20 集、4.3GB/集），这条不能退。
