# TG 频道网盘资源监控（1.6.57）

> 状态：进行中（代码已完成，待在真实 MP 验证）

## 需求

用户希望直接监控 Telegram 上的网盘资源分享频道，把频道里发布的网盘分享链接接入
CloudSubscribeX 的转存链路，支持**私有频道**与**公共频道**，使用用户自己的 TG API。

## 为什么必须是「用户会话」而不是 Bot

Bot API 只能收到被拉进群/频道的消息，读不到频道历史，也无法加入私有频道。用户
自己有 api_id/api_hash，可以用 Telethon 登成一个普通 TG 账号，能读自己已加入的
任何频道（公开/私有），也能读到历史消息。

## 设计

1. **凭据**：`tg_api_id` / `tg_api_hash` / `tg_session`（StringSession）。
   设置页没有直接在配置里贴 session 的强制要求：可以点页面上的「登录 TG」，
   走「手机号 → 验证码 →（可选）两步密码」，成功后把 session 写回配置。
2. **频道**：多行列表，支持 `@username`、`t.me/xxx`、`-100...`、邀请链接。
3. **扫描**：后台线程按 `tg_monitor_interval_minutes` 轮询；每个频道记录最后处理的
   消息 id，只读新消息；首次按 `tg_monitor_scan_limit` 回溯最近 N 条。
4. **解析**：从消息文本抽取网盘链接（复用搜索渠道的域名表：115/夸克/阿里/天翼/
   移动/123/光鸭/UC/迅雷），另支持 magnet、ed2k；按链接去重，同一资源只入一条。
5. **入库**：`data/tg_monitor/items.json`，最多保留 `tg_monitor_max_items` 条。
   独立 JSON 而不是插件私有库：条目是消息级数据，放进 `CloudSubscribeDataStore`
   要加表迁移，收益不大。
6. **转存**：页面点「转存」→ 选目标订阅 → 复用 `sync/manual`（手动添加）流程，
   由它做季集识别、跨盘转存、整理。监控线程本身**不直接操作网盘**。

## 边界

- 不做「自动转存」：频道消息质量参差，先人工过一眼。
- 不解析频道里图片/文件形式的资源（只读文本消息）。
- 不代用户加入频道：私有频道需要用户自己先加入。
- TG 会话等同于账号权限，只存配置、不写日志/历史/通知。

## 验收

- 单测：链接抽取、频道写法归一、增量扫描去重、未启用时空跑。
- 真机：设置页登录 → 填频道 → 立即扫描 → 列表出现资源 → 转存到订阅成功。

## 2026-10-18 每频道独立规则

> 状态：代码完成，待发布核验

原设计把所有频道塞进一个 `tg_channels` 列表，关键词/排除词/回溯条数全局共用。
实际使用时不同频道定位不同（4K 频道、合集频道、日更频道），全局规则要么漏收要么
混入大量无关资源。

新结构：`tg_channel_rules` = 规则数组，每条包含

- `channel`：频道写法（`@name` / `t.me/...` / `-100...` / 邀请链接）
- `enabled`：该频道是否参与扫描
- `keywords`：包含关键词（命中任意一个才收录，空=不过滤）
- `exclude_keywords`：排除关键词（命中任意一个就跳过）
- `scan_limit`：该频道每轮回溯条数（1–200）

扫描线程逐条规则读取，只使用该规则的关键词与条数；扫描间隔、最多保留条数仍是
全局配置。旧配置 `tg_channels` + `tg_monitor_keywords` / `tg_monitor_exclude_keywords`
/ `tg_monitor_scan_limit` 在 `normalize_channel_rules()` 中自动展开为每频道一份，
升级后不丢频道。

前端用 `TgChannelRulesField` 弹窗编辑：增删频道、逐条启停、关键词多行/逗号输入，
页面上以 chip 回显。

> `8d5f2852226dfe9c850e4c640c4e3b424101db48348941deaf9170693a0fe01f`。

## 2026-10-18 每频道自动转存

每条频道规则增加：

- `auto_transfer`：该频道命中规则的新资源是否自动转存
- `auto_subscribe_id`：自动转存目标订阅 ID（必填；为 0 时只记录不转存）

扫描线程在每轮扫描完成后处理本轮新增条目：调用插件原有的手动转存链路
`SyncApi.api_vue_start_manual_sync(subscribe_id, resource_links)`，成功则把条目状态
置为 `transferred` 并记录 `subscribe_id` / `auto_transferred_at`；失败保留 `new`
状态并写 `auto_transfer_error`，不自动重试，避免对失效链接反复打接口。

自动转存只在「首次入库」时触发；同一消息重复扫描不会重复提交。

## 2026-10-18 订阅白名单匹配（1.6.68）

> 状态：已发布并核验 1.6.68（2026-10-18），CI 三绿；zip sha256
> `9fd63315e7d237e580ca4043541690e821f4308e600e49e4fe5f438316d87a3b`。

单值 `auto_subscribe_id` 只能把整个频道绑到一个订阅，频道里同时出现多部剧/综艺时
必然转错。1.6.68 改为**每个频道可勾选多个订阅**：

- 新字段 `auto_subscribe_ids: [id, ...]`；旧的 `auto_subscribe_id` 继续读取并并入
  白名单，旧配置不用重填。
- 扫描到新资源时，在 `core/tg_match.py` 里解析消息标题：媒体名、季号、集号、年份、
  类型；再与白名单内订阅逐条打分。
- 只有「标题精确 + 季号一致/可缺省」且没有相近候选时才自动转存；多个同分候选、
  标题前缀、包含匹配、匹配度过低一律留在列表里，条目标注
  `match_status=pending` 与 `match_reason`，由用户手动选择。
- 电影额外校验年份（差 ≤1 年才接受）；电视剧/综艺有集号或季号时不允许匹配电影订阅。
- 自动与手动转存都会把频道消息标题作为 `resource_titles` 传入手动同步，电影单文件
  兜底不再只依赖订阅名。
- 前端频道规则弹窗改为多选 chips 白名单；频道监控列表展示「自动匹配：原因」。

边界：标题解析不做 TMDB 识别，只做保守的文本匹配；认不出就 pending，不猜。

## 2026-10-18 真实频道标题补丁（1.6.69）

> 状态：已发布并核验 2026-10-18（`CloudSubscribeX_v1.6.69`，zip sha256 `4e5aeaa8…`）

用 `@QukanMovie` 的公开网页消息做只读回归，发现真实标题后缀会破坏精确匹配：

- `嫁金钗 (2026) 第1-8集`、`嫁金钗 (2026) 1-8`：旧解析只认 `第N集`，范围写法残留
  在标题里，归一化后变成 `嫁金钗第18集` / `嫁金钗18`，只能拿到 88 分（标题前缀），
  不会自动转存。
- `美人余 (2026) S01E20 ✨4K WEB-DL DDP 5 1`：`DDP 5 1` 未被音轨标记规则剔除，
  标题变成 `美人余ddp51`，同样只有 88 分。

1.6.69 增加：`第1-8集`、`1-2集`、`1-8`、`全集` 的识别与剔除；`DDP 5.1`、
`EAC3`、`AC3`、`FLAC`、`OPUS`、`10bit`、`SDR` 等音视频标记剔除。匹配阈值不变，
仍然只有精确标题（+季号）才自动转存。

## 2026-10-18 隐藏链接补丁（1.6.70）

> 状态：已发布并核验 2026-10-18（`CloudSubscribeX_v1.6.70`，zip sha256 `cc6f1ca2…`）

用真实 TG 会话只读回放 `@QukanMovie` 最新 20 条消息，发现 `message.message`
里的链接只剩「点击跳转」四个字：真正的 115 分享地址在
`MessageEntityTextUrl.url`（或网页预览、内联按钮）里。旧逻辑只正则扫正文，
所以该频道 `added=0`，白名单自动转存永远不会触发。

1.6.70 新增 `extract_message_links()`：合并正文 URL、`message.entities`
（TextUrl/Url）、`media.webpage.url`、`reply_markup` 按钮 URL，再按原有网盘
域名表过滤。正文、实体、按钮三处重复链接自动去重。

## 2026-10-19 频道字段双层列表报错（1.6.71）

> 状态：已发布并核验 2026-10-19（`CloudSubscribeX_v1.6.71`，zip sha256 `862961f6…`）

线上日志出现：

```
06:20:40 tg_monitor.py - TG 频道监控（定时）无新增；
['https://t.me/+Jc37JCr1diEzNDMx']: 无法解析频道
（Cannot find any entity corresponding to "['https://t.me/+Jc37JCr1diEzNDMx']"）
```

根因：某个旧配置/设置页把频道字段存成列表，随后又被 `str()` 一次，变成
`"['https://t.me/+xxx']"`；旧 `normalize_channel` 先 `strip("[]")` 再
`strip("'\"")`，遇到外层还有引号时只剥掉一层，括号留在里面，Telethon 把整串
当成频道名。

1.6.71 改为 `_unwrap_channel_text()`：循环拆 JSON/Python 列表 + 最多 4 层引号，
取列表第一个有效频道，再走原有 `@name` / `t.me` / `-100` 归一化。真实配置
`tg_channel_rules` 不受影响。
