## 1. 背景

1.7.17 用「同一目标文件串行锁 + 同 SHA1 成功缓存 + 副本清理」压住了 E17 这一类重复，但它是**单点补丁**，不是系统性答案：

| 现状 | 证据 | 后果 |
| --- | --- | --- |
| 幂等只落在中继上传一个点 | `core/transfer.py:38-68`、`core/transfer.py:1277-1314` | 秒传、本地上传、后处理移动仍可能重复写目标 |
| 成功缓存只在进程内，TTL 30 分钟 | `_RELAY_TARGET_DONE`，`core/transfer.py:40-41` | 插件重启/多进程后缓存失效，同一文件可再次上传 |
| 锁键是「目录+文件名」，不含内容 | `_relay_target_lock_key`，`core/transfer.py:38-41` | 同名不同内容会互相排队；同名同内容跨路径/跨重启无法复用 |
| 状态分散在 history、offline pending、runtime task、内存 task | `handlers/sync/*`、`core/services/runtime.py` | 无法回答「这个文件现在到哪一步」，失败只能翻日志 |
| history/pending 保存是整表读-改-写 | `core/storage.py:102-122`、`core/database/repositories.py:183-208`、`:430-469` | 数据越大越慢；跨读改写有丢更新窗口，锁只保护单次保存 |
| 编排类职责过重 | `handlers/sync/service.py` 2961 行、`handlers/sync/postprocess.py` 2482 行、`core/transfer.py` 1989 行 | 事故修复只能继续在热点加分支，回归面越来越大 |

根因不是「锁不够多」，而是**没有一条持久化、可仲裁的「文件→目标」作业记录**。所有入口各自调用传输/后处理，正确性依赖调用顺序和进程内状态。

## 2. 决策

引入两层改造：

1. **持久化同步作业账本（`sync_jobs`）**：在产生任何云盘写操作之前，先写入一条带唯一幂等键的作业；作业状态是唯一事实来源，history 只是投影。
2. **统一目标写入器（`TargetWriter`）**：秒传、中继、本地上传、后处理移动全部走同一个目标提交入口；入口内部完成「查重 → 冲突决策 → 写入 → 校验 → 记账」。

核心原则：

- **先有意向，后有副作用**：没有 `sync_jobs` 记录，不允许写目标盘。
- **一个逻辑文件一个键**：键由「目标位置 + 目标文件名 + 内容身份」决定，不由入口、任务 ID 或进程决定。
- **至少一次执行 + 幂等副作用**：允许重试，但重复执行不能产生第二个文件。
- **状态迁移只能 CAS**：禁止业务代码直接改 `state` 字段。
- **不确定就降级为待处理**：查不到、校验失败、同名不同内容，一律 `needs_attention`，不伪装成功。

## 3. 数据模型

### 3.1 表 `sync_jobs`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `job_key` | TEXT PK | 幂等键，见 3.2 |
| `job_id` | TEXT UNIQUE | UUID，日志/历史/前端统一追踪号 |
| `content_key` | TEXT | `sha1:<hex>` / `md5:<hex>` / `id:<provider>:<file_id>:<size>` |

| `source_file_id` | TEXT | 源文件 ID（可为空） |
| `source_name` | TEXT | 源文件名 |

| `source_sha1` | TEXT | 可空 |
| `source_md5` | TEXT | 可空 |
| `target_provider` | TEXT | 目标盘标识 |
| `target_path` | TEXT | 规范化后的目标目录 |

索引：

- `(state, lease_until)`：worker 取任务/回收过期租约。
- `(target_provider, target_path, target_name)`：目标冲突排查。
- `(history_id)`：历史页反查。
- `(updated_at)`：保留期清理。

### 3.2 幂等键

```text
content_key =
  "sha1:" + lower(sha1)                  # 优先
  "md5:"  + lower(md5)                   # 次选
  "id:"   + provider + ":" + file_id + ":" + size   # 都没有时

job_key = sha256(
  target_provider + "\n" +
  normalize_path(target_path) + "\n" +
  normalize_name(target_name) + "\n" +
  content_key
)
```

`normalize_path`：NFC、去首尾空白、连续 `/` 折叠、去尾部 `/`、空值变 `/`。
`normalize_name`：NFC、去首尾空白，**不主动改大小写**；是否视为同名交给目标盘查重结果，避免本地规则把两个真实文件误合并。
不把 `source_provider` 放进键：同一内容从夸克或阿里云盘转到同一目标，仍然只应产生一个文件。

边界：

- 同一内容、不同目标文件名 → 不同作业（例如洗版改名），允许并存。
- 同一目标名、不同内容 → **不同 `job_key`**，但落在同一目标位置；由 `TargetWriter` 查同名文件后进入冲突决策，不自动覆盖。不能只靠键去重，键只负责「同一内容重复提交」。
- 目标文件名由重命名模板渲染；模板变化会产生新键。旧文件由后处理判重/洗版逻辑处理，不靠作业键清理。

### 3.3 状态机

```text
queued
  └─ claim ─> transferring
                ├─ 成功 ─> verifying
                │            ├─ 校验通过 ─> finalizing
                │            │                 ├─ 成功 ─> done
                │            │                 └─ 不可重试 ─> needs_attention
                │            └─ 校验失败 ─> retry_wait（可重试）
                └─ 可重试失败 ─> retry_wait ─> queued
                └─ 不可重试失败 ─> failed / needs_attention

任意非终态 ── 用户停止 ──> canceled
```

允许迁移（只允许这些）：

| from | to |
| --- | --- |
| `queued` | `transferring`, `canceled` |
| `transferring` | `verifying`, `retry_wait`, `failed`, `needs_attention`, `canceled` |
| `verifying` | `finalizing`, `retry_wait`, `needs_attention`, `canceled` |
| `finalizing` | `done`, `retry_wait`, `needs_attention`, `canceled` |
| `retry_wait` | `queued`, `failed`, `canceled` |

`failed` 与 `needs_attention` 的区别：

- `failed`：已达到 `max_attempts`，系统不再自动重试，但错误明确。
- `needs_attention`：状态不明确或需要人决策（同名不同内容、目标盘返回歧义、校验查不到），**不允许自动重试**，避免把错误放大。

### 3.4 租约与 CAS

claim 用条件更新，不用「先读后写」：

```sql
UPDATE sync_jobs
SET lease_owner = :owner,
    lease_until = :now + :ttl,
    attempt = attempt + 1,
    state = 'transferring',
    updated_at = :now
WHERE job_key = :key
  AND state IN ('queued', 'retry_wait')
  AND (lease_until IS NULL OR lease_until < :now);
```

- `rowcount == 1` 才算抢到；`0` 表示别人持有或状态已变，调用方转为等待/复用。
- 长任务每 15 秒心跳续租；worker 崩溃后租约到期，下一次 sweep 回收。
- 所有迁移都带 `WHERE state = :expected`，仓储层统一封装，业务层不写 SQL。
- 同一进程内保留 keyed lock 作为快路径，减少 SQLite 争用；**正确性只依赖数据库 CAS**，不依赖内存锁。

## 4. TargetWriter

### 4.1 接口

```python
@dataclass
class TargetPlan:
    target_provider: str
    target_path: str
    target_name: str
    content_key: str
    source: SourceRef
    conflict_policy: str  # skip | replace | suffix

class TargetWriter:
    def commit(self, plan: TargetPlan, artifact: Artifact) -> TargetResult: ...
```

`Artifact` 可以是本地临时文件，也可以是中继句柄；策略层不需要知道彼此存在。

### 4.2 commit 流程

1. **规范化**目标路径/文件名，计算 `job_key`。
2. **认领作业**：`claim_or_get(job_key)`。
   - 已 `done`：先按 `result_file_id` / 目标名查回；存在且大小匹配 → 返回复用，不写盘；查不到 → 说明结果已被人删/移走，重置为 `queued` 后重新执行（不新建键）。
   - 被他人持有 → 短轮询作业状态（100ms 起，指数退避，上限 2s），完成后复用；超时则返回「进行中」。
3. **查目标同名文件**：
   - 不存在 → 继续。
   - 存在且内容一致（sha1/md5/size 至少两项匹配）→ 记为 `existing`，直接 `done`。
   - 存在但内容不一致 → 按 `conflict_policy`：
     - `skip`（默认）：`needs_attention`，不覆盖。
     - `replace`：仅洗版/明确升级路径使用，先备份旧文件 ID 再写。
     - `suffix`：生成 `name (2).ext`，只用于用户显式允许的入口。
4. **选择策略**：`RapidStrategy` → `RelayStrategy` → `LocalUploadStrategy`。策略只负责「把字节放到目标」，不负责查重、命名、状态。
5. **校验**：按 `result_file_id` 或 `(path, name)` 查回文件；核对大小；有哈希则核对哈希。查不到 → `needs_attention`。
6. **记账**：写 `result_*`、`state=done`、`finished_at`；history 通过事件投影更新。
7. **失败**：可重试 → `retry_wait` + 退避；不可重试 → `failed` / `needs_attention`。禁止静默 `return None` 让上层猜。

### 4.3 覆盖范围

必须走 `TargetWriter` 的写操作（同步链路）：

- 秒传命中/未命中后的上传；
- 深圳中继上传；
- 本机回退上传；
- 跨盘暂存后的最终移动；
- 洗版替换（`replace` 策略）。

整理台批量改名/移动先复用同一套冲突决策（同名跳过、同内容复用、不同内容不覆盖），但执行器保持独立，不在 P2 强制改造范围。临时目录写入可以例外，但同步链路的最终落点必须过 `TargetWriter`。不允许在 handler 里直接调用 `upload_file` / `upload_progressive` / `relay.submit` 写最终目标。

## 5. 流程改造

### 5.1 入口统一

```text
cron / 手动同步 / TG 频道 / Webhook / 订阅事件
        │
        ▼
  SyncIntent（纯数据，不执行）
        │
        ▼
  enqueue_sync_job()  ── 写 sync_jobs（queued）
        │
        ▼
  worker claim ──> TargetWriter.commit ──> finalize ──> done
```

约束：

- 入口只做「识别 + 生成 intent」，不直接调用 transfer/postprocess。
- 同一 `job_key` 重复 enqueue 返回已有作业，不新建。
- 手动「立即重试」是把 `failed/needs_attention` 重置为 `queued` 并 `attempt=0`，不是绕过账本直接跑。

### 5.2 history 的定位

`history` 从「运行状态存储」降级为「展示投影」：

- 作业创建时写一条 `处理中` 记录，带 `job_id`。
- 状态迁移通过 `job_id` 更新对应记录；找不到就补建，不阻塞作业。
- 历史写入失败不回滚云盘操作，但必须记录 `history_sync_error`，由补偿任务重试。
- 不再用 history 的 `status` 推断「是否已转存」；判重先查 `sync_jobs`，history 只做展示和人工排查。

### 5.3 offline pending 的边界

磁力/离线下载继续用 `offline_pending_tasks` 管理「等下载完成」。下载完成后，每个输出文件生成一条 `sync_jobs`，再进入统一后处理。第一阶段不合并两张表，避免一次性改掉离线调度。

### 6.6 P2a 落地记录（2026-10-20）

- `SyncJobLedger.begin(..., verify_done=...)`：`done` 不再无条件复用，先回查目标文件。
- 回查结果是四态，不用布尔值掩盖查询失败：
  - `exists`：文件存在，大小/文件 ID 匹配 → 复用，不写盘；
  - `missing`：目录可读且确认文件不存在 → `done -> queued`，清空结果字段、`attempt=0`，本次请求继续 claim；
  - `mismatch`：同名文件存在但大小/文件 ID 不一致 → `done -> needs_attention`，不覆盖、不重传；
  - `unknown`：目录/列表查询失败 → 不复用也不重传，返回原因，避免把网络错误当成文件丢失。
- `SyncJobRepository.reopen_done()` 与 `transition(expected_updated_at=...)`：重开/转待处理都带 CAS，只有回查时看到的那条 `done` 记录未被别人改写才生效。
- `SyncHandler._verify_sync_job_result()`：用 `resolve_directory + list_directory` 精确列目录，不依赖可能返回空值的 `find_file`；`_transfer_file` 把该方法传给账本。
- 成功记账时清空 `last_error/last_error_at`，避免重开后成功仍显示旧错误。
- 已知边界：P1 的 `result_name` 记录的是期望名，不是目标盘实际改名后的名字；若 115 自动生成 `(1)`，回查会按期望名判断。P2b 由 `TargetWriter` 返回真实 `CloudFile` 后补上。
- 单测：`tests/test_sync_job_ledger.py` 30 passed、`tests/test_sync_transfer_ledger_wiring.py` 8 passed；全量 `pytest tests` 652 passed，仅 2 例既有 `p115client` 环境失败。证据见 [同步作业 done 回查单测](../test/2026-10-20-同步作业done回查单测.md)。

## 7. 验收

### 7.1 单测

- 键规范化：NFC、尾斜杠、连续斜杠、大小写、空路径。
- 同内容不同 `source_file_id` → 同键；同目标名不同内容 → 不同键。
- 状态机表驱动：允许的迁移全通过，禁止的迁移全部拒绝。
- CAS：两个线程同时 claim，只有一个 `rowcount=1`。
- 租约：持有者不续租，TTL 后可被回收；续租期间不可被抢。
- 冲突策略：`skip` 不覆盖、`replace` 先备份、`suffix` 生成合法文件名。
- 校验失败 → `needs_attention`，不写 `done`。
- history 投影失败不回滚作业，只记录补偿标记。

### 7.2 并发/故障注入

- 8 个线程同 `job_key` 同时提交：1 个真实上传，7 个复用，目标只有 1 个文件。
- 同目标名不同内容：1 个成功，其余按策略进入冲突，不产生 `(1)`。
- 上传成功后、记账前杀进程：重启后通过目标查回 + 哈希核对收敛为 `done`，不重复上传。
- claim 后杀进程：租约过期回收，重试不超过 `max_attempts`。
- SQLite `database is locked`：短事务 + busy_timeout 重试，不产生重复副作用。

### 7.3 真机 e2e

在 115 小目录复现 E17 场景：

1. 同一文件、同一目标名，两个 worker 同时中继。
2. 断言：目标目录只有 1 个文件，无 `(1)`，`sync_jobs` 只有 1 条 `done`。
3. 重启插件后再提交同一文件：直接复用，不再上传。
4. 手动停止/重试：状态正确，不产生孤儿文件。

## 8. 风险与取舍

| 风险 | 缓解 |
| --- | --- |
| SQLite 写争用 | 事务只包 CAS/结果写；心跳 15 秒一次；WAL + busy_timeout；不在事务里做网络请求 |
| 每阶段多一次 DB 写 | 可接受；相比重复文件/人工清理成本更低 |
| 模板改名导致新 job_key | 文档明确；旧文件由洗版/判重处理；不做自动删除 |
| 多实例共享同一 SQLite | 当前按单实例设计；如未来多容器，改用共享数据库或单写者服务，SQLite 文件不能跨机共享 |
| 作业表膨胀 | 终态保留期 + 定时清理；索引只保留查询必需的 |
| 旧路径绕过账本 | P2 后禁止 handler 直接写最终目标；加 lint/AST 检查上传调用点 |

## 9. 被否决的方案

- **加大全局锁**：牺牲所有并发，仍不解决进程重启和多实例；锁粒度越粗，死锁/排队越难查。
- **只把 `_RELAY_TARGET_DONE` 落盘**：能防重启，但只保护中继；本地上传、后处理移动仍可重复。
- **给 history 加唯一索引**：history 是事后记录，写入时云盘副作用已经发生，挡不住重复上传。
- **依赖 115 自动改名**：它会把重复变成 `(1)`，不是拒绝；这正是本次事故的表现。

## 11. 配套但不阻塞的改造

- **CI 收集缺口**：`.github/workflows/test-cloudsubscribex.yml:43` 用 `unittest discover`，仓库中 37 个顶层 `def test_` 不会被收集；迁移到 `pytest`，可选依赖用 `importorskip`。
- **可观测性**：所有日志带 `job_id`；指标至少 `sync_job_state_total`、`target_reuse_total`、`target_conflict_total`、`lease_reclaim_total`、`stage_duration_seconds`。
- **整理台 plan/execute**：先生成 `MovePlan`（源、目标、改名、跳过原因、清理范围），预览确认后按 `plan_id` 执行；空目录清理作为 plan 的一部分，避免直接扫源根。
- **postprocess 拆分**：先抽 `FinalizeTransaction`（prepare/commit/abort/compensate）和 `CloudMutationExecutor`，不做大爆炸重构。
