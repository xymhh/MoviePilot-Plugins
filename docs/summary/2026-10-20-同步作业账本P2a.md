# 同步作业账本 P2a：done 回查与重开（1.7.19）

> 状态：已完成并发布 2026-10-20（`f3ae6c3` / Release `CloudSubscribeX_v1.7.19`，CI 三绿）。设计见 [ADR](../plan/2026-10-20-同步作业状态机与幂等改造.md)。

## 做了什么

P1 的 `done` 复用只信任账本：文件被人从网盘删除后，再次提交会被当成已完成而直接跳过。P2a 把「复用」改成先回查目标文件：

| 回查结果 | 行为 |
| --- | --- |
| `exists` | 文件存在，大小/文件 ID 匹配 → 复用，不写盘 |
| `missing` | 目录可读且确认文件不存在 → `done -> queued`，清结果、`attempt=0`，本次继续转存 |
| `mismatch` | 同名文件大小/ID 不一致 → `done -> needs_attention`，不覆盖、不重传 |
| `unknown` | 目录/列表查询失败 → 既不复用也不重传，返回原因，避免把网络错误当文件丢失 |

关键实现：

- `SyncJobLedger.begin(..., verify_done=...)`：`done` 先回查，再决定复用/重开/待处理。
- `SyncJobResult`：只读快照，网络回查不持有 ORM 会话。
- `SyncJobRepository.reopen_done()`：`done -> queued`，清空 `result_*` 与 `finished_at`，`attempt=0`。
- `transition(expected_updated_at=...)`：重开/转待处理都带 CAS，旧观察不能改写别人刚完成的新结果。
- `SyncHandler._verify_sync_job_result()`：`resolve_directory + list_directory` 精确匹配，区分「空目录」与「查询失败」。
- 成功记账清空 `last_error/last_error_at`，避免重开后成功仍显示旧错误。

## 已知边界 / 下一步

- P1 的 `result_name` 是期望文件名，不是目标盘实际改名后的名字。若 115 自动生成 `(1)`，回查会按期望名判断；P2b 由 `TargetWriter` 返回真实 `CloudFile` 后补上。
- 尚无真实 115 删除/回查 e2e：需要升级 1.7.19 后，手动删除一个已完成任务的目标文件，再提交同一文件，确认账本从 done 重开并重新落盘。
- P2b 仍待做：中继/本地上传/最终移动统一走 `TargetWriter`，移除对 `_RELAY_TARGET_DONE` 的正确性依赖。
