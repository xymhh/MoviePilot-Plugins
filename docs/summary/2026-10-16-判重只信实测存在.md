# 1.6.51 复盘：判重只信「目标目录里有实物」

> 时间：2026-10-16｜版本：CloudSubscribeX 1.6.51｜关联：[计划](../plan/2026-10-16-判重只信实测存在.md)｜[单测证据](../test/2026-10-16-判重存在性校验单测.md)

## 一句话

用户的「缺集补不上」不是搜索问题，而是**判重采信了一条查无实据的历史记录**：跨盘转存留下「成功但没落盘」的假记录 → 写进 MP 整理历史 → 下一轮判重把它当已有版本 → 该集永远跳过。修法：历史版本必须能在目标目录里找到实物，否则按缺失处理；同时按用户要求保留人工兜底入口。

## 用户诉求与选择

1. 用户真机现象：跑完网盘里仍只有第 4 集，前 3 集没有（插件日志三集都是「按季集判重跳过」）。
2. 用户对修法的要求（原话）：「要健全代码的话，要留一条手动链路保底，完全依靠自动化难免会有问题。」
   → 所以这一版不是「让自动判重更聪明」了事，而是**自动判定收紧 + 人工入口补齐**两件事一起做。

## 做了什么

- 自动层：基线里的 `MoviePilot整理记录` / `插件转存记录` 条目必须能在目标季目录里找到同名文件、同 `file_id`，或该集在目录扫描里存在；记录指向**别的目录**（媒体库等）或**拿不到实测数据**时维持原口径。不通过 → 按缺失处理 + INFO 日志（季集/来源/文件名）。
- 手动层：历史页对「跨盘成功但查无落盘痕迹」（`cloud_dir` 空，或文件名没换成目标名）的记录开放「**重新转存此记录**」；连同已有的「删除记录」「手动同步」「关闭按季集判重」共四条兜底路径。
- 防复发：「跳过」合并**不再覆盖**成功记录的落盘字段，也**不再写进** MP 整理历史（假成功正是幻影来源）。

## 教训与决策记录

1. **「不可见的失败」比报错更贵**：假成功记录没有任何红字，表现只是「这集怎么都补不上」。凡「记录说成功」与「盘上有文件」是两个事实源，就必须交叉核验，否则错一次就永久错。
2. **回退姿态与修 bug 的取舍要写清**：拿不到实测数据（列目录失败）时保留旧口径 —— 宁可少补一次，也不要因为网络抖动把已存在的集重复转一遍（重复转存会真吃流量、真删旧文件）。
3. **手动链路要「可达」才算存在**：重转按钮本来就有，但「成功」记录被 `_history_retry_state` 一律拒掉，等于**用户看得见按钮却按不动**。设计保底入口时，验收标准是「用户能真的按下去并跑通」，不是「有这条代码」。
4. **修症状也要堵源头**：这次同时改了三处（判重校验 / 合并保护 / 平台历史写入）。只改判重校验能解掉当前现象，但假成功还会继续生产幻影记录。
5. **来源标记是判重的前提**：`_baseline_episode_versions` 原来把所有来源都标成 `插件基线`，丢了「这条来自整理历史还是媒体服务器」的信息 —— 没有来源就没法做分级信任，所以顺手把 `origin` 透传出来（用例 33 钉住）。
6. **用户是提醒者的角色**：他一句「完全依靠自动化难免会有问题」直接决定了本次方案形态；自动化越强的地方，越要在设计里显式留人工出口。
