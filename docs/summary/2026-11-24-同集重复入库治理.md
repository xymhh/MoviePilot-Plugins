# 同集重复入库治理（1.33.0）总结

> 任务书：[plan](../plan/2026-11-24-同集重复入库治理-任务书.md) ｜ 证据：[test](../test/2026-11-24-同集重复入库治理-验收.md)

## 起因

用户问「怎么一直在入库重复的媒体」。现网实测：85 组重复 .strm（48 组同集
两份不同视频、37 组同一视频两个 .strm、46 组至少一份已对不上 115 视频），
Emby 里 `无声的回响` 显示 `{1: [1,2,3,4,4,4,5,6]}`——E04 三个条目。

## 三个判断

1. **存量与新增要分开看**：85 组全部早于 1.31.0（同集兄弟清理 11-22 18:27
   才发），今天新写的 .strm 已经干净。但存量不会自愈——增量扫描对已存在
   文件直接跳过，兄弟清理只在「写新文件」时触发。所以补的是**存量清扫**，
   不是再改一次生成逻辑。
2. **「去重」有两条不同的边界**：入队去重管的是**在途**（queued/processing/
   failed），done 一释放键，同一集换个来源就能再入队并真实转存——实测
   S01E07 一小时内传了三次（4694MB + 4820MB + 272MB）。这不是 bug，是
   语义缺口：缺「最近已入库」这一维。
3. **删除要保守，跳过要激进**：自动删的东西只限「本地指针 + 115 已无对应
   视频」（纯垃圾），比例超阈值直接放弃；而「同集已有更大版本」只做
   **跳过上传**，绝不删云盘文件——删视频一律留给人工页。宁可留一份重复，
   不可误删一份正片。

## 交付

- A 陈旧 .strm 清扫（`sweep_orphan_strms`，样本 ≥20 时套 30% 安全阀，
  删除登记 Emby 屏蔽）。
- B 入队时间窗（`funnel_recent_done_window_hours` 默认 12h，0 关闭；
  洗版放行；落盘前实查仍是第二道防线）。
- C 上传前按同主干查重（同大小/更大 → reused；更小 → 只 warning）。
- 新增 11 条回归；全量 3000 passed，13 个存量失败与基线逐条一致；lint 0 error。

## 教训

「一直在发生」往往是两件事的叠加：**新产生的**（去重语义缺口）和
**没人清的存量**（只在写新文件时清理）。只看日志会以为前者是全部，
只看文件时间戳才知道后者才是大头——两个都要治，但治法是两种。
