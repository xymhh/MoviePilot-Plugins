# P115StrmHelper 生活事件监控「静默停摆」修复（2.8.78）

## 一、故障现象（真机，2026-10-13 ~ 10-14）

生活事件监控线程**静默停摆**：`is_alive()` 仍为 True，但不再拉取/处理 115 生活事件，且**一行日志都没有**，
持续 20 小时以上。后果：转存进媒体库的新文件长期没有 STRM，只能等次日 02:00/02:30 的全量同步兜底。

已独立复核的证据（均为只读，Asia/Shanghai）：

| 证据 | 结果 |
| --- | --- |
| 缺失 STRM（本地 `/strm/115网盘/剧集/国产剧`） | 死刑将至 E18、美人余 E09、喜剧之王 E17、雷霆令 E07、希望 (2026) 均缺 |
| 115 事件流里这些文件的事件 | **都在**（type=6 move_file：10-13 18:33~18:44、10-14 00:09），说明不是「无事件」 |
| 插件日志 10-13 12:35 → 10-14 07:00（5800+ 行） | `生活事件` **0 命中**（连线程启动行都没有） |
| MP 整理队列（00:2x、07:2x 两次查） | 均为空 ⇒ 不是「等整理队列」阻塞 |
| 02:30:58 全量同步 | 补上了 E18/E09；但 02:33:37 转存的美人余 E11/E12 **整晚没有 STRM**（同步已跑完，之后事件全漏） |

同形态故障 10-12 已出现过一次（清理线程曾卡在 115 请求上 5 小时 52 分）⇒ 属回归/长期缺陷，不是设计如此。

## 二、根因（代码级，可直接指出缺陷点）

1. `service/__init__.py` `check_monitor_life_guard()`（原 267-330 行）**只用 `is_alive()` 判活**，
   卡死线程被视为健康；且该函数所有分支都是 `logger.debug`（默认级别不可见）⇒ **静默**。
   卡死线程既不会被重启，也不会留下任何日志或通知。
2. 拉取循环 `helper/life/client.py` `once_pull()` 首行 `if self._wait_for_transfer_complete(): return`，
   整理队列长期非空时一直不拉取；`_pull_life_events()` 用 `list(iterator)` 一次性抽干事件，
   无进度心跳、无可见性；游标只在 `stop_event` 触发时持久化。
3. `monitor_life_first_pull_mode=latest`（线上现状）⇒ 线程重启从 `now` 起，**停机窗口内的事件永久丢失**。
4. 插件页自检接口 `check_life_event_status` 只看 `is_alive()` + 一个 `from_time=now` 的即时拉取
   ⇒ 永远「无新事件」，**假阴性**（本次排查中确实误导过一轮）。

真凶（卡在哪一行）**现场无法确定**：没有栈。因此本补丁的第一要务是「下次停摆能自动把栈打出来」。

## 四、关键设计决策：**不做截断**

任务书原本要求「单轮拉取上限」，实现时**主动改为只告警不截断**，理由：

115 生活事件接口的 `from_time` 是取值**下界**，迭代器按「新 → 旧」产出，而游标只能记住「本批最新一条」。
一旦截断，比截断点更旧、又没被取到的事件会落在游标之前，**永远不会再被拉取**（永久丢事件）。
因此上限只保留「条数异常偏高时记 WARNING」的告警语义，命名也从 `monitor_life_max_events_per_pull`
改为 `monitor_life_large_window_warn_events`，避免后来者误以为会截断。

## 六、遗留风险（如实）

1. **单条事件处理超过阈值（默认 15 分钟）仍会判停摆并回放重启**，可能重复处理已处理事件（下游 DB/STRM 幂等，代价是重复劳动）。任务书只豁免了整理等待。
2. **旧线程可能与新线程短暂并存**：停摆线程若 `join(25s)` 杀不掉，沿用现有行为置 `None` 再起新线程，两条线程会重复消费同一批事件（靠幂等收敛）。真正的解法是给线程加「代际令牌」，本版未做。
3. **看门狗关闭（阈值 0）或心跳从未打点时不判停摆**（没有证据不杀线程的设计取向）。
4. 前端配置页看不到 4 个新配置项（本仓库前端不随插件放开源改动）；要调参走 API 或配置文件。
5. 写放大：每轮（约 15 秒）一次游标 `save_plugin_data`。
6. 仍未定位「卡在哪一行」——2.8.78 上线后若再次停摆，插件日志里会有线程栈，届时可一次定案。

## 七、上线后怎么确认修好了

1. 插件页「生活事件状态检查」看「上次进度时间」应随新事件不断前进；出现「停摆分钟数」非 0 即为真阳性。
2. 转存新文件后 1 分钟内应出 STRM；跨轮询周期仍有缺，查日志里有无「停摆线程调用栈」。
3. 若日志出现 WARNING「判定为停摆」+ 调用栈 ⇒ 把它贴回来，即可定位真凶并做二次修复。
