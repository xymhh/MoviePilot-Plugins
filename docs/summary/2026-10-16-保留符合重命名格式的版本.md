# 1.6.50 复盘：判重时保留「已符合当前重命名格式」的现有版本

> 时间：2026-10-16｜版本：CloudSubscribeX 1.6.50｜关联：[计划](../plan/2026-10-16-保留符合重命名格式的版本.md)｜[单测证据](../test/2026-10-16-保留符合重命名格式的版本单测.md)

## 一句话

用户问「判重认集号是不是太绝对了，应该按现有重命名规则来保留吧」，答案分两半：
**判重的判据从来不是重命名模板**（模板变了照样判得出同一集），但**「谁该被替换」确实可以按现有重命名规则来定** —— 于是加了「名字已符合当前模板 → 保留」的门槛。

## 用户诉求与选择

1. 先纠正一个误解：1.6.48 的目录扫描不是「认第 1 集」，而是用 MP 自己的 MetaInfo 解析真实季集；「- 第 1 集」只是举例老命名也能认。
2. 用户选了 **B**：「已经按你新模板命名的规范版，被评分更高的候选替换掉」是问题 → **规范名版本直接保留**。

## 做了什么

`prefer_template_named_version`（默认开）：判定「是否替换现有版本」之前，先把现有文件名按当前重命名格式重新渲染一次（与转存落位同一套渲染），结果与原名一致 → 该集/该片保留，不转存、不删旧、不写新。

落点覆盖：剧集按季集判重、电影判重、电影洗版候选（预览 / Magnet / 正式）、下载后洗版、历史手动洗版（预览 + 正式）。

## 教训与决策记录

1. **「判据」和「谁被淘汰」是两件事**：判重键（季集身份）解决「这是不是同一集」；模板比对解决「两份里留哪份」。用户的原话把两者混在一起，先把前者讲清才问出后者。
2. **回退姿态要和用户预期同向**：渲染失败 → 回退评分逻辑（继续洗版），不是「拿不准就跳过」。因为「渲染失败」在真机上可能大面积发生（字段归一化差异），若失败即跳过会**悄悄冻掉整个洗版功能**，比误替换更难发现。
3. **测试桩的默认值要写清为什么**：旧桩 `_platform_rename_path` 是恒等的，若默认开新开关，全部旧用例都会被「误命中」而变绿/变红得莫名其妙 —— 所以测试里默认关，并在注释里写明理由。
4. **已知副作用要当面讲**：开这个开关后，插件自己写下的规范文件不再被更高评分的候选洗版（洗版对它们失效）。用户是知情的；想恢复 → 关开关。
5. **真机未验证的推断要标出来**：渲染幂等依赖 MP 对分辨率/编码/音轨字段的归一化口径，本地无 MP 运行时，只能靠日志 reason 文案在真机上验证（见单测文档第 4 节）。这是本次交付唯一的未验证点。
