# 2026-11-12 1.9.79 上传代理主路径补齐 — 复盘（定论）

## 1.9.78 漏了什么

1.9.78 把代理注入点定在「OSS 数据面」，方向对了，但**只覆盖了插件自己写的 `oss_multipart_*` 分片并发上传**。而线上 `p115oss` 走的是 `P115Client.upload_file` → `p115oss.upload_file`（单连接顺序上传），这条路同样用模块级 `request`，不传 `session` 就还是直连。

**一句话**：修对了机制，修漏了路径。改完必须核对「线上实际走哪条分支」，而不是「我改的那条分支」。

## 本次最严重的过程问题：残留 ACP 进程在改工作区

- 提交 1.9.78 后，工作区出现我**没有做过**的改动（版本变 1.9.79、`upload.py` 被改）。
- 排查：`ps aux | grep opencode` 发现**两个 `opencode acp` 进程**（04:06、05:23 启动），是我早前委派超时后未退出的会话，仍在后台写文件。
- 处理：`kill -TERM` 停止，确认 10 秒内 md5 稳定；逐行 diff 验收其改动后才采纳。
- **根因**：`delegate_external_agent` 报 "reached the preset max runtime" 时**只是中断了本次 turn，ACP 会话仍 open**。我后续没有 `action="close"`，进程就一直活着。
- **铁律**：委派超时后必须 ① `delegate_external_agent(action="status")` 看状态 ② 显式 `action="close"` ③ `ps aux | grep <runner>` 复查。否则后台 agent 会与主 agent 的编辑互相覆盖（本次我的 `edit_file` 直接报 "text to replace was not found"）。

## 测试写成「假通过」的教训

初版断言：

```python
splats = [kw for kw in call.keywords if kw.arg is None]
self.assertTrue(splats, "...")
```

只检查「存在 `**kwargs` 展开」。把 `dict(self._oss_proxy_kwargs(), max_retries=0)` 换成 `dict(max_retries=0)` 后，`**upload_kwargs` 这个 splat **仍然存在**，测试照样绿。

**修法**：回溯 splat 的来源 —— 收集函数内所有 `变量名 -> 赋值表达式`，`**upload_kwargs` 要能追到赋值里含 `_oss_proxy_kwargs`；`**dict(...)` 则直接看表达式源码。

**教训**：断言「语法结构存在」几乎总是不够的，必须断言「这个结构指向我要的东西」。**变异反证不是走流程，而是专门用来打穿这种假通过的。**

## 另一个 AST 陷阱

`self._rate_limited_call(self.client.upload_file, ...)` 里，`upload_file` 在**参数位置**，不是 `Call.func`。按 `func.attr == "upload_file"` 匹配得到 0 个结果。正确做法：遍历 `node.args` 与 `node.keywords[*].value` 找 `Attribute` 链。
