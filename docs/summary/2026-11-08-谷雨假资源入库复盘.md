# 谷雨（2026）假资源入库事故复盘

> 日期：2026-11-08 ｜ 影响：22 条脏历史 + 22 个 115 文件 + 22 个 STRM + Emby 22 集假条目

## 1. 现象

订阅《谷雨》(2026, TMDB 279155) 本应只有 8 集已播。2026-11-08 02:45 定时同步后：

- Emby item `687249` 显示 30 集，E09–E30 的 `RunTimeTicks` ≈ 60–85 秒；
- 115 媒体目录 `…/谷雨 (2026) {tmdb-279155}/Season 1` 多出 22 个 5.4–19 MB 的碎片；
- 订阅因 missing 22→0 被判定完成并移入历史，追更停止。

假资源来源：pansou 命中的夸克分享 `pan.quark.cn/s/5f03dca2b94f`，标题含「谷雨 完结」，实际是每集 60–85 秒的片段。

## 2. 根因（三道门同时缺位）

| 门 | 位置 | 缺失行为 |
| --- | --- | --- |
| 播出日期门 | `handlers/sync/television.py` | `air_date` 为 null 的集被当成「已播出」放行（谷雨 E11–E30 全是 null） |
| 体积门 | `handlers/sync/resources.py` | 首次转存完全不校验单集体积，碎片照收（`retry.py` 的 50MB 校验只在重试时生效） |
| 资源级门 | 全局 | 没有「文件数 > 总集数」这类整体异常告警 |

## 3. 处置

**A. 清理脏数据**（2026-11-08 08:00）

走插件自身的联动删除（等价于「从媒体库删掉」）：`POST /history/delete_batch` + `delete_linked_files=true`，22 条记录 / 22 个 115 文件（进回收站）/ 22 个 STRM。

> 备注：直接调 Emby `DELETE /Items/{id}` 需要用户会话，API key 认证报 `Value cannot be null. (Parameter 'user')`，因此改用插件联动删除 + 媒体库刷新，结果一致（Emby 条目随 STRM 消失）。

核验：

- Emby `Shows/687249/Episodes` → 8 集（E01–E08）
- 115 搜索「谷雨」→ 1 个目录 + 8 个视频文件
- 插件历史 → 8 条（E01–E08）

**B. 代码修复**

1. `television.py`：TMDB 没给播出日期的集一律按「未播出」处理；整季一条日期都没有（TMDB 无分集数据）时退回旧口径，避免整部剧永远卡在「缺集尚未播出」。
2. `resources.py`：新增 `MIN_EPISODE_BYTES = 100MB` 与 `_drop_undersized_media()`，在识别计划之前丢弃体积异常的视频文件；字幕/NFO/图片等非视频不受限，`size <= 0`（驱动不返回大小）不做判断；全部视频都被丢弃时记 skip 候选「视频体积异常」。

测试：`pytest tests` → 1357 passed，2 failed（`test_checkin_days.py` 两条 p115 签到用例，本机 Python 3.11 环境 import mock 问题，与本次改动无关）。

**C. 恢复订阅**

新建 MP 订阅 id `377`：谷雨 / 2026 / 电视剧 / tmdb 279155 / S01 / 起始集 9 / 总集数 30。

## 4. 遗留

- 代码修复需随版本发布（升版本 + 推 GitHub + 市场更新）才对线上生效；未更新前 10:30 的同步仍走旧逻辑。
- `retry.py` 的 50MB 匹配下限未动：它是「重试时匹配已有文件」的容忍阈值，语义与本次体积门不同。
