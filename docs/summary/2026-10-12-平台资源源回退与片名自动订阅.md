# 平台资源源方案回退 + 片名自动订阅（CloudSubscribe 1.6.26）

> 证据：[test/2026-10-12-片名自动订阅单测.md](../test/2026-10-12-片名自动订阅单测.md)、[test/2026-10-12-平台资源源单测.md](../test/2026-10-12-平台资源源单测.md)
> 被回退的方案：[plan/2026-10-12-MP平台资源源接入.md](../plan/2026-10-12-MP平台资源源接入.md)

## 结论

1.6.25 的「把网盘候选接进平台搜索」**整条回退**（用户判定方向错误），改做「**对话框直接发片名 → 自动建订阅 → 插件订阅接管接着干**」，随 1.6.26 发布。

## 为什么回退 1.6.25

| 方案 | 问题 |
| --- | --- |
| 1.6.25：插件实现 `search_torrents` 模块，把网盘候选以「网盘订阅助手｜xx」的名字塞进 MoviePilot 搜索结果，配合 `ResourceDownload` 接管把"下载"转成网盘转存 | ① 平台搜索是平台的语义，塞进去等于污染搜索结果，用户看到的是假种子条目；② 正确的链路本就存在——**建订阅**，让插件的订阅接管去搜网盘、转存、入库，不必借平台搜索的壳 |

用户原话（2026-10-12）：「不应该像站点搜索那样把网盘候选塞进 MP 搜索结果；正确链路＝输入片名 → 直接建订阅 → 插件订阅接管自然处理」。

## 1.6.26 做了什么

**回退（删除 1.6.25 的全部代码）**

- 删除 `core/hook/mp_module.py`（`MoviePilotSearchModule` / `search_torrents`）；
- 撤销 `core/hook/events.py` 的 `ResourceDownload` 下载接管；
- 撤销 `core/hook/__init__.py` 的模块导出、`core/services/platform.py` 为此加的 TMDB 身份回填；
- 撤销配置项 `mp_search_module_enabled` / `mp_search_module_limit`；
- 删除对应的 2 个测试文件；
- 平台搜索、平台下载路径与 1.6.24 完全一致。

**新功能：片名自动订阅（`title_subscribe_enabled`，默认开）**

- 复用已有的 `MessageRoutingHook`（已包装 `MessageChain._handle_message_core`，原用于消息里的网盘链接直达转存），在链接分支后追加片名分支；
- 片名 → `MetaInfo` + TMDB 识别 → 查重 → `SubscribeChain().add(...)` → `queue_subscribe_search(...)` → 回执；
- 已存在订阅则不发冗余通知，只触发一次搜索；
- 识别不出 / 非影视（闲聊、问句、命令、超长文本）原样交回平台，行为与旧版一致。

## 设计取舍

- **默认开**：用户明确要「输入片名直接就建订阅，不用再问」。守门规则（单行、≤40 字、无 `/`、无问号、无链接、必须有字母/汉字）用来挡掉闲聊与命令；识别不出就不接管，所以误建订阅的窗口很小。
- **消费消息（返回 True）**：既避免了平台再回一句「未搜索到资源」（用户当前 MP 未配置站点，搜索必然 0 命中），也避免同一片名产生两套动作。
- **立刻排队搜索**：不等平台定时订阅搜索，用户几秒内能看到结果——这也顺带绕开了 `takeover_new_subscribes` 默认关（新建订阅状态 `N` 平台不接管）这个坑。
- **不改搜索/下载**：这次把插件对平台的影响面收回到「消息一条 + 订阅一条」。

## 教训

1. **借平台的壳要慎之又慎**：把第三方资源伪装成平台的搜索结果，短期能"用"，长期是给用户的界面里塞假数据；用户的判断是对的。
2. **先看有没有原生链路**：插件本来就接管订阅搜索，"建订阅"这一步就是全部缺的东西，加一层平台搜索纯属多余。
3. **回退要干净**：删码、删配置项、删测试、改 README 索引与文档，一并做完（`git revert` 后逐项核对 `grep -rn mp_search_module` 无残留）。

## 2026-10-12 追加：1.6.27 方案 A（后置接入）的决策与代价

**决策**：1.6.26 的「发片名即识别即建订阅」被用户否决 —— 同名片名（不同年份/翻拍/不同季）时会替用户选错。用户选择**方案 A**：平台先出候选列表 → 用户点选 → 插件在该次真实搜索上接入订阅。

**落地**：片名消息改成「只登记不消费」（新模块 `core/pending_titles.py`，TTL 15 分钟、命中即消费、最多 64 条），接管点挪到已有的 SearchChain 搜索拦截（`SubscriptionSearchHook._dispatch_pending_title_search`），匹配只认「归一化后完全同名」或「TMDB ID 完全相同」，类型冲突（movie vs tv）直接跳过。命中后复用 1.6.26 的下游（查重 → 建订 `message=False`/`exist_ok=True` → `queue_subscribe_search` → 回执），回执文案改为「已按你在平台候选中选定的《xx》创建订阅」。只有媒体身份没有片名的搜索（`search_by_id`）走后台识别兜底，绝不阻塞搜索调用。

**已知代价（用户明确接受）**：站点搜索仍被插件阻止，所以平台那半句「未搜索到资源」会与插件回执同时出现 —— 这是方案 A 相对方案 B（连选择回调一起接管）的取舍：B 无多余台词，但要多做半天且要接管平台的 callback 交互，风险大。

**教训 / 判断依据**：

1. **「自动化程度」不是越高越好**：凡是要替用户做二选一（哪一部、哪一季）的地方，先让平台的既有交互完成确认，插件只在确认后的那次动作上接力。这次两版（1.6.26 直接建 / 1.6.27 选定后建）差别就在这一句「谁来做选择」。
2. **匹配规则宁漏不误**：只做「完全同名 / 身份完全一致」，不做包含、不做模糊。漏了用户会再搜一次，误建会污染订阅列表且需要人工清理 —— 后者的代价高得多。
3. **拦截点要选在平台自己会走的路由里**：这次没有新增任何 MP 侧入口（1.6.25 那套 `search_torrents` 模块已被判错并整条删除），只复用已存在的搜索拦截，改动的爆炸半径最小。
4. **拦截不能阻塞平台调用**：`search_by_*` 既有 sync 也有 async/stream，重活（TMDB 识别、建订阅）一律丢后台线程，包装器只做「解析参数 → 匹配 → 触发」。
5. **测试互不污染**：全量跑时别的测试会把 `cloudsubscribe.core.media` 注册成 mock，本次把 TMDB ID 读取抽成 `_tmdb_id_of()`/`_is_tmdb_source()` 供打桩，避免新测试依赖真实兼容层、也避免自己的 `load_module` 反过来污染别人。

## 2026-10-12 追加：1.6.28 复盘（钩子挂错位置 + 匹配过严）

**现象**：1.6.27 装好后，用户发「机智医生生活」→ 平台给出候选 → 点选 → 既不建订阅、也没有任何插件回执（平台只回「未搜索到需要的资源！」）。

**根因**（两条同时成立）：

1. 点选走 `InteractionChain._search_media_resources → SearchChain.process`，1.6.27 只挂了 `search_by_id/search_by_title` 一族 → 插件根本没被调用。
2. 就算被调用，`consume()` 只认完全同名 / TMDB 身份相同，而用户输入与官方名差一个字、登记时 TMDB 又识别失败 → 永远不相等。

**教训（对上面第 2 条「宁漏不误」的修订）**：

1. **「钩子挂上了」≠「路径覆盖到了」**：这次不是逻辑错，是**路由猜错**。凡涉及「用户在平台上做出的选择」，先读平台源码确认它最终落到哪个方法（这次是 `interaction.py:605`），再决定挂哪里；只凭「哪几个方法名字像搜索」挂钩子不可靠。
2. **宁漏不误，但要给「漏」留一条有界的窄缝**：1.6.27 的「完全同名」把用户唯一的真实用例漏掉了。1.6.28 补的是有界模糊（≥0.85、片名 ≥3 字、类型必须相容），不是无界兜底 —— 先试做的「窗口内唯一记录也算命中」被既有单测当场否掉（`test_unrelated_search_keeps_record` 失败：它会消费无关搜索的记录，正是当初要避免的误建）。**放宽匹配时必须让既有反例单测来否决方案，而不是靠感觉。**
3. **能在同一版里还掉的代价就还掉**：1.6.27 明说了「用户会多看到一句平台『未搜索到资源』」；把接管点挪到点选真正的入口后它自然消失 —— 说明那句话的根源就是当初挂错了位置。
4. **`process` 是公共入口**：订阅搜索、扫描等都会调它，所以 1.6.28 的 `process` 包装器用 pending 语义 —— **只有真消费到片名候选才拦**，否则原样透传，把爆炸半径压到最小。
5. **平台侧私有方法也要设兜底**：`InteractionChain._search_media_resources` 是私有方法，未来版本可能改名；安装时若取不到就只记一条 warning 并跳过，主链路（`process` 系列 pending 包装器）仍然生效。

## 2026-10-13 追加：1.6.33 复盘（点选即接入 —— 匹配再放宽一格，但只放宽点选这一条路）

**背景**：1.6.28 之后用户又撞了一次同样的墙 —— 发「画江湖」→ 平台出候选 → 点选「画江湖之不良人 (2014)」→ 既不建订阅、也没有插件回执，只剩平台「未搜索到需要的资源！」。用户明确表态：**「我需要的是你根据选中的选项信息来添加订阅」**（订阅按点选项建，别再拿片名去比）。

**根因**（与 1.6.28 同源，但这次落在「登记侧」而不是「挂接侧」）：

1. 纯片名消息只登记不过滤，登记记录要靠后台 TMDB 识别补身份；「画江湖」这条**识别失败**（记录 `tmdbid` 为空、`title` 仍是原文），于是身份级匹配永远不可能命中。
2. 点选后平台给出的正式名是「画江湖之不良人」，与登记名「画江湖」既不相等、相似度 0.6 也够不到 0.85 的模糊阈值（`core/pending_titles.py` 的 `FUZZY_MIN_RATIO`）→ 三级匹配全落空。
3. 记录不被消费 ⇒ 插件静默退出；而平台搜索此时又被接管 ⇒ 用户看到的就是「点了没反应 + 未搜索到」。

**改动**：在点选接入器（`InteractionChain._search_media_resources` 的包装器）这条路径上加第四级兜底 `allow_sole`：**只要登记表里还有类型相容的记录，就用最近一条接入**。订阅本身仍按点选项自带的 TMDB 身份/片名建，登记记录只决定「回执发给哪个渠道」。

**为什么这次敢放宽（以及为什么只在这一条路上放宽）**：

1. **触发者是用户的一次明确点击**，不是后台搜索 —— 语义上「我点了它」已经等价于「我要它」。1.6.28 那次否决「窗口内唯一记录也算命中」，是因为它作用在同步/异步/stream 搜索入口上，会把**无关搜索**的记录吃掉（`test_unrelated_search_keeps_record` 直接否定）；同样的兜底放在点选入口上，被吃掉的记录恰好就是用户点选的那一次意图。
2. **公共入口保持原样**：`process` 系列（订阅搜索、扫描都走）沿用严格匹配，`allow_sole` 默认 `False` —— 新增守用例 `test_process_wrapper_keeps_record_without_title_match` 钉住这一点。
3. **兜底自身有界**：必须有身份信号（片名或 TMDB，否则 `consume` 直接返回 `None`）、必须类型相容（movie/tv 不串台）、必须在 15 分钟 TTL 内、只能消费一条，并记录 `match=sole` 与 `match_candidates`（同表还有几条未消费）留日志。

**代价 / 已知边界**：

- 多条登记挂起时取**最近一条**（用户点选通常紧跟最后那条登记）。若用户连发两个片名再点选第一个的候选，会接到最近那条 —— 此时日志的 `登记表共 N 条未消费` 是唯一线索；真要严格对号入座，还是得点选后重发一次片名。
- 点选接入器是平台私有方法（`_search_media_resources`），未来改名会导致这条兜底失效；安装时取不到只记 warning，主链路（`process` 系列 strict 匹配）仍在。

**教训**：

1. **「点选是明确的用户动作」是可以被利用的信号** —— 之前的「宁漏不误」把点选和后台搜索一视同仁了；正确的做法是**按触发者区分严格度**，而不是全局收紧或全局放宽。
2. **登记侧的识别失败是隐藏杀手**：把「登记名」当选定的唯一凭据，就等于把成败押在后台 TMDB 识别上。识别失败的记录应当在消费时留一条明确日志（本次加了「点选候选未接上片名登记（titles=… / tmdbid=…），登记保留待过期」），否则用户报「没反应」时无迹可查。
