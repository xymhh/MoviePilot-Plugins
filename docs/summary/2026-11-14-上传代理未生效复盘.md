# 2026-11-14 上传代理未生效 — 复盘（定论）

## 结论

代理**从未生效**，不是「有时生效有时不生效」。1.9.78 的 OSS 注入方案是对的，1.9.79 补主路径也是对的，
**但地址取错了对象**，所以整条链路静默直连。

## 根因：对象链断裂

```
P115UploadService(OwnerDelegator)
  _owner → P115ClientManager          ← 不是插件实例
             __getattr__ → resolve_component(self, _COMPONENT_TYPES, ...)
                            ← 只找职责组件，不转发插件属性
```

`getattr(self._owner, "_cross_transfer_upload_proxy", "")` 恒为空串 → `oss_request_kwargs("")` → `{}`。
而 `P115ClientManager` 明明在 `create_client` 时已经把 `normalize_proxies(...)` 存进 `_upload_proxies` ——
**数据就在手边，只是读错了地方**。

## 为什么连续三轮「验证通过」却是假的

1. **1.9.76**：包装 `self.request` 后打了「已生效」日志 —— 真机无效（p115client 走模块级 request）。**假日志**。
2. **1.9.78**：注入点找对了（`session=ProxyManager`），但我核验的是「代码里有 `**proxy_kwargs`」和「本地能造出 ProxyManager」，**没有验证 owner 上真的能取到代理地址**。
3. **1.9.79**：补 `p115oss.upload_file` 主路径，同样只验证「参数传了」，没验证「值非空」。
4. **测试**：`test_upload_proxy_1_9_78.py` 注入的 owner 是 `SimpleNamespace(_cross_transfer_upload_proxy=...)` —— **假对象恰好带这个属性**，所以测试永远绿。真实 `P115ClientManager` 没有这个属性。

**教训（最重要的一条）**：验证「参数被传下去」不等于验证「参数有值」。
跨对象边界取值时，必须用**真实类**跑一遍取值链路，或者显式断言「真实 owner 上这个属性不存在」——
本次修复里我加了这条反证测试（`test_manager_regression_old_read_path_returns_empty`），就是为了让这个坑不再复发。

## 另一条教训：假日志比没日志更糟

1.9.76 那句「115 上传代理已生效」让用户以为已经修好，实际完全没生效，还浪费了两轮排查。
现在改为「115 上传数据面已启用代理（…）：<url>」，并且只在**真正拿到 session** 时打一次 —— 日志与事实绑定。

## 现场核对方法（以后照这个做）

1. 配置层：`GET /api/v1/plugin/CloudSubscribeX` 看 `cross_transfer_upload_proxy` 是否非空。
2. 生效层：mihomo `/connections` 里是否有来自 `172.18.0.5` 的连接（**对端视角**，不是自己打的日志）。
3. 日志层：搜「数据面已启用代理」；**没有这行 = 没生效**，不要看别处。
4. 三层任一不满足就继续查，不要凭单层结论收工。

## 附带处理

- `package.v2.json` 写坏（note 含裸双引号）→ 用 `json.dumps` 重新生成 + `json.loads` 验证。

  已第二次踩到（上次是 1.9.79），规则固定为：委派超时后 `status` → `close` → `ps aux | grep <runner>`。
