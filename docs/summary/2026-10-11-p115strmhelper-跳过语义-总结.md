## 1. 问题（用户视角）

MoviePilot V3 上，115 整理命中「媒体库已存在同名且质量更好（体积不小于源文件）的文件」时，插件把这条裁决
写进了**失败通道**：`task_failures` → `_record_fail()` → `add_transfer_fail()`。后果有三层：

1. 历史表 `ux_transferhistory_src_storage(src, src_storage)` 唯一索引会把**同源原有成功记录 replace 成失败记录** → 该路径长期停在「失败/未入库」；
2. 每次整理事件都会重试这条注定失败的裁决，反复打扰；
3. 推送失败通知，与真实语义（本就不该覆盖）不符。

宿主 MoviePilot V3 自己是有「覆盖跳过」语义的（`_is_overwrite_declined` + settlement 里不写失败记录、不通知、不重试），插件的接管路径没有沿用。

## 2. 决策与实现

- 用户选定**方案 1**：不留任何失败记录（保留原成功记录），并**删除低质量源文件**。
- 实施：把两处跳过裁决改走新的 `task_skips` 通道；`_batch_move_or_copy` / `batch_move_or_copy` 返回值
  `(失败, 跳过, 成功)`；新增 `_batch_record_skips` / `_record_skip`（不写历史、不发 `TransferFailed`、不登记智能体重试，
  仅日志 + 插件通知 + 源文件删除）。
- **主 agent 复核时的收紧（实施方初稿没有区分）**：删除源文件只对「媒体库存在同名文件，且质量更好」这一原因生效；
  `覆盖模式=never` 与第三方插件拒绝覆盖的跳过**保留源文件**——这两种情况无法确认库内更优，删源有丢失更好版本的风险，
  属不可逆破坏，宁可少删。该收紧已补 1 条断言（`test_never_mode_keeps_source_file`）。
- 交付方式：fork 一个私有可控仓库 → 走仓库自带的 CI/Release 工作流出包 → 用户插件市场按仓库地址更新。

## 4. 教训 / 值得记住

1. **「跳过」不是「失败」**：接入宿主链路的插件，凡是「按策略不处理」的裁决都不要塞进失败通道——失败记录会影响历史表、
   重试与通知三条链路，而 V3 的失败记录表对同源路径有唯一索引，会把成功记录顶掉。
2. **破坏性动作要按原因收窄**：初稿把所有跳过原因都当「库内更优」删源文件；`never` 模式只表示"不覆盖"，
   不代表"库里更好"，此时删源等于丢数据。删除条件必须绑定到唯一能证明「库内不劣」的那个原因。
3. **fork 仓库的工作流默认不跑**：fork 后需先启用 Actions 权限（API `PUT actions/permissions {"enabled":true}`
   或网页点一次），再触发工作流；本次用 `workflow_dispatch` 手动跑通，后续 push 会自动触发。
4. 委派外部 runner 时，**行号级任务书有效**（初稿一次成型、结构正确），但**语义边界仍需主 agent 复核**——
   本次的价值增量全部来自「删除条件收窄」这一处复核。
