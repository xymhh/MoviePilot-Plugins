# 复盘：插件 ID 独立化（CloudSubscribe → CloudSubscribeX，1.6.49）

> 计划：[../plan/2026-10-16-插件ID独立化.md](../plan/2026-10-16-插件ID独立化.md) ·
> 验收证据：[../test/2026-10-16-插件ID独立化验收.md](../test/2026-10-16-插件ID独立化验收.md)

## 一句话

本 fork 与上游 odomu 共用插件 ID `CloudSubscribe`，MP 市场「同 ID 只留最高版本」→ 上游一发新版就把本 fork 顶掉；
1.6.49 起改用独立 ID `CloudSubscribeX`（显示名「网盘订阅助手（跨盘优化版）」，作者 `xymhh（基于 odomu）`），
并实现**首次启动自动从旧 ID 迁移配置/数据/私有库**，用户切换零手工搬运。

## 为什么必须改 ID（而不是改显示名/作者）

- MP 市场列表按插件 ID 去重，只保留最高版本（v3 `app/application/plugin/catalog.py:343-401`）。
  fork 与上游同 ID ⇒ 用户的更新入口永远指向「最新的那条」，本 fork 的改动随时被覆盖。
- 实测（2026-10-16 之前）：MP 市场里两条 CloudSubscribe，本 fork `1.6.48`（已装）+ 上游 `1.7.x`，
  用户点更新即被顶成上游版本。

## 关键发现（决定了迁移方案不能「只改目录名」）

1. **配置不在文件里**：MP v3 的插件配置存在宿主数据库 `PluginInstance.config_data`（`app/db/oper/plugininstance.py:244`），
   不是 `config/plugins/<id>/config.json`。所以「把配置目录改个名」搬不走配置。
2. **插件键值数据在宿主主库表 `PluginData`**（按 `plugin_id` 索引），SDK `get_data/save_data(plugin_id=...)`
   可以跨 ID 读写且**没有 ACL** ⇒ 插件自己能迁移；反过来，MP 的公开 API 只能**读**插件数据
   （`GET /api/v1/plugin/runtime/{id}/data`），不能写 ⇒ 外部脚本迁移数据这条路走不通。
3. **私有 SQLite 在插件数据目录**：`config/plugins/<插件类名>/cloudsubscribe.db`（`core/storage.py` 用 `owner.get_data_path()`）。
   宿主加载时会把类名改写成实例 ID（`loader.py:476`），所以 ID 改后目录名自动跟随。
4. **前端产物按 ID 小写取**：`/plugin/file/<plugin_id.lower()>/<dist>/remoteEntry.js`（`paths.py:81`），
   且 CI 的 release 工作流用 `package.v2.json` 的键算出 `backend_path = id.lower()` 去找 `frontend/<backend_path>`
   ⇒ 目录改名必须**后端目录 + 前端目录 + vite outDir/federation name + 前端代码里的 id 串**一起改，缺一处就白屏。
5. 目录名必须是**插件 ID 全小写**（`package.py:230-236`），所以 `plugins.v2/cloudsubscribex`。

## 迁移设计取舍

- **执行时机在 `init_plugin` 最前**：早于 `initialize()` 建库，否则新库文件已存在会让「复制旧库」被跳过（丢订阅/历史）。
- **只复制、不移动、不删除**旧 ID 的数据：用户可能回退，删了就没退路。
- **迁移后 `enabled` 强制 False**：迁移发生时旧插件大概率还在跑，两个插件同时转存会互相踩
  （同一集重复转存、互删中继文件——正是 1.6.47 修的坑）。宁可让用户多点一次「启用」，也不要制造双写。
- **留痕键 `legacy_id_migration`**：既能阻止二次回灌（用户此后清空配置属主动重置），
  也是事后排查「到底迁没迁、迁了多少」的事实记录。
- **目标库非空不覆盖**：本插件的库一旦建好就以它为准；只对「0 字节空文件」（宿主提前 connect 建过）例外。
- **数据形态双兼容**：宿主新版 `get_data(plugin_id=...)` 返回 ORM 行列表（`.key`/`.value`），
  旧版返回 dict —— `_data_items` 两种都归一化，避免 SDK 版本差异导致静默漏搬。
- **迁移逻辑放 `core/legacy_migration.py` 而不是塞 `__init__.py`**：`__init__.py` 加载依赖一大堆宿主模块，
  测试里无法轻量加载；拆出来后 13 例单测用宿主桩跑，秒级、可变异反证。

## 踩坑记录

- **批次 sed 误伤内部契约**：把测试里断言插件内部分支标记的 `__cloudsubscribe_owner__` 一起改成了
  `__cloudsubscribex_owner__`，被 `test_interaction_hook_binds_renamed_platform_class` 抓住。
  教训：改 ID 时**只改模块名与路径**，`plugin_config_prefix`、数据键、线程名、内部标记一律不动；
  第一版勘察用的 `grep | head -25` 截断把 `cloudsubscribe_owner__` 这类键漏出了视野（它排在长列表后面），
  靠全量测试兜住了。
- **vite `outDir` 与 federation `name` 必须一起改**：CI 构建时才知道，若不改会产出旧 ID 的 remoteEntry → 插件页加载失败。
- **Release 资产名与 tag 都由 `package.v2.json` 的键推导**（`get_plugin_meta.py`），键一改 tag 变 `CloudSubscribeX_v1.6.49`、
  资产变 `cloudsubscribex_v1.6.49.zip`；历史 release（`CloudSubscribe_v1.6.48` 及更早）仍在，可回退。

## 遗留与后续

- **旧 ID 插件仍是上游的入口**：本 fork 不再发布 `CloudSubscribe` 这个 ID 的新版本；
  MP 市场里那一条会显示为上游的 1.7.x（与 1.6.48 状态一致）。用户按 README 步骤切换即可。
- **迁移是「单跳」的**：`legacy_plugin_id` 硬编码 `CloudSubscribe`。若将来再改 ID，需在新 ID 里加一跳
  （或把 `legacy_plugin_id` 改成列表）。
- **未做**：迁移进度提示/失败重试入口（当前是日志 + 留痕键，失败时重载插件即可重试）。
- 用户真机验收清单见验收文档第 6 节，尚未回报。
