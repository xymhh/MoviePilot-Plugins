# 复盘：洗版「媒体服务器内容」永远 0 条（1.6.53）

## 现象

用户反馈：插件「洗版 → 媒体服务器内容」搜索任何片子都返回「已读取 0 个媒体库内容」，但 Emby 里明明有（如《美人余》，`/api/v1/mediaserver/exists` 能查到 `item_id=655616`）。

## 排查过程（关键一步）

1. 先按最直觉的假设修：`local_resource_path` 由 `/downloads` 改成 `/strm/115网盘` —— 用户改完**仍然 0 条**。
2. 于是不再猜，找一个**只读**出口把 MP 库里的真实数据取出来：插件自己的 `/resource/detail`（POST，只读）返回的 `library_items` 里带**条目真实路径**：

   ```
   {"item_id":"655616","item_type":"电视剧","media_type":"tv",
    "path":"/media/strm/115网盘/剧集/国产剧/美人余 (2026) {tmdb-294446}"}
   ```

   一眼看出：**Emby 容器挂 `/media/strm`，MP 容器挂 `/strm`**，同一份数据两个前缀。TMDB 身份（`media_source`/`media_id`）完全正常。

## 根因

- `_configured_media_path()` 要求条目路径**字面量**落在 `local_resource_path` 之下，不做前缀翻译 → 抛 `ValueError`；
- 调用方逐条 `continue`，**既不打日志也不上报** → 前端只能显示「0 条」。**两次排错成本都花在「静默」上，而不是根因本身**。

## 修复（1.6.53）

1. `_configured_media_path` 解析顺序：原样命中 → 显式映射 `media_server_path_mappings` → **尾部对齐兜底**（逐级丢前缀段，落 root 下且必须真实存在；命中打 INFO 日志）。两条安全边界不放宽：必须在 root 之下、结果必须存在；尾部对齐**严格**落在 root 之下（退化成 root 本身不算命中）。
2. 搜索返回新增 `diagnostics`（matched / dropped_no_identity / dropped_path / root / mappings），0 条且被路径挡掉时给出**可执行**提示（直接告诉用户填 `/media/strm=/strm`），前端复用现有提示位展示。

## 教训

- **静默丢弃是排错成本的最大来源**：凡是「遍历 + continue」的过滤，必须留计数与首个样本，否则用户只会看到「0 条」，而排查要花掉一整轮对话。
- **先取证再改配置**：这次真正的突破口是找到一个只读接口把库里的**原始字段**（尤其路径）打出来，而不是继续按直觉改配置。
- 同类隐患：`/resource/detail` 的 `library_items` 是最好的只读取数入口，以后遇到「媒体库对不上」优先用它。
