# 金银岛卡后处理复盘（1.7.37）

> 状态：已修复并上线 2026-10-24

## 现象

订阅 160「金银岛」卡片长时间停在 `postprocessing` / progress 95% /
`postprocess_file_completed: 1/2`，提示「文件：金银岛 - S01E02.mp4；约 59 秒后复查」，
十几分钟不结束。

## 根因（两层，均已实测确认）

### 1. canceled 是死终态，挡住重新转存

- 15:13:31 用户点停止 → `sync_jobs` 两条记录 `state=canceled`（`last_error=用户停止`，
  `attempt=1/3`，`target_name` 分别是 `金银岛 - S01E01/E02 - 第N集.mkv`）。
- 15:47 重新同步时 `claim()` 只认 `queued/retry_wait`，日志：
  `同步作业未认领，跳过本次转存…原因=作业由其他 worker 持有或已终止：canceled`。
- 结果：同一 `job_key` 永远认领不到，该文件永久转不进来，而 `attempt` 还剩 2 次。

### 2. 历史终态写不进去 → 每 60 秒重排队

- `pending` 项的 `file_name` 是 `金银岛 - S01E02.mp4`（上游资源名），而平台侧历史是
  `金银岛 - S01E02 - 第 2 集.mkv`。
- `_mark_offline_history_status_batch` 只按 `finalize_key`、share_url 或
  `(file_name, cloud_dir)` 精确匹配 → 全部落空 → `_resolve_history_record` 返回 False
  → `history_resync_count` 每次 +1、`next_check_at = now+60`，要 10 次才强制结算。
- 实测：15:47 起 `history_resync_count` 1→4→6，UI 上表现为「卡住」十几分钟。

## 修复（1.7.37，commit ed3690b）

1. `sync_job_state.py`：新增迁移 `canceled -> queued`。
2. `sync_jobs.reopen_canceled()`：重开时 `attempt=0`、清 finished_at/租约/last_error。
3. `sync_job_ledger.acquire()`：认领失败且状态为 canceled → 自动重开并重试认领一次。
4. `history._mark_offline_history_status_batch()`：新增「目标目录 + 季集号」兜底匹配。
5. `postprocess._HISTORY_RESYNC_MAX_AGE_SECONDS = 1800`：重排队加墙钟上限，到点强制结算。

测试：709 passed / 1 例预存在失败（`test_tg_monitor` 邀请链接用例）。

## 线上验收

- 部署 1.7.37 并 reload：`plugin_version=1.7.37`、`state=True`、`runtime_status=active`。
- 卡住的 pending 项 **PENDING COUNT 0**，`/runtime` 任务列表为空 → 卡片收敛。
- Emby 媒体库 `金银岛 (2026) S01` 实际已有 `{1: [1, 2]}` —— S01E02 **本身早已落地**，
  卡住的只是插件的后处理记录收敛（不是文件没转存）。
- 手动触发订阅 160 同步：`共转存 0 个文件` / `跳过未播出剧集：E03-E06` → 无缺集。

## 教训

- 「终态」不一定是业务的终态：用户主动停止只是否掉这一次，不是否掉这个文件。
- 写死「文件名精确匹配」在平台侧会改名（集名后缀、编码后缀）时必然失败，要带
  语义维度（目录 + 季 + 集）兜底。
- 任何「重排队」都必须有墙钟上限，否则次数上限 10 × 60 秒 = UI 卡 10 分钟。
