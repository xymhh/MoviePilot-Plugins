# Dian115 签到「幸运转盘」从不执行 — 复盘（1.6.36）

- 日期：2026-10-13
- 现象：插件里 Dian115 渠道的「启用幸运转盘」已经打开、每日目标 20 次，但签到记录里转盘永远是空，转盘一次都没跑
- 结论：**配置接线断在客户端创建处**，与站点、账号、积分、权限都无关

## 1. 现象与证据（线上实测，非推断）

| 证据 | 内容 |
| --- | --- |
| 插件配置（`GET /api/v1/plugin/CloudSubscribe`） | `dian115_checkin_enabled=True`、`dian115_lottery_enabled=True`、`dian115_lottery_count=20` |
| 签到历史（`.../checkin/dian115/history`） | 4 条记录，`lottery_target_count` / `lottery_executed` **全为 null** |
| 插件日志（2026-10-13 08:00:36） | `Dian115 签到结果：模式=normal，状态=签到完成，积分变化=4，消息=签到 +4`（没有「转盘 x/y」） |
| 线上代码 vs 本地仓库 | `search/dian115/client.py` md5 完全一致 → 不是「线上版本太旧」 |

## 2. 根因链路

签到链路取客户端的路径是 `core/services/checkin.py::_resolve_client()` → 搜索 Provider 的
`SearchCapability.CHECKIN` → `provider.py:8 create_dian115_provider()` 里的 `service.get_client()`。

1. `search/dian115/service.py` 的 `_get_dian115_resources()` **自己 new 客户端**，构造参数里只有
   email/password/proxy/请求间隔/解锁频率，**没有 `lottery_enabled` / `lottery_count`** →
   客户端里 `self._lottery_enabled = False`、`self._lottery_count = 0`。
2. `search/dian115/client.py::checkin()` 里转盘是
   `lottery = self.run_lottery(self._lottery_count) if self._lottery_enabled else {}` → 恒为空，
   签到只报「签到 +4」，历史里 lottery 字段恒 null。
3. 配置其实**被读过一次**：`search/dian115/definition.py::create_client()` 正确取了
   `dian115_lottery_enabled` / `dian115_lottery_count`，但 registry 拿到这个返回值后传给
   `create_service()`（搜索定义走基类实现，返回 None）与 `create_provider()`（Dian115 的实现只认
   `service.get_client()`），**等于算完就丢**，还顺带每次多造一个没人用、也没人关的客户端实例。
4. 全仓库只有 `tests/` 里**没有任何 Dian115 用例**，所以这条接线断了没人发现。

一句话：**开关读到了、值也算出来了，但没送到真正跑签到的那个客户端对象上。**

## 3. 修法（1.6.36）

| 位置 | 改动 |
| --- | --- |
| `search/dian115/definition.py::configure_owner` | 按既有约定把 `dian115_lottery_enabled` / `dian115_lottery_count` 装配成 `owner._dian115_lottery_enabled` / `_dian115_lottery_count`（次数默认 1、上限 20，脏数据不炸） |
| `search/dian115/service.py::_get_dian115_resources` | 创建客户端时带上两个参数；`matches_config()` 也带上，改配置后自动重建客户端（不用重启插件） |
| `search/dian115/client.py::matches_config` | 新增可选参数 `lottery_enabled` / `lottery_count` 参与比对；不传则不参与（其它调用方行为不变） |
| `search/dian115/definition.py` | 删掉读了配置却被丢弃的 `create_client()`，客户端统一由 `Dian115SearchService` 持有，不再多造实例 |

行为不变的部分：转盘仍然只在签到链路、仍然「先读站点当天已用次数、只补差额」、仍然最多 20 次、
每次消耗 5 积分；关掉开关时签到文案与 1.6.35 逐字一致。

## 4. 教训

1. **配置有字段 ≠ 配置有接线**：前端字段、`create_client` 里读取、历史记录字段都存在，唯独
   执行路径上的那个对象没拿到值。这类「半接线」比完全没做更难发现，因为代码看起来哪哪都对。
2. **能力对象要只有一个来源**：`service.get_client()` 与 `definition.create_client()` 两处都能造
   客户端，谁被使用取决于调用方，结果一处带配置、一处不带。要么只留一处，要么让调用方复用同一个。
3. **新增渠道必须配一条「配置 → 客户端」的单测**：本次新增 `tests/test_dian115_lottery.py`
   9 例，直接断言 provider 的 CHECKIN 能力对象上 `_lottery_enabled` 为真；此前的 Dian115 用例数为 0，
   这正是同类问题潜伏的地方。
4. **线上证据先看记录字段再猜机制**：`lottery_target_count` 恒 null 立刻把方向锁到「转盘分支没进」，
   避免去查站点接口/积分/风控。已把这一点写进检查顺序：先看记录字段 → 再看日志 → 最后才看代码。

## 6. 追加复盘（1.6.37）：配置键根本没进运行期快照

- 触发：用户真机更新到 1.6.36 后触发一次手动签到，**转盘依旧一次没跑**
- 真机证据（2026-10-13 12:02:39，`trigger=manual`）：`message=「今日已签到」`（没有「转盘 N/20」片段）、`lottery_target_count` / `lottery_executed` / `lottery_cost_points` / `lottery_award_points` 全为 null；同一条记录里 `points_before=1239 / points_after=1182 / points_change=0`
  - 差额 57 与转盘无关：转盘只要跑过一次，记录里必然留下 `lottery_*` 与「转盘 x/y」文案；这里的差是账号余额快照与站点实际的漂移（`points_change=0` 说明服务层没结算任何转盘收支）
  - 由此把范围锁死在「转盘的 enabled 分支根本没进」，而不是站点接口 / 风控 / 积分不够
- 根因（本地加载线上同版代码复刻，非推断）：宿主处理器 `SearchHandler.__init__` 装配运行期属性时只遍历 `definition.get_config_keys()`

  ```python
  for key in definition.get_config_keys():
      setattr(self, f"_{key}", get_val(key))
  ```

  而 `SearchSourceDefinition.get_config_keys()` 只汇总**搜索分组**（`get_config_groups()`）的字段；「启用幸运转盘 / 每日转盘目标次数」两个键声明在**签到分组**（`get_checkin_definition().group`）里。于是这两个键从未落到处理器属性上，`configure_owner` 里 `config_value(owner.__dict__, "dian115_lottery_enabled", False)` 取到默认 False → 客户端 `_lottery_enabled=False` → 转盘分支不进。
  本地实测（1.6.36 代码）：`get_config_keys()` 共 11 个键、含 lottery 的 **0** 个；按宿主播种逻辑装配后 `handler._dian115_lottery_enabled` 属性根本不存在。
- 为什么 1.6.36 的修复没生效：1.6.36 修的是「客户端构造时漏传转盘参数」，而这条链路的**上游**（owner 属性）本来就是空的，改下游照样拿不到值。1.6.36 的单测把配置直接 `setattr` 到 owner 上，等于跳过了宿主播种那一跳，所以测试全绿、真机仍不工作。
- 修法（1.6.37）：
  1. `core/definitions.py::get_config_keys()` 把签到分组字段一并纳入快照（该方法同时被 `handlers/search/service.py` 的属性播种与 `core/api/search.py` 的隔离测试白名单使用，纳入属正确语义）；
  2. `search/dian115/definition.py::configure_owner` 取值改为「先查 owner 字典，缺失时回退宿主插件的同名键」，双保险。
- 教训：
  1. **测试要复刻宿主的装配路径，而不是绕过它**：把配置直接写进 owner 看起来端到端，实际跳过了最容易错的一跳。本次补的 `test_host_seeding_wiring_keeps_lottery_enabled` 就是按宿主那两行逻辑逐字复刻的。
  2. **同一份配置存在两套「键集」时，缺键会静默回默认值**：搜索分组 / 签到分组各有一份字段表，取值方只看其中一份，缺键不报错、只回 False。这类缺口必须在「键集」层面钉住（新增 `test_config_keys_cover_checkin_group_fields`）。
  3. **真机验收先看记录字段**：`lottery_*` 恒 null 一条就把方向锁死，比翻日志快。
