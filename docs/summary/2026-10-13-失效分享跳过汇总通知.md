# 结论：失效分享被静默跳过 → 汇总可见化（1.6.35）

> 2026-10-13。任务书：`../plan/2026-10-13-失效分享跳过汇总通知.md`；证据：`../test/2026-10-13-失效分享跳过汇总通知.md`

## 一句话

插件里「候选资源被跳过」原本只有 debug 日志、用户侧完全无感；1.6.35 起，被跳过的候选会按
**类型 + 网盘** 汇总成一行进日志，并在「本次未转存任何资源」的完成通知里说明原因，
不改变任何跳过行为本身。

## 用户诉求与范围

- 原话：「网盘分享链接失效插件不会反馈，而是直接跳过了转存」。
- 我给了 4 个修法，用户回「4」→ 只做**汇总入口可见化**；1（debug 升 warning）、2（落历史）、
  3（手动/点选接口返回原因）本次不做。
- 实施中发现第三类同样静默的跳过（内容与目标季/集不匹配），一并纳入统计 —— 否则用户原始症状
  很可能依然无输出（光鸭那条候选的具体失败点当时无法从 debug 日志区分）。范围修订记在任务书里。

## 结果

- 三类：`invalid` 分享链接失效、`empty` 分享无可用文件、`mismatch` 内容与目标季/集不匹配（共 6 个出口）。
- 日志：`本次跳过 N 个候选资源：分享链接失效 x、无可用文件 y、内容不匹配 z（115网盘 n、光鸭网盘 m）`
- 通知（仅原有那条「执行完成」通知，且仅当本次转存 0 个文件）：正文后追加
  `被跳过的候选：分享链接失效 x 个（网盘…）、…。`
- 无跳过记录时，日志与通知文案与 1.6.34 **逐字一致**（回归约束，有单测守）。
- 实现：新增 `core/services/skip_stats.py::SkipStatsCollector`（线程安全、按 `(kind, provider, reference)`
  去重、`take()` 取用即清零），采集一律走 `handlers/sync/resources.py::_record_skip_candidate`（内部
  try/except + 组件宿主兜底 `_plugin._skip_stats`），汇总在 `core/services/sync.py` 运行开始 `reset()`、
  完成日志后 `take()`、`finally` 兜底 `take()`。
- 验证：255 passed（基线 232 + 新增 23）、lint `--all` 0 error、版本两处 1.6.35、CI 出 Release。

## 决策与教训

1. **「跳过」必须留痕**：写「静默 continue」是性能与代码简洁的妥协，但对用户是黑洞 ——
   任何会被 `continue` 掉的候选，都应当能被汇总成一个可读的数字与原因。
2. **排查时靠日志级别区分不了失败点**：光鸭那条候选 3 秒内从「找到 1 个候选」走到「共转存 0 个文件」，
   三种失败点（失效 / 无内容 / 不匹配）在该级别下都是零输出。**信息量不足时不要假装定论**，
   与其猜是哪一类，不如让三类都可见（本次做法）。
3. **委派 + 独立验收有效**：两轮委派（第二轮因 ACP 环境硬拦截 pip 而重新下发指令、第三轮最大运行时中断），
   但改动落地完整；验收必须自己跑 pytest/lint + 读 diff + 自己写脚本核对文案格式，
   期间抓到「新模块导致既有测试 harness 缺注册」（委派方已顺手补上，我复核为仅补注册、无断言改动）。
4. **文案即契约**：把示例文案逐字写进任务书（含中文标点、括号、单位「个」），
   验收就能做字符串相等断言，不需要主观判断「看起来对不对」。

## 未做（若用户后续要）

- debug → warning：单条候选失败原因进生产日志。
- 跳过落历史：插件历史列表里能看到「跳过」条目。
- 手动/点选接口返回失败原因：前端点选后即时提示而不是等汇总。
- 洗版路径的「评分不足跳过」纳入统计。
