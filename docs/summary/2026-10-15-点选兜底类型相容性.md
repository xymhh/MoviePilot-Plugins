# 复盘：点选候选不建订阅，根因是「类型相容性否决了四级匹配」（1.6.42）

日期：2026-10-15　版本：1.6.41 → 1.6.42　类型：线上 bug 修复

## 现象与用户的问法

用户问「为什么搜索没结果时没有添加订阅」。这个问法本身包含一个**因果假设**：
「先搜索没结果，所以没建订阅」。日志显示的因果链正好相反：

```
用户点选候选 → 插件尝试接入订阅（失败）→ 透传给平台搜索 → 平台无可用站点 → 0 结果 → 「未搜索到资源」
```

「未搜索到资源」是**失败之后的下游症状**，不是原因。

## 根因（一句话）

登记记录被后台 TMDB 识别补上了类型（发「洛基」→ 补成**电影** 洛基 (2021) 636901），
用户点选的是**电视剧** 洛基 (2021) 84958；而 `pending_titles.consume()` 把类型相容性检查
放在四级匹配**之前**，类型不相容就 `continue` —— tmdbid / 同名 / 模糊 / 1.6.33 加的点选兜底
**四级全部失效**，`consume()` 返回 None。

同一形态 2026-10-15 出现两次（10:42「征途」电影 611395 vs 点选电视剧 336207；11:58「洛基」），
且核对订阅表确认两次都**没有**建出订阅。

## 修法

把「类型相容」在**点选路径**上从**否决条件**降级为**优先级**：
类型相容的登记记录优先，没有相容的才用最近一条兜底接入。
非点选路径（订阅搜索、扫描）保持 `if not compatible: continue`，行为逐字节不变。

## 教训

1. **「兜底」如果被前置的硬过滤挡死，它就不是兜底**。1.6.33 特意为点选路径加了
   `allow_sole` 兜底，但兜底的候选集在进入循环时就被类型过滤清空了 —— 加了兜底分支、
   却没检查候选集是否可能恒空。写兜底时要问：**这个分支在什么输入下永远不可达？**
2. **后台「补全」字段等于引入新的否决权**。`mtype` 本来是「未知就放行」，后台识别把未知
   写成了确定值（电影），于是一个**猜测**获得了否决用户明确动作的权力。凡是会被
   「补全」的字段，都要问它在哪些判断里是**否决级**的。
3. **用户的问法可能自带错误因果**。用户问「搜索没结果时为什么没建订阅」，真实链路是
   「订阅没建 → 才去搜」。查这类问题时，先按日志把**时序**摆出来，再回答因果，
   否则会顺着错误假设去查平台搜索为什么 0 结果（那条线本身也有问题：站点未认证）。
4. **同名影视是高频歧义**，而 TMDB 对中文短名的识别常常给出同名外语片/老片。
   只要有「同名不同类」的影视存在，任何以识别结果为准的类型判断都必须可被用户的
   明确动作覆盖。
