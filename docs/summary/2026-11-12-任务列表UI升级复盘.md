# 2026-11-12 任务列表 UI 升级 — 复盘（定论）

## 用户诉求

> 「我现在需要一个健壮逻辑，新增任务列表UI，跟上游仓库那样，历史记录你也看看上游是如何做的」

## 结论

- **任务列表**：从 184 行浮条 → 完整卡片（对齐上游 `RuntimeCard.vue` 能力），后端零改动。
- **历史记录**：**不改**。我们 2055 行已是上游同架构（`group_key` 聚合 + 服务端分页 + 展开明细 + 移动端手风琴），且多出「重试全部失败 / 重试选中 / 标记选中为成功」三项上游没有的能力。

## 我犯的错：凭一次查漏就下「做不了」的结论

调研 v1 我写「搜索渠道明细、后处理分步、待办计数 **无数据源**」，建议只做 5 项。用户追问「上游的搜索渠道明细如何处理跨盘转存，为什么我们做不了」——一查就发现**全都有**：

- `handlers/search/service.py:464` 的 `search_channels=progress_data.get("channels", [])` 与上游 `:481` **一字不差**
- `core/services/runtime.py:396/407` 的 `_idle_search_state()` / `_idle_postprocess_state()` 字段与上游**完全一致**

**错因**：我只 grep 了 `core/transfer.py`（跨盘任务），而 `search_channels` 属于**订阅搜索任务**那条线。**跨盘转存确实没有多渠道搜索阶段，但任务卡片本来就不只服务跨盘任务** —— 我把「跨盘任务的字段」当成「任务卡片的字段」了。

**教训**：判断「有没有数据源」时，要按**UI 消费方的语义**去搜（任务卡片会显示哪些任务 → 那些任务由谁产生 → 那个模块有什么字段），而不是只搜你最近改的那个模块。**用户比我更了解他自己的系统，他质疑时先复查，不要坚持。**

## 过程中抓到的 3 个真 bug（都不是用户报的）

1. `channelLabel({})` → `String({})` → 界面显示 `[object Object]`
2. `taskElapsedSeconds` 把后端**秒级** `started_at` 当毫秒 → 耗时恒为 0
3. `emit("stop-task")` **两个挂载点都没监听** → 按钮点了没反应

**共性**：都是「写完了、能构建、看起来对」但**实际不可用**的问题。第 3 个尤其典型 —— 组件自己 emit 了事件，编译通过，测试也能过，只有把「有没有监听者」当成断言才抓得到。

## 测试假通过（第三次）

`test_channel_label_fallbacks` 断言了 6 种输入，但**没覆盖空对象**这个真实 bug 场景，变异 B（回退旧实现）照样通过。补 `test_channel_label_no_object_string` 后才有效。

**规律固化**：写回归测试时，**变异反证必须对应你实际修的那个 bug 的具体输入**，不能只测「周边行为」。

## 发布事故：同版本号不会重建 Release

1.9.81 首次发布后（`18587d88`），我又提交了停止按钮接线（`0068dd84`），**版本号没变** → CI 判定「无变化」，**Release 没重建**，包内还是旧 `AppPage`。

读回核验时发现 `AppPage` chunk 里没有 `stop-task`，才暴露出来。

**规则（写进 MEMORY）**：**任何代码改动（含前端源码）都必须升版本号**，否则 CI 的变更检测会跳过 Release，用户装到的是旧包。

另：读回核验时我还一度误判「包内没有监听」，因为去搜 `stop-task` 字面量 —— 而 Vue 编译后是 **`onStopTask`**，且 `stopRuntimeTask` 被压缩器内联。**核验产物要按编译后的形态搜（`onXxx`），不能按源码写法搜。**
