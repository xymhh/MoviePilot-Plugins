# HDHaven 签到失败（BROWSER_REQUIRED）定位与修复 — 1.6.30

> 日期：2026-10-12　版本：网盘订阅助手 1.6.30
> 现象：签到重试汇总通知「HDHaven：失败，签到失败，HDHaven 无法获取 Cloudflare site key」

## 结论

HDHaven 站点（`hdhaven.com`）当天起对网页接口加了**浏览器 Fetch Metadata 判定**：请求缺少 `Sec-Fetch-Site` 等 `Sec-Fetch-*` 头即返回

```
403 {"code":"BROWSER_REQUIRED","message":"网页接口仅供浏览器访问，程序接入请使用 OPENAPI 授权"}
```

插件的 HDHaven 会话只有 UA / Accept / Accept-Language / Referer / Origin，**没有** `Sec-Fetch-*`（同插件的 hdhive、dian115、uindex 都有），于是 `GET /api/auth/registration-config` 恒 403 → 取不到 Turnstile site key → 每次签到都在这句报错上失败。

## 修法

`search/hdhaven/client.py` 的会话默认头补 `Sec-Fetch-Site: same-origin`、`Sec-Fetch-Mode: cors`、`Sec-Fetch-Dest: empty`（浏览器 XHR 的标准形态）。实测补头后该接口 200 并返回 site key。

## 影响面（重要）

不是「只有签到坏」：HDHaven 的**登录、搜索、解锁**都走这套网页接口，此前的 403 会一并影响它们——只是签到每周都跑、且失败会汇总成通知，所以先被看到。本版一并恢复。

## 判别方法（可复用）

- 站点把「非浏览器客户端」挡在外面时，先看响应体里的 `code`：`BROWSER_REQUIRED` 这种明确文案比 403 本身信息量大得多；
- 用**头隔离测试**定位到底缺哪个头（逐个加头重试），本次一步锁定了判据是 `Sec-Fetch-Site`，UA / Referer / Origin 都不是；
- 站点自己给的出路是 **OPENAPI 授权**：短期补头能恢复网页接口，长期若站点对网页接口再加 JS 挑战/TLS 指纹，插件就需要改走 OPENAPI（需站点签发的密钥，属新功能，另议）。

## 教训

该 fork 的多个站点适配器各写各的会话头，缺少统一基线——同类问题（某站点新增风控后某个适配器缺头）还会再出现。若后续再做此类修复，考虑把「浏览器基线头」抽成公共函数，避免逐个适配器漏。
