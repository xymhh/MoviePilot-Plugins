# 2026-11-13 集号识别与未播出守卫修复 — 复盘（定论）

## 用户诉求

《玫瑰战争》库 13 集、分享 14 集，手动添加却 `共转存 0 个文件`。我上一轮诊断给了两处错误结论（识别计划丢 E14、E14 被未播出守卫挡），用户一句「不是之前说是交集吗？应该要转14集啊」推翻了它——按 `missing ∩ share_episodes` 就该转 E14。本地复现 + 真机 preview 拿到真实文件树后定位真因：**E14 在 `share_episodes` 里凭空消失**，交集当然为空。

## 教训（比修复本身更重要）

1. **不要靠日志「没有失败记录」就推断「匹配阶段文件被拦」**。这次真实原因是两套集号解析口径不一致：识别计划（`classify_path._episode_from_name`）认「开头数字」，转存阶段的 `FileMatcher` + `rescue_tail_episodes_from_names` 只认「末尾紧贴数字」。`14 DV.mkv` 在前者是 E14、在后者是「认不出」。**同一份文件树在两处被用不同规则解析，且第二处只在「整批都无集号」时才兜底**——这是设计缺陷，不是数据问题。
2. **用户比日志更懂自己的系统，质疑时先复现，不要坚持上一条结论**。我上一条把「交集」和「识别计划丢文件」混着说，逻辑不自洽。喂真实文件树跑 `build_plan` 与 `rescue_tail_episodes_from_names`，十几秒就能得到确证。
3. **静态断言会被注释里的字符串骗过**：变异 B 第一次把 `unaired_episodes -= library_episodes` 换成 `pass  # MUTATED: unaired_episodes -= library_episodes`，字符串断言照样绿。改成 **AST 断言真实 AugAssign 语句**后才真正有效。
4. **行为级测试要执行真实函数体**，别把逻辑在测试里重写一遍（那样变异改了源码、测试照样绿）。用 AST 抽出方法体 `exec` + 注入可控依赖（`FileMatcher` / `MediaFileParser`），变异 A2 才被抓出。
5. 谷雨事故的防护（TMDB 无分集数据退回旧口径）要保留；这次只让**媒体库物理已存在的集**覆盖 TMDB 错位日期，不放宽「库里没有的集」。
6. 发布前仍要核 Release 包内容（之前吃过「同版本号不重建 Release」的亏）。这次三绿 + 包内读回三处关键字符串。
