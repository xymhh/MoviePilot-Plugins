# MP 插件安装永久卡死的真因：请求取消遗留 idle-in-transaction 连接持锁

> 状态：已定位并修复（守护已上线）。**推翻同日早前结论**——`2026-10-24-MP更新卡死根因-LexiAnnot编译占锁.md`
> 里"LexiAnnot 的 spacy→thinc 编译占住全局依赖安装锁"只是当时观察到的**伴生现象**，不是本问题的根因
> （那次确实有过一次卡死，但清理后仍反复复现的是本文描述的机制）。

## 1. 现象

- MoviePilot v3.1.9 里点插件"更新/安装"，界面永久停在"更新中"，点不动。
- 插件代码**实际已经更新成功**（`/app/app/plugins/cloudsubscribex/__init__.py` 已是新版本，插件也在正常跑）。
- 重启 MP 能暂时恢复，**但下一次更新又卡**。
- 事务表 `plugininstallation` 留下 `phase='prepared'` 记录，重启后 `recovery.py` 也无法回收。

## 2. 证据链

| 时间 (CST) | 证据 | 含义 |
| --- | --- | --- |
| 11:03:47 | `package.py - CloudSubscribeX 存在依赖，开始尝试安装依赖` | 安装进入依赖检查 |
| 11:03:50 | `lifecycle.py - 正在停止插件 CloudSubscribeX...` → `插件停止完成`（16ms） | 重载开始 |
| 11:03:54 | 插件日志 `[8e97350c…] - 搜索资源优先级：pansou` | **同一 request id**：插件其实已重载成功并在响应 |
| 11:03:50 之后 | 主日志再无任何插件安装相关行 | `registration_refresh` / `database_commit` 永不回来 |
| 事后 | `pg_stat_activity` 两条 `idle in transaction`，xact_age **36:55 / 31:39** | 与 11:03(CloudSubscribeX)、11:09(CloudDriveDisk) 两次安装精确对应 |
| 事后 | `wait_event_type='Lock'` 计数 0 | 等待方早已放弃，锁仍被僵尸事务持有 |

**根因链**：

1. 安装走同步长流程（下载 → 换入 → 依赖检查 → 重载插件树 → 注册刷新 → DB 提交）。
2. 前端在等待中刷新/超时 → HTTP 请求断开 → asyncio 取消安装协程。
3. 该请求的 DB 会话**没有回滚就退回连接池**，连接状态停在 `idle in transaction`，继续持有 `plugininstallation` 行的写锁。
4. 重载线程本身跑完了（所以插件能正常跑），但 `commit_installation` 永远拿不到锁 → 事务留 `prepared`。
5. 之后每次安装都撞同一把锁 → 连续卡死（11:09 的 CloudDriveDisk 就是第二例）。
6. 重启进程会释放锁，但 `recovery.py` 因"运行目录补偿快照不存在"跳过恢复并保留 journal → **prepared 行永存** → UI 永久"更新中"。

## 3. 修复

### 3.1 一次性清理（本次执行）

```bash
# 1) 杀掉僵尸连接（释放锁）
docker exec postgres psql -U moviepilot -d moviepilot -c \
  "select pg_terminate_backend(pid) from pg_stat_activity
   where datname='moviepilot' and state='idle in transaction'
     and now()-state_change > interval '5 minutes'"

# 2) 清掉卡死的安装事务（本次为 CloudSubscribeX / CloudDriveDisk 两条 prepared）
docker exec postgres psql -U moviepilot -d moviepilot -c "delete from plugininstallation"

# 3) 归档对应 journal（容器内）
docker exec moviepilot-v3 sh -c \
  'cd /config/plugin_transactions && for d in *; do mv "$d" "$d.orphan-bak"; done'
```

结果：`plugininstallation` 0 行，`idle in transaction` 0 条。

### 3.2 守护任务（防复发，已上线）

1Panel 计划任务 **`mp-plugin-tx-guard`**（id 32），`*/5 * * * *`，脚本逻辑：

1. 杀超过 5 分钟的 `idle in transaction` 连接（释放行锁）。
2. 删除 `updated_at` 早于 20 分钟的 `prepared` 事务，并把它对应的 `plugin_transactions/<tx>` 改名为 `.orphan-bak`。
3. 日志写 `/opt/1panel/apps/moviepilot/config/plugin_transactions/.guard.log`（保留最近 40 行）。

效果：即使再次因刷新中断，最多 5 分钟解锁、20 分钟清账，**不会再出现"永久卡住 + 只能重启"**。

## 5. 教训

- **"重启能解决"通常是锁/连接泄漏的信号**，不是配置问题。下次看到"重启就好、过会儿又坏"，先查 `pg_stat_activity` 的 `idle in transaction`。
- MP 的插件安装是**同步长事务 + 前端等待**的模型，前端刷新会打断提交。**等它自己转完，别中途刷新**（虽然现在有守护兜底）。
- 诊断要走"能自己执行"的通路：本机没有 MP 登录态，改用 1Panel 计划任务（`/api/v2/cronjobs` handle）作为宿主 shell 执行通道，全程自助排查，不依赖用户点击。
- 上游 MP 侧的正解应是：请求取消时回滚会话（or 安装改后台任务 + 轮询）。可向上游提 issue。
