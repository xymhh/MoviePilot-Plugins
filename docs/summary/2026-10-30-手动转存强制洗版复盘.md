# 手动/频道转存强制洗版：开关失效复盘（1.7.112）

> 日期：2026-10-30
> 关联：`docs/summary/2026-10-30-频道队列按集分发.md`（上一版只修了"整季基线"，没修"谁有权进洗版"）

## 结论

`core/api/sync.py` 里对"订阅绑定的手动提交"无条件注入 `manual_upgrade=True`，让它绕过全部开关直接进洗版链。用户关掉洗版开关后，Telegram 频道消息和手动转存照样打「【洗版转存】」、整季重建基线。1.7.112 改为按 `_is_cloud_upgrade_subscribe` 判定，只有真正在洗版范围内的订阅才走洗版。

## 影响面（线上实测）

| 现象 | 证据 |
| --- | --- |
| 洗版开关关闭无效 | 「嫁金钗」一条消息升了 36 集；「小城良方」重下 E01–E06，每集 4.3 GB |
| 空库订阅点转存 = 什么都不发生 | `handlers/sync/upgrade.py:172-177`：`manual_upgrade=True` 且无真实网盘旧文件时，只打一条 warning 就 `return`，不回退普通转存 |
| 队列水位居高不下 | 队列 74 条中 52 条是同剧多消息，每条都进洗版链（1.7.110 之前的量级问题） |

第二条是最容易被忽略的：用户看到"已提交"，实际没有任何文件被转存。

## 根因链

```
core/api/sync.py  手动提交
  └─ payload["manual_upgrade"] = True   （无条件）
handlers/sync/television.py:131-140
  └─ manual_upgrade or _enable_cloud_upgrade or subscribe.best_version  →  OR 短路
handlers/sync/upgrade.py:170
  └─ 打印【洗版转存】→ 建整季基线（target_episodes 只裁集数，不裁"是否洗版"）
```

`_enable_cloud_upgrade` 这个开关只在"是否自动进入洗版"处生效，入口强行传 `True` 后，OR 链一路短路。

## 修法（1.7.112）

1. `SyncApi._manual_upgrade_for_subscribe(subscribe)`：调用宿主的 `_is_cloud_upgrade_subscribe`，它同时校验全局开关、`best_version`、精选订阅 ID。
2. 注入点改为该方法的返回值；payload 里显式给了 `manual_upgrade` 时仍以调用方为准（保留 API 兼容）。
3. 判定抛异常 / 宿主没有这个方法（热升级残留旧类）时返回 `False` —— 保守走普通转存，绝不回退成强制洗版。

安全性依据：普通路径本来就按 `missing_episode_set & share_episodes` 只挑"当前缺失集"（`handlers/sync/television.py:647-653`），已入库的集不会被重复转存，所以"降级"不等于"整包重下"。

## 验证

## 教训

1. **开关的"入口短路"比开关本身更容易坏**。这次 `_enable_cloud_upgrade` 在功能代码里用得没错，坏在 API 层替用户做了决定。
2. **`or` 链上的默认值要看来源**。`manual_upgrade or enable or best_version` 里任何一处被上游写死 True，整条链就废了。
3. **"没转存"和"转存失败"是两种故障**。洗版路径空基线时只 warning + return，历史里没有失败记录，用户以为在排队——这类"静默成功"要在文档里点明。
