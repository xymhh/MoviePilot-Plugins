# 「集号不符」根因与转存匹配兜底（v1.9.73）

> 状态：已完成 2026-11-10，发布 `CloudSubscribeX_v1.9.73`

## 现象

手动添加《黑色五叶草》夸克分享（170 个文件，命名 `黑色五叶草001.mp4`…），日志出现：

```
识别计划[ready] 转 169 个 / 丢 1 个（文件 170）
本次跳过 1 个候选资源：集号不符 1（夸克网盘 1）
网盘订阅同步完成，共转存 0 个文件
```

识别阶段明明认出了 169 集，转存阶段却一个都不挑。

## 根因

两条路径用的不是同一套集号逻辑：

| 阶段 | 入口 | 紧贴数字命名 |
| --- | --- | --- |
| 识别（算计划） | `share_recognize.rescue_tail_episodes_from_names` | 有兜底，认出 169 集 |
| 转存（挑文件） | `FileMatcher.episode_candidates` → `episode_from_file` | **无兜底**，返回 `None` |

`episode_from_file` 依赖 MP 宿主的 `MetaVideo`，而它对「中文名+紧贴数字」不认（`黑色五叶草078.mp4` → `begin_episode=None`）。随后 `episode_candidates` 里：

```python
if found_episode is not None:
    ...
    continue
if mediainfo is not None:      # ← 有目标媒体就直接丢
    continue
```

所以 169 个文件全部被丢弃 → `matched_items` 为空 → 报「集号不符」。而账本里的 reason 是拿识别阶段的 `share_episodes`（`E01-E170`）和缺失集拼出来的，看上去"明明有交集"，进一步误导判断。

v1.9.71 只修了「转存前重算集号」，没修「转存时逐文件挑」。这是同一根因的第二段。

## 修法

`utils/file_matcher.py`：

- `episode_candidates` 先把文件与解析结果收集成 `entries`；
- 若**整批一个集号都解析不出**，按 `_tail_episode_from_name`（末尾紧贴数字，排除 4 位与分辨率）统计兜底，门槛与识别阶段完全一致：命中 ≥3、集号去重 ≥3、命中率 ≥80%；
- 兜底命中的集号只在与目标集号有交集时进 `strict_matches`；
- 平台能解析的文件、以及宽松匹配（loose/loosest）分支行为不变。

没有加 UI 正则输入：根因是转存阶段漏了兜底，不是规则不够灵活。补上同一套兜底后，这类命名的分享自动可用，也不引入用户需要手工维护的规则。

## 验证

- 新增 `tests/test_episode_candidates_tail_fallback.py` 6 例：
  - `黑色五叶草001-010.mp4` → E01-E10 各命中 1 个
  - 只补缺失集（目标 `[3, 7]` 只返回 3、7）
  - 命中率 <80% → 全部留空
  - 命中 <3 → 留空
  - `SxxExx` 命名行为不变
  - `1080` 这类 4 位数字不参与兜底
- 变异反证：把兜底赋值改成 `None` 后，前两例立即失败（证明测试真的覆盖兜底路径）。
- 全量 `pytest tests`：1370 passed（13 个 115 签到用例因本地缺 `p115client` deselect）。
- `scripts/lint.py --all`：0 error（473 文件）。

## 待真机复验

用户升级到 1.9.73 后重新转存同一分享，预期补齐缺失的 74 集（Emby 已有 96 集），日志不再出现「集号不符」，`黑色五叶草078.mp4`（55MB）仍按体积规则丢弃。

## 教训

- 「识别」和「挑文件」是两条独立路径，任何兜底规则必须两边都接，否则计划 ready 也没用。
- 账本 reason 用识别阶段的集号集合描述，与真正挑文件的逻辑不是同一个来源，排查时容易误判「明明有交集」。
