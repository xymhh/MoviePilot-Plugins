# 复盘：1.8.0 内置 aria2 全量回落（HTTP 400）— 2026-10-31

> 结论：**配置值超出 aria2 选项合法区间 → RPC 直接 400 → 每次下载都回落内置下载器**（功能等于没上，数据没坏）。
> 修复：1.8.1，`--max-connection-per-server` 封顶 16（aria2 硬上限），默认 16，配置项上限同步 16。

## 1. 现象

用户真机开「内置 aria2」后日志：

```
10:55:22,674 engine.py - aria2 下载引擎已就绪： 端口 57389, 并发 2, 连接 64
10:55:22,676 transfer.py - aria2 下载失败，回落内置下载器： 196 4K.mp4（HTTP Error 400: Bad Request）
```

daemon 起来了、`getVersion` 通、但**每个文件**在 2ms 内失败并回落。

## 2. 根因

`core/aria2/service.py` 把配置里的连接数（默认 64）原样写进两个选项：

```python
"split": "64",
"max-connection-per-server": "64",
```

`--max-connection-per-server` 在 aria2 源码里是 **1..16** 的受限选项，越界时 JSON-RPC 返回 **HTTP 400** + `{"error":{"code":1,"message":"We encountered a problem while processing the option '--max-connection-per-server'."}}`。我们的 `rpc.call` 把 HTTP 400 归成 `Aria2Error(-1, "HTTP Error 400: Bad Request")` → 接缝层按"失败"回落。

隔离复现（`/tmp/repro_400.py`，真实 aria2c 1.37.0）：

| 用例 | 结果 |
| --- | --- |
| 最小 addUri | 200 |
| 全 options（x=64） | **400**（指向 `--max-connection-per-server`） |
| 长 cookie 头（2000+ 字符） | 200 |
| 中文文件名 / 中文目录 | 200 |
| header 冒号后无空格 / 空值 | 200 |

## 3. 连带发现：aria2 对同一服务器的连接数硬顶 16

原架构假设"96 连接交给 aria2 吃"，实测**不成立**（`/tmp/probe_dup.py`，限速服务端 200 MB）：

| 配置 | aria2 自报连接峰值 | 服务端并发峰值 |
| --- | --- | --- |
| 单 URI，x=16，split=16 | 16 | 17 |
| 4 份相同 URI，x=16，split=64 | 16 | 16 |
| 6 份"查询串不同"的变体 URI，x=16，split=96 | 16 | 16 |

重复 URI、变体 URI、放大 split 都突破不了 16。结论：**aria2 单文件对单服务器最多 16 连接**，与插件内置下载器默认 16 并发同量级；夸克侧 64/96 连接的收益 aria2 拿不到。

## 4. 修复（1.8.1）

1. `service.py`：新增 `ARIA2_PER_SERVER_MAX = 16`，`connections = min(settings.connections, 16)`，`split` 与 `max-connection-per-server` 都用该值。
2. `Aria2Settings.connections` 默认 64→16、夹取区间 1..96→1..16；`config.py` 默认值、`__init__.py` 类默认与解析、前端字段 `max: 96→16` 与提示文案同步。
3. 回归用例 `test_connection_options_stay_within_aria2_limits`：断言 `split`/`max-connection-per-server` 落在 1..16。
4. 真机冒烟复跑（connections=16）：100 MB 0.80s、17 个 Range 请求、续传只发 55/100 MB、`kill -9` 后自动重启、取消干净、shutdown 无残留。

## 5. 教训

1. **"daemon 能起来"不等于"参数合法"**：选项校验发生在每次 addUri，必须在真机上跑一次真实下载，FakeRpc 单测永远发现不了。
2. 委派出去的实现，**选项取值必须由我给出并附来源**（本次任务书写了"连接数硬夹 96"，恰好把错误写进了规格——规格的错比代码的错更贵）。
3. 好处是回落层工作正常：功能坏掉时用户只是"没变快"，没有丢数据、没有卡住转存。

## 6. 未解决

- 想要 >16 连接只能绕开 aria2 的连接模型（自切 N 段、每段一个下载再拼接），等于把内置下载器重写一遍，收益可疑，暂不做。
- 若后续确认夸克在 16 连接下明显慢于 64 连接，那么 aria2 引擎的定位应写成"续传/崩溃恢复/单进程调度"，而不是提速；默认保持关闭。

## 7. 补记（2026-10-31 晚，1.8.2）：结论只是"上游标准版"的边界

用户追问"GitHub 上没有其它 aria2 吗"，查证后此前"aria2 单文件最多 16 连接"的说法要收窄：

- 16 是**上游 `aria2/aria2` 的源码常量**（`src/OptionHandlerFactory.cc:441-443`），不是协议或实现限制；
- `P3TERX/Aria2-Pro-Core`（⭐435）的补丁 `patch/0001-options-unlock-connection-per-server-limit.patch`
  直接把它改成无上限，并提供 Linux 静态二进制 Release；
- 换包实测：`x=64` 真开 64 连接、`x=96` 真开 96 连接（同一限速服务端，服务端并发计数 44 / 98）。

所以 1.8.2 的处理是：**换补丁版二进制 + 连接数上限恢复 96 + 保留"标准版拒绝时回落 16"的防御**。

教训修正：上一节的第 2 条教训仍然成立（规格写错最贵），但要再加一条——
**说"某工具做不到"之前先确认是标准上游的实现限制还是生态边界**；一次 GitHub 英文检索就能发现补丁版，
当时省下的 3 分钟，导致 1.8.0/1.8.1 连发两个版本才回到用户最初想要的 64 连接。
