# 媒体信息永远空白的根因与修复（1.7.74）

> 证据：[验证记录](../test/2026-10-26-1.7.74媒体信息提取验证.md)｜方案：[计划](../plan/2026-10-26-媒体信息提取改走神医任务.md)

## 结论

Emby 里剧集「有文件、能播放、但没有媒体信息（时长/码率/编码）」，在 CS 这一侧是两个独立缺陷叠加：

1. **触发方式无效**：CS 用 `POST /emby/Items/{id}/PlaybackInfo` 当"提取"手段。
   实测返回 200，但 Emby 不会因此跑 ffprobe，`MediaStreams` 依旧是空数组。
   真正会跑 ffprobe 的是神医助手注册的计划任务 `Extract MediaInfo`（Key `MediaInfoExtractTask`）。
2. **直链缓存比直链寿命长**：`core/api/redirect.py` 缓存 115 直链 6 小时，而实测 115 直链
   **≤70 分钟**就返回 `{"message":"request expired","status":403}`（19:46:17 签发 → 20:56 失效）。
   于是任何"稍晚一点"的探测（神医定时任务、用户重播、ffprobe）拿到的都是死链。

第三个是掩盖问题的坑：`with RequestUtils(...).get_res(...)` 在连接异常时 `get_res` 返回 `None`，
`with None` 抛 `TypeError: 'NoneType' object does not support the context manager protocol`，
日志里只剩"异常"，真实原因（超时/拒绝连接/DNS）全丢失。

## 修复

| 改动 | 位置 |
| --- | --- |
| 直链缓存 6h → 45 分钟 | `core/api/redirect.py` `_CACHE_TTL_SECONDS` |
| 触发改为启动 Emby 计划任务 `Extract MediaInfo`，5 分钟冷却、任务在跑则跳过 | `handlers/notification/media_server.py` `_trigger_mediainfo_task` |
| 统一 `_emby_request()`：`raise_exception=True` + 原样带出「异常类型: 消息」 | 同上 |

## 实测

40 集的《宋代足球小将》从 **4/40** 有媒体信息，触发任务后 150 秒内变成 **40/40**。

## 教训

- **401/200 不等于完成了事**：`PlaybackInfo` 200 是个典型"接口成功、语义没做"的例子。
  判断某接口是否真的触发副作用，要看最终数据（`MediaStreams`），不要看状态码。
- **缓存 TTL 必须短于上游签名寿命**，且要有实测依据；官方描述（12h）和实际（≤70min）差 10 倍。
- **`with` 一个可能为 `None` 的响应对象会掩盖真实错误**，诊断代码里应当显式判空并打印原因。
- 排障顺序应为「先确认触发手段有效，再怀疑链路」——本次先查了路径映射（1.7.67 修过），
  又查了 403/UA，最后才确认是触发方式本身无效，绕了远路。
