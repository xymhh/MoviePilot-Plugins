# 缓存残留与磁盘巡检（1.32.0）总结

> 任务书：[plan](../plan/2026-11-24-缓存残留与磁盘巡检-任务书.md) ｜ 证据：[test](../test/2026-11-24-缓存残留与磁盘巡检-验收.md)

## 起因

2026-11-24 德国 VPS 磁盘用到 91%（可用 11.1GB），
`/opt/1panel/apps/moviepilot/downloads` 里堆了 **38.16GB / 19 个文件**。
清盘时才发现插件侧根本没有回收机制：文件是 1.12.1 之后「目标名落盘」的新命名，
而残留清理的正则只认 `cloud-transfer-<hash>` 前缀。

## 两个判断（值得记住）

1. **命名变更没同步清理规则**：1.12.1 把缓存文件名改成目标名（不含 hash），
   但 `core/residue.py` 的分组只认旧前缀，注释里还写着「其它文件一律不碰」。
   这是典型的「改了一半」——写入侧换了命名，回收侧没跟上，失败文件就永久占盘。
2. **孤儿删除不管上传失败**：`delete_orphan_files` 删的是**云盘**孤儿 + 本地 `.strm`，
   且只在「提交前复查发现重复」时写 `orphan_location=`；上传失败这条路它不覆盖。
   所以把本地路径塞进 `orphan_location` 是错的方向（会让界面去删一个不存在的云文件），
   正确做法是让残留清理本身认识真名文件 + 用通知把体积暴露出来。

## 交付

- P0：`scan_residue(real_name_min_age_seconds=...)` 支持真名媒体（12 种视频扩展名），
  四道闸（扩展名白名单 / 在途任务名 / `.aria2` 伴随文件 / 独立保留期默认 24h），
  漏斗 `queued/processing/failed` 行指向的文件永久受保护，`held` 不保护；
  新增 `cross_transfer_real_name_retention_hours`（0 关闭、clamp 0~168）与配置页字段。
- P1：`CacheWatchService` + `CloudSubscribe_CacheWatch`（6h）——缓存目录 >20GB 或
  分区剩余 <15% 发通知、恢复发恢复通知、同状态 12h 去重。
- 测试：新增 17 条；全量 2989 passed，13 个存量失败与基线逐条一致；lint 0 error。

## 留个教训

盘满不是「存储问题」，是**可观测性问题**：38GB 在服务器上躺了 3 天（最老的文件
11-18 就在），期间没有任何一处会因为它超过阈值而发声。所以这次补的不只是清理，
还有「量一次、超了就说话」。
