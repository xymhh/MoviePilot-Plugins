# 1.6.45 复盘：跨盘转存「秒传未命中即中止」

> 2026-10-15｜任务书：[../plan/2026-10-15-秒传未命中即中止.md](../plan/2026-10-15-秒传未命中即中止.md)｜证据：[../test/2026-10-15-秒传未命中即中止单测.md](../test/2026-10-15-秒传未命中即中止单测.md)

## 起因

用户担心跨盘转存里「真上传」的流量拖累 115 账号：秒传没命中时不想让插件继续把文件完整上传一遍，要求**直接中止该文件的转存、删掉上传任务、清理本地缓存**。同时明确保留现有「回落普通上传」作为可选项——默认行为不能变。

## 改动与边界

1. **新配置 `cross_transfer_rapid_miss_action`**（`fallback` 默认 / `abort`）：三件套齐改（`core/config.py` 默认值、`__init__.py` 属性 + `_apply_sync_config` 读取并归一化非法值、前端 `transfer.js` select 字段），`CloudDriveManager` 把值接线进 `CrossTransferTaskManager`。
2. **abort 模式先探测后下载**：源文件有 sha1（115 场景）时零流量探测——p115 新增 `try_rapid_upload_by_hash`（只走 `upload_file_init`）；p115client 对 ≥1MB 文件要求二次校验范围（sign_check，形如 `start-end`）的 SHA1，没有本地文件时用 `_RemoteSha1RangeReader` 从源盘直链读该小段（百 KB 级下载、零上传、不落本地）；取链失败自动退回「下载后探测」。无法零流量探测（无校验和、直链失败）才先下载，下载后仍未命中同样中止。
3. **未命中 → 中止并清理**：`status="failed"`、`phase="aborted"`、`abort_reason="rapid_miss"`、message/error「未命中秒传，已按设置中止（未上传任何数据）」；本地中继缓存**无条件删除**（即使 `cache_complete` 为真也不保留——这是与 fallback 唯一的语义差别）；`CrossDriveTransfer.transfer(fallback=False)` 保证不进入 `upload_file`；探测未命中时若 115 侧返回上传会话信息则尽力 `oss_multipart_upload_cancel`（无残留跳过）。
4. **fallback 模式零影响**：所有新分支都在 `rapid_miss_abort` 护栏内；`fallback=(fallback and not rapid_miss_abort)` 在 fallback 模式下恒等于原 `fallback`；直传（can_stream / Range 直传）只在 abort 模式被禁用。
5. **单文件隔离**：每个文件是独立的 manager 任务，单个中止不影响同订阅其它文件（`test_abort_multi_file_isolation` 固定）。

## 教训

- **p115 的「秒传」不是拿到 sha1 就能探测**：`upload_file_init` 对 ≥1MB 文件有二次校验挑战（sign_check range），纯 sha1 探测只对小文件成立。第一版设计里「有 sha1 = 零流量」在 ≥1MB 场景必须拆成「零流量（小文件）」与「小段 Range 校验（大文件，零上传）」两档，编排层还要为取链失败准备「下载后探测」的降级路径——任务书写了三级降级，实现照单全收，缺一档都会在真机上翻车。
- **探测异常必须按「无法判定」处理**：`try_rapid_upload_by_hash` 内部任何异常都收敛为 `None`（继续走下载后探测），绝不能把探测抖动变成任务失败——否则 abort 模式比 fallback 更脆。
- **中止语义要靠「护栏」而不是「改共享函数」**：没有给 `CrossDriveTransfer.transfer` 加新参数分支，而是用现有 `fallback=False` 语义 + 编排层专属异常 `RapidMissAborted`，把「不上传」与「中止后清理」拆在两层，fallback 路径一行未动。
- **先更新状态再标成功**：命中秒传清理缓存时，第一版先 `_update(success)` 再删缓存，单测轮询到 success 时删除还没执行（竞态假失败）；改为先删缓存再标成功。终态字段与盘上状态对观测者必须原子可见。
