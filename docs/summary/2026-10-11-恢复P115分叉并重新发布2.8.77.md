# 恢复 P115StrmHelper 分叉并重新发布 2.8.77

> 状态：已完成 2026-10-11。上一篇 [撤下 P115 分叉与仓库瘦身](2026-10-11-撤下P115分叉与仓库瘦身.md) 的结论被实机证伪，本篇为准。

## 起因（用户实机反馈）

官方（DDSRem）2.8.76，即便开启「实用功能」，整理仍会失败：

```
整理失败，失败阶段：文件转移
媒体库存在同名文件，且质量更好
下一步：检查源文件和目标存储，修复后重新整理
```

用户要求恢复此前撤下的 fork 修改版。

## 事实核对（源码侧，2026-10-11）

- 官方仓库 `DDSRem-Dev/MoviePilot-Plugins`：`P115StrmHelper` 位于 **V2 线**，`package.v2.json` 版本 **2.8.76**；其 V3 线（`package.v3.json`）只有 P115Disk / P123StrmHelper / P115SubFixer / SaMediaSyncDel 等，**没有** P115StrmHelper。
- 官方 V2 线 `helper/transfer/handler.py`：`skip_reason = "媒体库存在同名文件，且质量更好"` → 写入 `task_failures[task_path]` → 并入 `failed_tasks` → `_record_fail` 落库为失败历史；同源唯一索引会用这条失败记录**替换掉该路径原来的成功记录**，于是同一文件被整理队列反复重投、反复推送失败通知。
- 结论：官方**没有**把该情形按「跳过」处理，与用户现象一致 → 上次「上游用配置项就能覆盖」的判断不成立。配置项管的是「谁来裁决」，不管「裁决结果怎么落库」。

## 决定与做法

1. **恢复源码**：从本仓库 git 历史 `775d12c9^`（撤下提交的父提交）取回 `plugins.v3/p115strmhelper`（410 文件，含 `dist/`、离线 wheels）、`frontend/p115strmhelper`（37 文件）、`package.v3.json`、单测工作流 `.github/workflows/test-p115strmhelper-v3.yml`。其中已含补丁提交 `c3dcb42c`（整理接管跳过语义）。
2. **版本号 2.7.26 → 2.8.77**：用户机器上装的是官方 **2.8.76**，MoviePilot 市场按版本号比较，必须**高于官方**才会显示「可更新」并允许直接覆盖安装。zkmydgth 上游线刻意用 2.7.x 是为了不给订阅者误报「官方已更新」，本仓库的用法不需要这个策略，故恢复时直接抬到 2.8.77。
3. **代码基线**：zkmydgth 上游（已同步官方 2.8.76 代码 + 一批 V3 适配修复）+ 跳过语义补丁。`version.py` 与 `package.v3.json` 版本同步，本地跑 `.github/scripts/verify_plugin_versions.py` 已通过（`[OK] P115StrmHelper 版本 2.8.77`）。
4. **文档同步**：README 恢复插件表项与安装步骤、写明「先撤后恢复」的原因（附官方失败日志原文）、排障表补两条（该失败消息 → 装 2.8.77；装了官方版看不到更新 → 同步插件源）。

## 跳过语义的边界（恢复后的行为，别记错）

| 情形 | 行为 |
| --- | --- |
| 库内同名文件质量更好（体积 ≥ 源文件） | 跳过：只记日志与通知；不写失败记录（保留原成功记录）、不发 `TransferFailed`、不登记智能体重试；**删除低质量源文件** |
| 覆盖模式 = `never` / 第三方插件拒绝覆盖等其它跳过原因 | 只记日志与通知，**保留源文件**（不比较质量，避免误删更好版本） |

## 本次明确没做

- 没有把补丁移植到 DDSRem 的 V2 线代码（本 fork 是 V3 线，用户宿主是 MoviePilot V3；V2 线仅作对照）。
- 没有改动官方源的配置项语义，官方配置项该怎么配还怎么配。

## 教训

- **「上游有配置项就能覆盖」是纸面结论**：只看源码分支与配置项名字就下了定论，没做真机 e2e，结果把可用的修复合集整个删掉，三天后又得从 git 历史里捞回来。此后这类判断必须拿到**实机证据**（日志/截图/库内记录）才落成删除动作。
- **版本号是分发契约**：自维护 fork 与官方同 id 时，版本号必须**高于官方**，否则市场里连更新入口都不给。
