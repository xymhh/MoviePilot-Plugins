# 复盘：移动云盘搜不到（1.6.39，PanSou 类型键错位 + 订阅搜索收窄）

> 任务书：[../plan/2026-10-14-移动云盘搜索类型键.md](../plan/2026-10-14-移动云盘搜索类型键.md)
> 证据：[../test/2026-10-14-移动云盘搜索类型键单测.md](../test/2026-10-14-移动云盘搜索类型键单测.md)
> 版本：`CloudSubscribe` 1.6.39（2026-10-14）

## 一句话

用户界面里「资源类型优先级 = 115 + 移动云盘」是**读得到、写得进**的，但移动云盘
资源一条都进不来 —— 两层各自独立的问题叠在一起：**跨系统词表没对齐**（`yun139` vs `mobile`）
和**一个只读不写的属性**（`_cloud_drive_resource_types`）。

## 出了什么事

线上配置齐全（115 目标盘、跨盘开、139 已授权、路径都填了），搜出来的资源里
移动云盘恒为 0，其它类型都正常。用户一开始的判断是「移动云盘资源本来就少」——
这个解释在**修复前后各测一次**才被证伪：同一关键词同一接口，只是把请求里的
类型键从 `yun139` 换成 `mobile`，移动云盘桶就从 0 变成 1。

## 根因（两层）

### 第一层：出站/入站词表错位

PanSou 接口的类型键与插件内部键不同名（`mobile`/`yun139`、`aliyun`/`alipan`）。

- 出站发内部键 `yun139`，接口按自己的词表过滤 → **整桶丢弃**（不是"没有资源"，
  是"根本没问"）。
- 入站拿接口键 `mobile` 比内部允许集 → **必然不匹配**，即使返回了也被丢。

两层都是"静默丢弃"：日志里只有总数变化，没有任何"类型不认识"的提示。

### 第二层：死属性 `_cloud_drive_resource_types`

订阅搜索会把允许类型收窄成"能落地的类型"，读的是 `_cloud_drive_resource_types`；
但**全仓没有任何地方给它赋值**（只有读），于是永远走老兜底 `{目标盘, magnet, ed2k}`。
跨盘来源（139 → 下载 → 上传 115）不在兜底里 → 订阅搜索必砍。

注意这层的**独立性**：只修第一层，资源列表页能看到移动云盘，订阅搜索仍然拿不到。
两层必须一起修，否则用户会看到"资源页有、订阅搜索没有"的更迷惑现象。

## 决策

1. **在词表层做双向映射，而不是改内部键**：内部键 `yun139`/`alipan` 被前端目录、
   驱动注册表、转存路径配置（`yun139_transfer_path`）等大量复用，改内部键是翻修；
   在边界（出站请求、入站归一化）映射，改动面最小、可回滚。
2. **入站统一归一化到内部键**：分组名顺带从 `mobile` 变成「移动云盘」，前端类型目录
   不用改（此前 `aliyun` 也是靠下游某处归一化成 `alipan` 才显示正常的，属于隐性依赖，
   现在提前到解析入口）。
3. **能力回写用"每次重算先清空"**：切换网盘后不残留上一台的能力集合，
   无活动网盘时清空（避免搜索侧拿到过期线索）。
4. **收窄链保留旧兜底作为最后一档**：只有两条线索都缺时才回落 `{目标盘, magnet, ed2k}`，
   保证与旧版行为在异常路径上一致（有单测钉住）。
5. **不做范围外的事**：不扩资源页词表（`others` 兜底桶要不要展示另议）、不动其它
   来源的逻辑、不顺手重构缓存层。

## 教训

1. **跨系统边界要各存一份词表并做显式映射**——"内部键 = 外部键"这个假设没有测试钉住时，
   就是静默丢数据的温床。别名表（入站）当时只做了一个方向，出站方向压根没写。
2. **只读属性的杀伤力等于"功能没接线"**：`_cloud_drive_resource_types` 在搜索侧
   有完整的分支逻辑，但那里永远不会命中——读的人不知道它是死的。
   写测试时要断言"**它被写成了什么**"，而不是"读到它时怎么分支"。
3. **兜底分支必须可观测**：老兜底 `{115, magnet, ed2k}` 让功能看起来"照常工作"，
   用户和日志都看不出被砍了什么。这次保留了兜底但加了注释与单测；下一版可考虑
   在收窄掉类型时打一行 INFO。
4. **"资源本来就少"这类解释必须先反证再接受**：用户的合理猜测把一个接口契约 bug
   藏了很久；对照实测（改前/改后同一请求）是最省事的证伪手段。
5. **多测试文件共用进程时，Mock 会互相污染**：本次新测试必须显式按文件加载
   `core.cloud` / `core.transfer` / `drive.scanner`（否则同进程里先跑的测试把
   `cloudsubscribe.core.cloud` 注册成 Mock，`CloudDriveCapability` 枚举就不是真的了）。
   这是既有测试组织方式的隐性成本，后续测试照此办理。
