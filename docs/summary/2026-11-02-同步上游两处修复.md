# 同步上游两处缺失修复（1.9.27）

> 日期：2026-11-02　版本：1.9.27　提交：`59d088f`

## 背景

用户提出「加了这么多功能，可能存在 bug」，要求对比上游仓库。本仓库从上游 `odomu/MoviePilot-Plugins` 的 **1.6.22** 分叉（README 记载），上游当前已到 **1.7.6**（2026-10-29 推送）。分叉后的上游修复本地不会自动获得，必须逐条对账。

## 对比方法

1. `git clone` 上游全量历史（72 条提交），筛出 **32 条 fix 类提交**；
2. 对每条提交，把 diff 里的新增行拿到本地插件源码全文做子串匹配，算出「新增行命中率」；
3. 命中率 < 60% 的逐条人工核验，再看新增函数名在本地是否存在；
4. 区分三种情况：**真缺失**、**本地已用等价实现覆盖**、**架构路线不同（不算缺失）**。

## 本次修复内容

### 1. 光鸭 `signedURL`（`drive/guangya/files.py:112`）

光鸭 API 在不同接口/时段返回的直链字段名不一致，部分响应是 `signedURL`（全大写 URL）。原代码取不到值后抛 `RuntimeError("光鸭未返回有效下载地址")`。

影响面（沿调用链确认）：
- `core/api/redirect.py:88` → 光鸭 **302 播放失败**
- `core/transfer.py:1659/1760/1793` → 光鸭 **跨盘转存失败**

修复：在字段优先级最前面补 `signedURL`。

### 2. Bangumi 正片集数核对（`handlers/sync/metadata.py` + `television.py:186`）

Bangumi 条目的 `total_episodes` 含 OP/ED/SP，而 `eps` 才是正片数。若订阅总集数抄了前者，TMDB S01 会一直算出「缺 E13-E15」这类虚假缺集，导致反复搜索无效资源（与账本里 254 条非影视噪音同源）。

修复逻辑（三重相等才动手）：

```
TMDB 已播最大集号 == BGM 正片 eps  <  BGM 总条目  ==  订阅 total_episode
```

- 仅 `season == 1` 且媒体身份为 themoviedb；
- TMDB 集号必须连续（`1..main`），断档说明不是纯正片序列，不动；
- 命中后 `SubscribeOper().update(id, {"total_episode": main})` 并同步内存对象；
- 任何异常只记 `logger.debug(..., exc_info=True)`，不阻断主流程；
- `transient_target`（临时目标）不参与。

## 教训

1. **分叉即欠债**：本地版本号跑到 1.9.x 会让人误以为「比上游 1.7.6 新，什么都不缺」。版本号是本地自增的，与上游修复无关。需要定期（每季度或每次大改前）跑一次上游 fix 对账。
2. **对账要用文本命中率，不要凭印象**：32 条提交里只有 5 条真缺失，人工扫代码会漏也会误判；先机械算命中率再人工核验，成本最低。
3. **区分「缺修复」与「路线不同」**：`resolve_base_url` 命中率 35% 但本地 STRM 走 redirect，属于架构差异，跟了反而制造双实现。
4. **本地 lint 预算会拦住「上游写法」**：上游用 `logger.debug(f"...{error}")`，本地预算要求 `exc_info=True`；移植代码要按本地规范改写，不能照抄。
