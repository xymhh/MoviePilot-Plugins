# v1.9.12 追更进度表整表归零复盘（2026-11-01）

## 现象

用户更新到 v1.9.12 后反馈「问题更大了」。真机截图表现：

- 「全部订阅（10）」——实际库里有 79 条订阅
- 卡片文案是「已转存 13 集 / 已全集转存 / 有待补/跳过集」——这是**历史记录卡片视图**的旧文案
- 进度条按「成功记录数 / 本组记录数」计算，与订阅无关

## 根因

`core/api/page.py` 的 `_build_subscribes_progress()` 在 v1.9.12 新增了「合并 HistoryRecord 成功集」的代码块，但把该块插到了 `tmdb_id` 赋值**之前**：

```text
:401  history_success_map.get(f"tmdb:{tmdb_id}:{eff_season}", ...)   # 用了
:406  tmdb_id = getattr(sub, "tmdbid", None) or ...                   # 才赋值
```

`tmdb_id` 是函数局部变量（后面有赋值），提前引用抛 `UnboundLocalError`；该异常被
逐条 `except Exception: logger.debug(...); continue` 静默吞掉 → 53 部剧全部被跳过 →
`subscribes_progress` 返回 `[]` → 前端 `AppPage.vue:122`
`subscribesProgress.length ? subscribesProgress : historyGroups` 退化到历史分组视图。

**一个静默的 `except` + 一个「空则回退」的兜底 = 表象完全看不出后端炸了。**

## 修复

1. `tmdb_id` / `state` 解析前置到合并逻辑之前（回到 v1.9.11 的次序）
2. 合并键加 `if tmdb_id` / `if name` 保护，避免 `None` 参与拼 key
3. 单条订阅失败不再静默：`logger.warning`（最多 3 条）+ 循环结束汇总「跳过 N 条 / 成功 M 条」
4. 外层 `SessionFactory` 读取失败的日志 `debug` → `warning`

## 验证

隔离单测 `docs/test/test_subscribes_progress_isolation.py`：用 ast 抽出真实函数体，注入假
`app.*` 模块与假订阅/历史数据直接跑。

- 旧版代码（`CS_PAGE_PY=/tmp/page_v1912.py`）：`cannot access local variable 'tmdb_id'`
  → 返回空列表 → 断言失败 ✅ 复现
- 修复后：牧神记 13/13 缺 0；尚公主 20/24 缺 E21-E24；电影 total=0 不报缺 ✅ 通过

线上真实数据核对（`GET /api/v1/subscribe/`，79 条 = 53 剧 + 26 电影）：修复后按
`note ∪ 历史成功集` 计算，53 部剧全部存在缺集，例如 牧神记 93/110 缺 17、仙逆 165/200
缺 35、伟大的长征 41/60 缺 19 —— 与「已全集转存」截然不同，反证截图就是兜底视图。

## 教训

- **凡是「空数据就回退到另一套渲染」的地方，必须能区分「真的空」与「后端挂了」。**
  目前仍保留该兜底（电影模式要用），后续可加一条「订阅接口异常时显式提示」。
- 单条循环里的 `except: continue` 一定要有可观测出口（计数 + 汇总告警），否则整表归零
  只能靠用户肉眼发现。
- 每次发布前跑一遍隔离单测，比在真机上反复试错便宜得多。

# 追加：v1.9.13 之后「卡片与分集矩阵两边不一致」（同日）

## 现象

抽屉头部「已入库 93 集 / 待补齐 17 集 / 全剧共 110 集」，但矩阵里 93–106 全涂绿，
只有 107–110 是待补 —— 说缺 17，实际只看到 4 个灰块。

## 根因

线上 `page_data.subscribes_progress` 实测：`牧神记 tmdb_id = None`、`library_episodes = 1..92,97`、
`missing = 93..96,98..110`，而 `records` 里 13 条 `status=成功`（E93–E106，`subscribe_id=None`，
`tmdb_id=236534`）。

1. **后端合并键失配**：MoviePilot V3 的订阅把外部 ID 放在 `media_source + media_id`
   （实测 `media_id="236534"`），`tmdbid` / `tmdb_id` 都是空的 →
   `_build_subscribes_progress` 拼出 `tmdb:None:1`，13 条成功流水一条都没并进 `library_episodes`。
2. **前端各自为政**：`MediaDrawer.episodesList` 在 `library_episodes` 命中不到时，会回落到
   「records 里有成功记录就算已入库」→ 93–106 被涂绿；而头部数字用的是后端聚合的
   `library_count/missing_count`（93 / 17）。**同一屏两个数据源，必然打架。**

## 修复

1. 新增 `_resolve_subscribe_tmdb_id()`：依次尝试 `tmdbid` → `tmdb_id` → `media_id`
   （后者要求 `media_source` 含 tmdb，或来源为空时按 TMDB 处理）。
2. `MediaDrawer` 口径收口：有 `total_episodes`（后端聚合）时，已入库只认 `library_episodes`，
   单条流水不再把状态改绿；集数上界严格取 `total_episodes`。

## 验证

隔离单测新增 V3 形态用例（`tmdbid=None`、只有 `media_id="236534"`、历史 title 是文件名）：

- v1.9.13 代码：`已入库 93 / 缺 17`（与线上截图完全一致）✅ 复现
- 修复后：`已入库 106 / 缺 [107,108,109,110]` ✅ 通过

## 教训

**「两边不一致」几乎总是因为两边各自算了一遍。** 任何统计口径只能有一个真相来源，
前端只做展示、不做第二次推断；后端缺字段时要修后端，不能在前端补一层兜底推断。
