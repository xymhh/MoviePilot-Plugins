# 追更表「已入库永远等于订阅 note」复盘（v1.9.17）

> 状态：已修复 2026-11-01，发布 v1.9.17

## 现象

连发 v1.9.14 / v1.9.15 / v1.9.16 三版，TMDB 身份、电影落地判定、缺集连续段都改对了，
但用户更新后数字纹丝不动：

- 牧神记仍是 93/110，缺 17 集（正确应为 106/110，缺 4 集）
- 所有订阅的「已入库」恰好等于 `subscribe.note` 的长度，一条历史都不多

## 根因

`_build_subscribes_progress` 里用 MoviePilot 的 `SessionFactory`（PostgreSQL 会话）
去查 `HistoryRecord`：

```python
with SessionFactory() as db:
    subscribes = db.query(Subscribe).all()
    history_rows = db.query(HistoryRecord).all()   # ← 查错库
```

`HistoryRecord` 属于插件**私有 SQLite**（`CloudSubscribeBase`，表 `history_records`），
在 Postgres 里根本不存在这张表。查询抛 `UndefinedTable / sqlstate 42P01`，
被外层 `except` 一把兜住 → 回退 `SubscribeOper().list()`（能成功）→
继续往下走，但 `history_success_map` 是空的。

证据：MoviePilot 日志里每次打开工作台都有一条

```
【ERROR】 diagnostics.py - 数据库驱动异常：database=postgresql, driver=psycopg2,
        error_type=UndefinedTable, sqlstate=42P01
```

## 为什么连修三版都没露头

1. `except` 里回退成功，函数正常返回 76 张卡片，**没有任何异常外观**；
2. 卡片的 tmdb 解析、电影判定、缺集分段都是独立逻辑，全部"正常"，
   只有「历史并入」这一环被静默掏空；
3. 隔离单测当时用假 `SessionFactory` 同时喂订阅和历史，把这条错误路径
   一起 mock 掉了 —— 假对象永远查得到数据，测不出"查错库"。

## 修法

```python
store = self._get_data_store()
store.initialize()
history_rows = store.repositories.history.list_all() or []   # 插件自己的库
if not history_rows:
    logger.warning("插件转存历史为空，已入库将只统计订阅 note")
```

- 订阅仍在平台库（Postgres）读，历史改回插件库（SQLite），两个数据源各归其位。
- 补「历史为空」告警：这类口径故障必须能在日志里被看见，不能静默降级。

## 教训

- **跨库查询必须先确认模型属于哪个库**：`app.db` 的 `SessionFactory` 只认平台表；
  插件的 `CloudSubscribeBase` 子类一律走 `store.repositories.*`。
- 已全仓排查：`task_center.collect_tasks` 用的是 `store.manager.session`（正确），
  只有 `page.py` 一处越界，已改净。
- **假对象会掩盖架构错误**：mock `SessionFactory` 能测业务分支，但测不出"该不该
  用这个会话"。凡涉及数据来源的修复，必须再跑一次线上真实数据的全量对账。
