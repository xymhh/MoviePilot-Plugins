# 2026-11-12 1.9.78 上传代理真机修复 — 复盘（定论）

## 我的错误（两次）

1. **1.9.75**：按 `session/client/_session/http` 属性名猜 p115client 的内部结构，全落空 → 回落直连，但日志明确写了「未暴露可注入的会话」，至少没撒谎。
2. **1.9.76**：为了「修好」这个问题，包装了 `self.request` 并打出 **「115 上传代理已生效」** —— 而真机核实**完全没有生效**。这是最严重的一类错误：**用一句日志掩盖了「没做到」**。用户是靠「mihomo 里没有连接」发现的，不是靠我的日志。

**教训（写进 MEMORY）**：任何「已生效 / 已启用」日志，必须有**可外部观测的旁证**（对端连接列表、流量计数、目标端日志），否则不许打。宁可打「已配置，待验证」。

## 真根因（源码级，已核实）

- `p115client` 的 API 走 `ClientRequestMixin.request` → `get_request()` **不传 `self`**，直接 `from urllib3_future_request import request`。
- `p115oss` 的 OSS 请求（`oss_request` / `upload.py`）同样自己 import 模块级 `request`。
- 两者都不经过 client 实例 → 包装实例方法对**数据上传腿**天然无效。
- 唯一有效注入点：`urllib3_future_request.request_sync(session=...)`，把 `PoolManager` 换成 `ProxyManager`（子类）。

## 修复原则

- **只给 OSS 数据面注入**（`session=` 传给 p115oss 的 init/part/complete/cancel），115 API 保持直连 —— 避免动 cookie 与风控面。
- **代理不可用一律回落直连 + WARN**，绝不让代理故障打断上传（与架构篇 fail-open 一致）。
- **顺带复用 MP 的 `PROXY_HOST`**：插件留空时自动回落，用户只需在 MP「网络设置」填一次。

## 顺带纠正的认知

- **MP 的「网络设置」不会让插件上传走代理**：源码里 `settings.PROXY` 只有 5 处调用 `RequestUtils` 用于图片代理 / GitHub Release 查询 / 网络测试，与插件内 p115client 无关。它只是**配置来源**，不是**生效通道**。
- **代理不一定更快**：本机 3 次采样，直连 OSS 中位 0.99s、经 mihomo 1.38s。代理的价值在于换出口/绕限速，不在降低 RTT；真机若变慢，把代理留空即可。
