# 2026-11-12 1.9.76 真机冲突 — 复盘（定论）

## 根因

用户切「回落普通上传」+ 配代理后仍卡在 `6 分钟前已确认未命中（115），24 小时内不再下载`，是 4 个问题叠加，全部是代码缺陷，与用户操作无关：

1. 24h 负缓存读取**无模式条件**（`core/transfer.py` 4 处 `raise RapidMissAborted` 里唯一一处没带 `if rapid_miss_abort:`）→ fallback 也被历史 abort 负缓存拦住。
2. `except RapidMissAborted` 无条件重写负缓存时间戳 → **TTL 自我续期，等 24 小时也不会恢复**。
3. 改配置不重建 `CloudDriveManager`（`service_config_keys` 不含 `cross_transfer_*`，且 `_refresh_platform_services()` 不重建它）→ 运行期动作可能是旧值。
4. 1.9.75 代理注入按 `session/client/_session/http` 猜 p115client 内部结构，线上走 `urllib3_future_request` 模块级 callable，全部落空 → 回落直连（真机日志明证）。

## 教训

1. **默认值会掩盖逻辑缺陷**：负缓存无条件读取是历史遗留，abort 长期是默认/唯一实用模式，从不暴露；用户一切到 fallback 就炸。以后给「多模式开关」加能力，必须补**跨模式交叉单测**，不能只测默认模式。
2. **缓存命中路径绝不刷新 TTL**：命中即重写时间戳等于永不过期。缓存读与缓存写必须分离，写入只发生在「真实新探测」时。
3. **配置运行期同步不要依赖重建集合**：加键到 `service_config_keys` 只会调 `_refresh_platform_services()`，而它不重建 drive manager —— 加了也没用。正确做法是给运行期对象一个 setter，`_apply_plugin_config` 直接同步。
4. **第三方库内部结构不能靠猜**：按属性名猜 session 是脆弱实现，必须看源码并在真机验证；失败时日志要明确「回落直连」，不能静默。
5. **诚实标注覆盖边界**：p115oss 分片 PUT 的 `**request_kwargs` 是否接受 `proxies` 未在真机验证，盲传可能被底层抛 `TypeError` 打断上传；本版**明确不碰**，而不是假装「代理已全链路生效」。同理不设全局环境变量代理（会把 MP 进程的 TMDB/TG/搜索 HTTP 一起带进代理）。
6. **真机日志是最有效的验收**：本次所有根因都来自 `cloudsubscribex.log` 的实际行，而不是推测；1.9.75 的「本机全绿 + CI 三绿」并不能证明模式切换场景可用。
