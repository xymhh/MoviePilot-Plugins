# 移除任务中心（1.9.44）

## 决策

用户 2026-11-05 反馈「任务中心看着多余，不知道有什么用」，在三个方案中选 **B：整块删掉任务中心，全局暂停开关移到顶栏 ⋮ 菜单**。

## 依据（线上实测，2026-11-05 16:5x）

`GET /api/v1/plugin/CloudSubscribeX/tasks` 返回 200 条（接口上限），分布：

| 项 | 数量 | 说明 |
| --- | --- | --- |
| `处理中`（`retry_wait`） | 192 | 无阶段、无动作可做；最早 10-27，最老 164 小时未动 |
| `失败`（含死信） | 5 | 真正的失败 |
| `下载中` | 3 | 当时真在跑 |

- 185/192 条错误文案同为「转存实现返回失败」（`handlers/sync/transfer_ops.py:653`，实现返回 False 时的兜底文案，真实原因被吞）。
- `retry_wait` 只会在下一轮同步碰到**同一文件**时被 `SyncJobLedger.claim()` 认领，没有后台 worker 轮询 → 这批行永远不会自己动。
- 任务调度页顶部已有 `RuntimeCard` 展示运行中/排队中进度，下面的表把同样内容再列一遍 → 重复感。

结论：功能本身（暂停开关、死信重试）有用，但**数据卫生 + 展示未收敛**导致完全不可用，用户选择直接去掉这块。

## 改动

1. `frontend/cloudsubscribex/src/components/AppPage.vue`：删掉 `<TaskCenterTable>` 及其 import、`.task-pane :deep(.task-center-panel)` 样式、无用的 `showTaskCenter` ref；删除 `components/dashboard/TaskCenterTable.vue`。
2. 全局暂停开关移入顶栏「更多」菜单：`暂停转存 / 恢复转存`，打开菜单时 `GET /sync/pause` 读真实状态，切换走 `POST /sync/pause`，成功/失败都有 toast。
3. 后端 `/tasks`、`/tasks/retry`、`/tasks/pause`、`/tasks/resume` 接口**保留**（CLI 与既有调用不受影响），仅前端不再调用。

## 代价（已知，用户接受）

- 死信作业的手动重试 UI 入口消失；需要时走 `cli.py ledger` 或直接调 `/tasks/retry`。
- 单任务暂停/恢复的 UI 一并消失（只挡认领的能力仍在后端）。

## 遗留

- 192 条 `retry_wait` 僵尸仍留在库表里，不影响页面（不再有表展示），但也没有回收。若以后要治理：给 `retry_wait` 加「超过 N 小时无人认领 → 转 failed(dead_letter) 并写明真实原因」，同时把 `transfer_ops.py:653` 的兜底文案换成具体失败原因。
